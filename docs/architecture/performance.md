## Threads and the main thread
- `AudioRecord.read()` blocks, so it runs on `Dispatchers.IO.limitedParallelism(1)`. DSP runs on `Dispatchers.Default`. The reference tone's and the metronome's blocking `AudioTrack.write()` each have their own single thread too (`IO.limitedParallelism(1)`), and the drone's has a thread of its own at `THREAD_PRIORITY_AUDIO`, gone a few seconds after it stops ([Notes, tunings and audio](notes-and-audio.md), *Reference tone*; [Strum check and metronome](strum-and-metronome.md), *Metronome*).
- **No allocations in the per-frame loop.** Buffers are allocated once; per-frame garbage at ~47 Hz causes GC jank.
- **YIN difference function via FFT.** The direct O(W·τ_max) sum (~2.6 M multiply-adds per frame) took 69 % of the app's CPU cycles on the S26 (~7 ms per frame). `FftDifference` computes `d(τ) = e(0) + e(τ) − 2·r(τ)` (paper, eq. 7): energies as a running sum, the cross-correlation from one complex FFT carrying both real inputs plus one inverse (N = 4096, or 8192 for low notes; radix-2 `Fft`, doubles, no allocation). `FftDifferenceTest` checks it within 1e-10 of the direct sum. `./gradlew :core:dsp:benchmark` (kept out of CI): YIN **1.05 → 0.48 ms** per frame on the JVM. Budget: 2 ms.
- **FFT passes block by block.** Run twiddle by twiddle, each pass sweeps the whole arrays once per twiddle; at N = 8192 (128 KB of doubles) they don't stay in the CPU's cache, and the low-note window cost 4× the standard one on the JVM. Walking each pass block by block, in memory order, gives identical results and: JVM 0.48 → **0.18 ms** (4096), 2.0 → **0.49 ms** (8192).
- **The refinement on the lowest partials without another FFT** (Phase 46, 2026-10-28; [Signal pipeline](signal-pipeline.md), *Pitch detection*, item 3). The band-limited correlation is summed straight from the bins `FftDifference` keeps, at the ~100 lags around the dip only, and the tapered energies take 3·W multiply-adds: in all a few tens of thousands of operations a frame, where a second inverse FFT (and a time-domain filter's start-up) would have cost more. `YinBenchmark` on the JVM: 0.17 → **0.20 ms** (4096), 0.38 → **0.53 ms** (8192). Xiaomi 12X (`scripts/dsp-phone-benchmark.sh`): detector 0.31 → 0.34 ms and 0.70 → 0.77 ms; gate + detector + smoother 0.33 → **0.37 ms** (1.7 % of a core) and 0.76 → **0.83 ms** (3.9 %); on the little cores 2.3 → 2.45 ms (11.5 %) and 5.2 → 5.5 ms (26 %); the watch chain at 16 kHz 0.46 → 0.49 ms, 2.7 → 2.9 ms on the little cores (14 %). Far inside the hop and the budget; the tables below are from before.
- **The low range's mains hum canceller** (Phase 46; [Signal pipeline](signal-pipeline.md), *Low notes*, *Mains hum*). It runs once over each hop's new samples, not over the window: 11 adaptive notches, a few multiply-adds each per sample, in doubles. `YinBenchmark` on the JVM: **0.035 ms** a hop (the low-range detector 0.40). Xiaomi 12X (`scripts/dsp-phone-benchmark.sh`, 2026-10-28): 0.083 ms a hop; low range hum + gate + detector + smoother 0.83 → **0.91 ms** (4.3 % of a core); the standard range has no canceller and stays at 0.37 ms.
- **StrictMode in debug builds** (Phase 65): `TwangleApplication` turns on StrictMode's thread and VM policies with `detectAll()` and `penaltyLog()` only when `BuildConfig.DEBUG`, so a file read on the main thread or a leaked closeable shows in logcat (tag `StrictMode`) while building; nothing is stopped, and release builds never run it.
- **Only visible changes reach the main thread:**
  - **Silence:** equal `Listening` states are dropped with `distinctUntilChanged()` on the DSP dispatcher.
  - **ViewModel:** `distinctUntilChanged { old, new -> old.looksLike(new) }` drops readings that would look the same as the last one *sent*: same text (whole cents, 0.1 Hz) and the needle within `NEEDLE_STEP_CENTS` = 0.03 cents (below a pixel) or pinned at the same edge, reception within `RECEPTION_STEP` (0.02). `looksLike` allocates nothing; `TunerUiStateShownTest` fails if `Detected` gains a field it doesn't compare.
  - **Composition:** `TunerScreen` composes from `state.asShown()` through `derivedStateOf`, so it recomposes only when text changes. Exact cents and reception reach the meter and wave as `LiveFloat`s read only in layer and draw phases: a fun interface returning a plain `Float`, NaN for no note, so the reads on every frame box nothing (a `() -> Float?`, or even `() -> Float` through Kotlin's generic `Function0`, made a `Float` object each time; Phase 65). The wave reads the exact cents too, not the whole cents the text shows (before Phase 65, 0.6 and 1.4 cents drifted alike). The 12th-fret check's and the chord name's soft field behind their panels make their brush once per size and colour (`drawWithCache`).
  - **Needle** (the lens's marker since Phase 71): `Lens` follows the lambda with `snapshotFlow` into an `Animatable` spring (each new target `launch`ed so the spring keeps its speed). Moving parts sit in their own `graphicsLayer` and only change its transform, so a moving needle neither recomposes nor re-records drawing.
  - **Frame rate:** on Android 15+ a plain Compose animation gets the "normal" rate category (60 Hz on the S26), so the meter asks for 120 Hz with `Modifier.preferredFrameRate(120f)`, which only counts while it draws.

## Measured on the Galaxy S26
Phase 5. Minified `benchmarkRelease` build, portrait, CPU per thread from `/proc/<pid>/task/*/stat` (percent of one core).

| | Before (direct YIN, JIT only) | After (FFT YIN + Baseline Profile) |
|---|---|---|
| Silence: whole app | 7.8 % (main thread 2.3 %) | 5.6 % (main thread ≈ 0) |
| Note sounding: whole app | ≈ 45 % | ≈ 20 % |
| Note sounding: DSP thread | ≈ 34 % (≈ 7 ms/frame) | ≈ 9 % |

Main thread with identical synthetic input, before and after the recomposition work above: guitar mode 11.6 % → 5.1 %; chromatic 15.8 % at ~75 frames/s → 12.2 % at ~110 frames/s (≈ 2.1 → 1.1 ms per frame). Nothing is drawn in silence. Battery: ≈ 0.8 mAh per hour of listening for the app's CPU; the screen costs far more.

## Low-note window on the Xiaomi 12X
`scripts/dsp-phone-benchmark.sh` dexes `:core:dsp` and runs `DspPhoneBenchmark` with `dalvikvm` on the phone (ART with JIT, not a debuggable build; no app, no sound, ~20 s). 48 kHz, 2,000 warm-up and 1,000 timed frames of bass, guitar and noise test signals; CPU from `/proc/thread-self/schedstat`.

| Per frame (hop = 21.3 ms) | Standard, 4096 | Low notes, 8192 | Low notes, before the FFT change |
|---|---|---|---|
| Detector, wherever the scheduler puts it | 0.31 ms | 0.69 ms | 0.98 ms |
| Gate + detector + smoother | 0.33 ms (1.5 % of a core) | **0.74 ms (3.5 %)** | 1.03 ms |
| Gate + detector + smoother, little cores only (`TASKSET=0f`) | 2.2 ms (10 %) | **5.1 ms (24 %)** | |

So the low-note window costs about 2.3× the standard one and stays far inside the hop even on a little core. Guitar tunings keep the standard window and its cost.

## Watch CPU and the native detector
A C++ (NDK) YIN was planned (Phase 21) only if the Kotlin one proved too slow, for the low-note window, strum check or the watch. The watch had no measurement, so `DspPhoneBenchmark` also times the watch's chain as `WatchPitchPipeline` runs it (gate, sustain check, noise floor, detector, smoother, in-tune detector; standard range) at 16 kHz, where many watch mics record and frames are upsampled ×2 before YIN, and at 48 kHz. The Xiaomi 12X's little cores (`TASKSET=0f`: Cortex-A55, 1.8 GHz) stand in for a watch's CPU (Snapdragon W5: Cortex-A53, 1.7 GHz; Exynos W930/W1000: Cortex-A55, 1.4 GHz); the x86 emulator says nothing. Measured 2026-10-15, same method as above.

| Per frame (hop = 21.3 ms) | Big core, unpinned | Little cores (`TASKSET=0f`) |
|---|---|---|
| Watch chain, 16 kHz (1365-sample window, 341 hop) | 0.46 ms (2.2 %) | **2.7 ms (13 %)** |
| Watch chain, 48 kHz (4096 window, 1024 hop) | 0.33 ms (1.6 %) | 2.2 ms (10.5 %) |
| Phone: gate + detector + smoother, standard / low notes | 0.33 / 0.75 ms (1.5 / 3.5 %) | 2.3 / 5.2 ms (11 / 24 %) |
| Strum check, standard / low notes, every 0.1 s | 2.6 / 5.2 ms (≈ 3 / 5 %) | 16 / 32 ms (16 / 32 %) |
| Chord name, standard / low notes, every 0.1 s (2026-11-03) | 1.7 / 3.9 ms (≈ 2 / 4 %) | 12 ms (12 %) / – |

The ×2 upsampling makes 16 kHz a little dearer than 48 kHz. Allowing for a slower watch core (up to ≈ 1.5×) the watch tuner takes about 15–20 % of one of its cores, with a reading ready in a few ms of each 21 ms hop and nothing else heavy running (the screen is the watch's real battery cost). On the phone the tuner runs on a big core at under 4 %.

**Decision: no native detector.** Nothing comes near the budget: the dearest case, the low-note strum check pinned to a little core, still finishes in a third of its 0.1 s, and the phone's scheduler gives it a big core. A C++ YIN would at best halve these numbers while adding the NDK to the build, JNI, and a second detector to keep within ±1 cent. Look again only if a real watch drops readings or warms up, or a new feature runs YIN many times per frame; `scripts/dsp-phone-benchmark.sh` repeats these numbers in about a minute.

## Strums heard beside the tuner
2.0, Phase 74: `StrumWatcher` hears every chunk beside the tuner's `PitchChain` ([Strum check and metronome](strum-and-metronome.md), *The strum check's button*). Since the owner's guitar check (2026-11-03) only while the strum check's button is on, every sound read as a strum: then it costs what 1.1's strum check did, and nothing otherwise; the figures below are of the first step, which decided every sound by itself (those rules went on 2026-11-03). Before 2.0, 1.1 ran the strum check and the chord name only while their tool was on, and instead of the tuner (those tools and their analysis went in the phase's second step). **Budget** (set with this step): on a big core, no more on average than the tuner's own chain while single strings are tuned, no more than 1.1's strum check (≈ 3 % of a core) while a strum rings, and no hop over a quarter of the hop (5.3 ms), so a reading is never late. A cheaper schedule was not needed: a sound decided as one string is not read further, and only a frame that may be open strings pays for `StrumDetector` as well.

`scripts/dsp-phone-benchmark.sh` on the Xiaomi 12X, 2026-11-03, before (on `v2` as it was) and after. Before, the tuner ran its chain alone: **0.37 ms a hop** (`PitchChain 48 kHz STANDARD hop`, 1.7 % of a core), the strum detector 2.6 ms and a chord detection (new in the benchmark) 1.7 ms a frame, both unchanged after. After, the watcher's own cost per hop over 12 s of a quiet room with the sound named (PluckSynth strings, a 1024-sample hop, on top of the tuner's 0.37 ms):

| Per hop (21.3 ms) | Big core: mean / p95 / worst hop | Little cores (`TASKSET=0f`): mean / worst hop |
|---|---|---|
| Room only | 0.007 / 0.009 / 0.02 ms | 0.03 / 0.23 ms |
| A string every 2 s | **0.07** / 0.09 / 1.8 ms | 0.45 / 12 ms |
| An open strum every 3 s (read every 0.1 s while it rings) | **0.49** / 2.8 / 4.5 ms | 2.9 / 29 ms |
| A C chord every 3 s | 0.31 / 1.8 / 1.9 ms | 2.0 / 17 ms |

So tuning string by string adds a fifth of the tuner's own cost (0.37 → 0.44 ms a hop, 2 % of a core), and a ringing strum 0.49 ms (0.86 ms, 4 %), the strum check's 2.6 ms every 0.1 s as in 1.1. The dearest hop, a strum's first frames, which run `ChordDetector` and `StrumDetector` (4.5 ms with the tuner's 0.37), stays inside the budget on a big core. Pinned to the little cores that hop takes 29 ms, more than one hop: the recorder's buffer holds several hops, so a reading is a few ms late once per strum, and the scheduler gives the busy DSP thread a big core anyway. On the JVM (`StrumDetectorBenchmark`, after) a strum detection takes 2.3 ms (341 ms frame) and 4.5 ms (683 ms); the detectors themselves are unchanged but for `ChordDetector` keeping each note's salience and `StrumListener` copying the frame before a strum once per sound.

## Drone on the Xiaomi 12X
`scripts/dsp-phone-benchmark.sh` also times the drone (`DroneSynth`, [Notes, tunings and audio](notes-and-audio.md), *Drone*): one 10 ms chunk (480 samples at 48 kHz, what a player writes at a time) of each sound in its dearest case, root, fifth and octave an octave down (the pad then turns 870 phasors a sample), after the tanpura's six plucks are all ringing. Measured 2026-10-26.

| Per 10 ms chunk | Big core, unpinned | Little cores (`TASKSET=0f`) |
|---|---|---|
| Warm pad | 1.1 ms (11 %) | 3.3 ms (33 %) |
| Harmonium | 0.45 ms (4.5 %) | 1.4 ms (14 %) |
| Tanpura | 0.32 ms (3 %) | 1.0 ms (10 %) |
| Flute organ | 0.04 ms (0.4 %) | 0.1 ms (1 %) |

A crossfade (0.4 s) runs two drones, so twice that for a moment; the default (tanpura with its fifth, not lower) costs less. There was no budget yet for sound made in the app; this keeps the dearest drone, even crossfading on a little core, inside two thirds of real time, and the tuner's microphone isn't running meanwhile (Scales doesn't listen). `PartialBank` renders a block partial by partial, four at a time, rather than all partials a sample: the four rotations and levels stay in registers and only the block's 64 output samples are read and written. That made the pad 2.8× faster on the little cores than the first version (9.4 ms, where a crossfade could not have kept up) and 1.3× on the big one; folding the levels into the phasors (to save the ramp's multiply) gained nothing measurable and was dropped. On the JVM (`DroneSynthBenchmark`) every sound is under 1 ms a chunk.

## Baseline Profile
Lists the classes and methods used at startup and on every screen so Android compiles them ahead of time.
- `:baselineprofile` has `BaselineProfileGenerator`, `StartupBenchmark` and `MeterFramesBenchmark`. The generator's journeys (`TunerJourney.kt`, walking 2.0's screens since Phase 76), each from a cold start: **startup**; **tuner** (listening, Any note on and off through the picker sheet's switch, found as the sheet's lowest checkable item as `MeterFramesBenchmark` finds it, since Compose doesn't show it as an `android.widget.Switch`; then focus mode: on with its button, which turns the app on its side, the full-screen tuner a while, a tap for its controls and their button back to full screen, off with the exit button, and the phone held upright again with UI Automator's `setOrientationNatural`, the lock the run expects anyway; the strum check and the chord name run by themselves beside the tuner since Phase 74, and the 12th-fret check, opened from the picker sheet's last row, isn't walked); **Practice** (the Metronome tab: Start, the tempo ruler swiped both ways and tapped, faster, slower, stopped, tap tempo; then the Practice cards, each tool opened from its card: Chords, a chord and its next shape; Scales, a scale on the neck; the Capo helper; Ear training, its first question, then Intervals and Chord types, each question sounded again; Back to the cards and the Tune tab); **settings** (the gear, Settings scrolled to the end past Meter's moving cards, About opened and scrolled, Back twice). It never taps About's "Twangle on Google Play" row, which would leave the app. UI Automator finds controls by test tag (`NavigationTestTags`, `TunerTestTags`, `MetronomeTestTags`, `PracticeTestTags`, `EarTrainingTestTags`, the settings' `ABOUT_LINK_TAG`, exposed as resource ids with `testTagsAsResourceId`).
- Generate with the phone connected: `./gradlew :app:generateBaselineProfile -Pandroid.testInstrumentationRunnerArguments.class=io.github.klaboukes.twangle.baselineprofile.BaselineProfileGenerator` (~15 min on the Xiaomi 12X; without the class filter it also runs `MeterFramesBenchmark`, 4 more minutes). It installs a release-type build, so uninstall the debug build first and reinstall it after. It writes `app/src/release/generated/baselineProfiles/`, which is committed; `profileinstaller` installs it for sideloaded APKs. Three things to do first (learned 2026-11-02): **stand the phone upright and lock it there** (`settings put system accelerometer_rotation 0` and `user_rotation 0`, put back after), since the journeys expect an upright phone and on its side the Practice and Settings journeys fail; **delete `baselineprofile/build/intermediates/baselineprofiles/`**, since the plugin merges every run's files it finds there, so an old run's classes (Spirit level and Eclipse, that night) stay in the new profile; and expect Play Protect's "Send app for a security check?" after each journey's install, which stalls the run until **Don't send** is tapped (*Every device* in [devices.md](../devices.md)). Last regenerated 2026-11-03 on the Xiaomi 12X for 2.0 (Phase 76, on `v2`: the journeys above, Ear training and focus mode for the first time; 29,600 rules, 19,958 in the startup profile, against 1.1.0's 29,064 and 22,542, about one rule in seven new and none left of 1.1's removed screens, the style looks, the wave view, the mode switch or the tour; focus mode turned the phone on its side and back without trouble, and no Play Protect prompt came that run). The one before, 2026-11-02 for 1.1.0 (with Pointers and Loupe, the metronome's subdivisions and the Phase 63–65 screens), never opened Ear training; the one before that (2026-10-17, Phase 37) still had Spirit level and Eclipse, and the first (Phase 5) predated the metronome and the navigation bar. **Kept current for releases** (Phase 65): `scripts/release.sh bundle` refuses when the profile's last commit is older than the last change under `app/src/main`, `feature/*/src/main` or `core/designsystem/src/main` (`scripts/release.sh profile` checks it alone), so it is regenerated before a release, or the owner chooses `bundle --keep-old-profile` ([release.md](../release.md)).
- Startup: `./gradlew :baselineprofile:connectedBenchmarkReleaseAndroidTest`. On the S26 cold start was ~89 ms with or without the profile. On the Xiaomi 12X with 2.0's profile (2026-11-03, `-Pandroid.testInstrumentationRunnerArguments.class=…StartupBenchmark`, 10 cold starts each, median time to the first frame): 408 ms with the profile, 491 ms without any compilation, about a sixth faster. It stays because it is free and matters more on slower phones. Neither task runs in CI.

## Release build: shrinking and signing
- **Shrinking:** R8 (`isMinifyEnabled`) and resource shrinking; the APK went from 9.3 MB to 1.8 MB. The app uses no reflection; `app/proguard-rules.pro` only keeps the enums settings save by name (`TunerMode`, `InTunePrecision`, `ThemeMode`, `LensLook` (since Phase 67, in place of 1.1's `VisualStyle`, `TunerDisplay`, `WaveLook`, `MeterLook` and `InTuneEffect`), `Notation`, the metronome's `Meter` and `ClickSound`, `PracticeTool`, `PitchClass`, `ChordQuality`, `ScaleType`, `DroneSound` and `DroneVoicing`, and since Phase 65 the metronome's `Subdivision` and Ear training's `Exercise`, `NoteChoice`, `NoteMatch`, `Interval` and `IntervalDirection`, which had been missed) as a safety net; a new enum saved by name gets a rule too, and `SavedEnumRulesTest` (`:app`, JVM) fails until it has one: it reads `DataStoreSettingsRepository`'s `enumOrNull<…>` and `enumSetOrNull<…>` and the rules file. **Never rename saved enum constants.**
- **Signing:** the release builds of both apps (phone and watch, which share an app ID) use the owner's **upload key**, never in the repo; the root `build.gradle.kts` reads it once and both modules sign with it: `~/.twangle-keys/` (`twangle-upload.jks`, alias `upload`, with `keystore.properties` and a README), or the path in the Gradle property `twangle.keystoreProperties`. Without it (CI, other machines) the release builds are unsigned and nothing fails; CI builds them anyway (`assembleRelease bundleRelease`) so R8, resource shrinking or bundle breakage shows up the next morning. `.gitignore` excludes `*.jks`, `*.keystore` and `keystore.properties`. The Play Store will use Play App Signing, so a lost upload key can be reset.
- `./gradlew assembleRelease` (APK) or `bundleRelease` (AAB); check with `apksigner verify --print-certs`.
- **The "no internet" promise, checked by the build** (Phase 64): the README, the store text and Play's Data safety answer say Twangle has no internet permission, so a library update that brings `INTERNET` (or `ACCESS_NETWORK_STATE`, `AD_ID`) along must not ship unnoticed. The root `build.gradle.kts` gives each app module (`:app`, `:wear`) a `checkReleasePermissions` task that reads the merged release manifest (`SingleArtifact.MERGED_MANIFEST`, after `processReleaseMainManifest`) and fails, naming the permission and those three, on any `<uses-permission>` (or `-sdk-23`) outside `allowedPermissions`: `RECORD_AUDIO`, `VIBRATE` and AndroidX core's signature-level `<app ID>.DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION`, the same for both apps today. `test` and `check` depend on it, so every local run and the nightly CI see it. `checkReleaseBundlePermissions` checks the bundle itself (`SingleArtifact.BUNDLE`; the base manifest as `bundletool dump manifest` prints it, through AGP's own bundletool), and `scripts/release.sh bundle` runs it before tagging. A permission Twangle really needs goes on the list after the owner's yes; one a library brings unasked is removed with `tools:node="remove"` in the module's manifest (the merger's report, `build/outputs/logs/manifest-merger-release-report.txt`, names the library).
- **Uploads to Play** (Phase 41): `:app` applies Gradle Play Publisher (`com.github.triplet.play`, version in the catalog; 4.x is the line for AGP 9 and Gradle 9). It is build-time only, so the app gains nothing (no `INTERNET` permission). It signs in to the Google Play Developer API with the robot user's key, a service-account JSON key kept next to the upload key: `~/.twangle-keys/play-service-account.json`, or the path in the Gradle property `twangle.playServiceAccount`. Without it (CI, other machines) nothing changes: the play tasks exist but nothing runs them, and `scripts/release.sh upload` stops first, saying the key is missing. Only the `release` variant has play tasks (`publishReleaseBundle`, `publishReleaseListing`, `promoteReleaseArtifact` and so on; `play { enabled = false }` with `playConfigs { release { enabled = true } }`). `scripts/release.sh` drives them: `upload` runs `publishReleaseBundle` to the internal track; `listing` runs `publishReleaseListing --rerun` (every language's texts and pictures, and the app details); `promote closed|production`, `rollout <percent>` and `halt` run `promoteReleaseArtifact` on the same versionCode (`--version-code`, from `internal` to `alpha` or `production`, or `--update production` with `--user-fraction` and `--release-status inProgress|completed|halted`), so a promotion never builds or uploads again ([release.md](../release.md)).
  - **One place for the store texts:** the plugin wants its own layout under `src/<source set>/play/`; Twangle keeps the fastlane layout in `fastlane/metadata/android/` (`StoreListingTest`). `syncPlayResourcesFromFastlane` copies it at task time into `app/build/twangle-play/play/` in the plugin's layout (`title.txt`, `short-description.txt`, `full-description.txt`, `graphics/<type>/`, and `changelogs/<this versionCode>.txt` as `release-notes/<locale>/default.txt`), and `generateReleasePlayResources` is pointed at that copy. The sync also writes Play's app details at the top (`default-language.txt` en-US, `contact-email.txt`, `contact-website.txt`, from `playAppDetails`: Play replaces them together, so all three are always there) and rewrites the screenshots as 24-bit PNG (Play takes none with alpha; the store canvas is saved with an alpha channel). The icon exists only for en-US, the default language, which Play shows for the others; each language has its own feature graphic (Phase 65: it carries a translated line). Its properties (`resSrcDirs`, `resSrcTree`) are not public API, so they are set by name in an `onVariants` that runs after the plugin's own: a plugin update that renames them fails at configuration, not silently.
  - **Read-only looks** (`release.sh status`, `health [days]`, `reviews [language]`) are not Gradle tasks: `scripts/PlayReports.java`, a plain-JDK single source file run with Android Studio's `java` (no Gradle start, no plugin internals, nothing to install; the JDK has HTTP and RSA signing, and the file carries a small JSON reader). It signs in with the same service-account key (a JWT signed with its private key swapped for an access token, scopes `androidpublisher` and `playdeveloperreporting`). `status` opens an Android Publisher edit, reads `tracks` and `listings`, and deletes the edit, never commits it. `health` asks the Play Developer Reporting API (`v1beta1`, `crashRateMetricSet` and `anrRateMetricSet`) for `userPerceivedCrashRate` / `userPerceivedAnrRate` and `distinctUsers`, DAILY by `versionCode` (Pacific time, Play's only zone for daily data) over the last N days up to the metric set's `freshnessInfo`, weights each day by its users (as Play's 7-day figure) and compares with Play's bad-behaviour lines (1.09 %, 0.47 %); no rows is "no data yet", a switched-off API a plain hint. `reviews` is `reviews.list` with `translationLanguage` (text reviews of the last 7 days only). The app is untouched by all of it.
  - `release.sh upload` sends the bundle `release.sh bundle` made (`--artifact-dir release/Twangle-<version>.aab`, so nothing is rebuilt) to the internal track, as a draft by default. `bundle` builds the watch app's bundle too; it goes to Play only with `watch` (`upload watch`, `promote watch …`, `rollout watch`, `halt watch`), on its own Wear OS tracks (`wear:qa`, `wear:<closed test>`, `wear:production`), since Play takes no watch bundle on the phone's tracks ([docs/release.md](../release.md), *The watch app*; decision 3).
- **Version:** one place for both apps, `twangle.version` in `gradle.properties` (major.minor.patch, each 0–99, no suffix). The root `build.gradle.kts` makes it the `versionName` and `versionCode` = major × 10000 + minor × 100 + patch (1.1.0 is 10100); the watch's code adds 1,000,000 (1,010,100). Every build that leaves the PC needs a higher version. About shows `versionName`. Releases: [docs/release.md](../release.md) (`scripts/release.sh`, a `v<version>` tag on each).

  - **Passed down, never looked up:** `MainActivity` hands `AppContainer.toolSwitches` to `TunerScreen` and `MetronomeScreen` (a required parameter, so the app can't forget it), which give it to `TunerViewModel.tools` and `MetronomeViewModel.tools`. The bar (the Practice tab or none, `AppNavigationFrame(destinations)`, `destinationsFor`) and the Practice tab's tool button (`MainActivity.PracticeTab`, `practiceToolsFor` in `:feature:practice`) are decided by `:app` itself. A tool reads its switch where it adds a mode, tab or setting, so with the switch off it leaves no trace on screen.
  - **Tests:** `ToolSwitchesTest` (`:core:settings`) keeps `byName` complete; the JVM tests of each tool check it with its switch off too (`tunerToolsFor`, `practiceToolsFor`, the ViewModels with `ToolSwitches.ALL_OFF`). ViewModels default to `ToolSwitches.ALL_ON` in their JVM tests, and a feature UI test passes the switches it wants to the screen.
