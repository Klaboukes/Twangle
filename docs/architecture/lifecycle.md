## Microphone, permission and lifetime
- `RECORD_AUDIO` is requested at runtime from the tuner. `rememberMicPermissionState()` tracks a `MicPermissionStatus` (rules in the pure `MicPermissionRules`, in `:core:audio` so the watch follows them too), and `PermissionPrompt` shows one action per state:
  - `NOT_REQUESTED`: asked automatically once; the prompt explains why and offers "Allow microphone".
  - `DENIED` (rationale shown): ask again.
  - `PERMANENTLY_DENIED`: "Open settings" deep-links to the app's page, and the text gives the way to the microphone there: from Android 11 "choose to allow it while using the app" (its page offers that among other choices), before it "turn on Microphone" (a switch in the Permissions list).
  - `GRANTED`: the tuner.
- **Telling a dismissed dialog from a permanent denial:** Android only says `shouldShowRequestPermissionRationale`, which is false both before the first refusal and after a permanent one, and a dialog dismissed without an answer (a tap outside, Back) comes back denied without changing it. After a request the rules look at the rationale before and after it and at `AppSettings.micRefused` (saved in DataStore on each refusal): a rationale afterwards is `DENIED`; one that went away is a real "don't ask again" (Android 10 and older) or a second refusal (11 and newer), so `PERMANENTLY_DENIED`; no rationale either side after an earlier refusal means Android answered without showing the dialog (denied for good in an earlier session), also `PERMANENTLY_DENIED`; never refused means the dialog was only dismissed, so `NOT_REQUESTED` keeps "Allow microphone".
- Checked again on every `ON_RESUME`: a grant in Settings is picked up, and a permission lost while the app was open (taken back in Settings, a one-time grant that ran out) goes back to the prompt instead of the tuner's "Microphone access was turned off" error. The same check runs when the recorder reports `MIC_PERMISSION_MISSING`; if Android still says granted, that error stays, with Try again.
- Survives rotation (`rememberSaveable`); only `micRefused` is persisted.
- The microphone is open **only while the tuner screen is visible**: `SharingStarted.WhileSubscribed(5_000)` plus `collectAsStateWithLifecycle()`, so `AudioRecord` is released in the background and the privacy indicator turns off. The 5 s grace keeps the session through a rotation. `MicLifecycleTest` (`:app`, device) checks it against `AudioManager.activeRecordingConfigurations`.
- No foreground service: background capture is neither needed nor allowed.

- **Listen on the metronome** asks for the microphone only when Listen is tapped, by the same rules (`rememberListenPermission` in `:feature:metronome`, `MicPermissionRules`, the saved `micRefused`): allowed, it listens at once; otherwise Android's dialog, and listening starts if the player allows it. Nothing is asked when the screen opens. A refusal shows "Microphone is off" in the status line for 8 s, with "Open settings" once only Settings can allow it. The microphone is open only while it listens (at most 15 s): Stop, another control, leaving the screen (`ON_STOP`, another tab) or the ViewModel going all release it. It has its own `AudioRecorder` (`AppContainer.listenRecorder`), so it never waits on the tuner's, which keeps the microphone 5 s after the tuner leaves and reads on one thread. Audio stays in memory.
- **Ear training's Play it back** (Phase 55) asks as the tuner does (`rememberEarMicPermission` in `:feature:eartraining`, `MicPermissionRules`, the saved `micRefused`): once by itself the first time an exercise that listens is shown, checked again on every `ON_RESUME`; Intervals and Chord type never ask. Without it Play it back says "Microphone is off" with *Allow microphone* or, refused for good, *Open settings*. Its own recorder (`AppContainer.earTrainingRecorder`, `UNPROCESSED` with the `VOICE_RECOGNITION` fallback as every recorder) is open only while Play it back is shown and allowed: `WhileSubscribed(5_000)` plus `collectAsStateWithLifecycle()`, as the tuner ([Metronome, widget and watch](ui-other-screens.md), *Practice tab*, **Ear training**).
- **The metronome** plays only while its screen is shown (`StopWhenHidden` in `MetronomeScreen`: `ON_STOP` and leaving the composition both stop it), so going home, locking the phone or opening another screen stops the clicks. A configuration change (the phone turning, dark mode, the font size) recreates the activity, which stops it and disposes the composition too; while `Activity.isChangingConfigurations` neither stops the clicks, so they play on through it. `MetronomeRecreationTest` checks it. No foreground service. While it plays it keeps the screen on (`View.keepScreenOn`), so the screen timeout doesn't stop it; the volume keys set the media volume there, as on the tuner.

## Settings
Settings (`:feature:settings`) is one of the three tabs of the navigation bar ([UI basics](ui.md), *Navigation bar*), so it has no back arrow; About, opened from it, keeps one. `MainActivity` switches between tuner, metronome, settings, About and the tuning editor with one saved `Screen` value (no navigation library; `navigation/Navigation.kt`) and a `SaveableStateHolder`; Back returns About → settings → tuner, metronome and editor → tuner, and from the tuner leaves the app (`Screen.back`, JVM-tested). The editor's draft is dropped on leaving it (`removeState`), so each opening starts afresh. `SettingsViewModel` saves every change at once; there is no save button.

Four groups under headings (in the style's title face and `primary`, marked as headings for TalkBack), then Language, Show me around and About, each with an arrow (they open something). Groups are 32 dp apart; rows, including the card grids, keep 16 dp from the edges. No group holds more than two card grids.
- **Pitch and notes:** A4 calibration, note names, in-tune precision, left-handed. (The instrument and tuning are picked on the tuner itself, and in the Practice tools, with the instrument button.)
- **Look:** style, light or dark, wallpaper colours.
- **Tuner screen:** meter look, in-tune effect (with a one-line explanation), "Below the note" (numbers or wave; the saved value for numbers is `TunerDisplay.NEEDLE`), wave look, focus mode.
- **While tuning:** keep screen on, vibrate when in tune, tune up/down hint, signal bars.

What each does:
- **A4 calibration:** slider 415–466 Hz in 1 Hz stops, − and + buttons, "Reset to 440 Hz"; saved when the finger lifts. Every string joins a number and "Hz" with a no-break space (`\u00A0`), so "442 Hz" never breaks across lines (`HertzStringsTest` checks every language); the value beside the title is one line. The tuner itself shows no "A4 =" line (the screen stays calm; only Settings shows the reference).
- **Note names:** sharps, flats or Do Re Mi (`RadioGroupSetting`). A preset's own spelling wins in guitar mode ([Notes, tunings and audio](notes-and-audio.md), **Tuning spelling**).
- **In-tune precision:** Relaxed (≤ 5 cents, default) or Precise (≤ 2). `TunerInterpreter` swaps in `InTuneDetector.forPrecision` on the next frame; everything that follows `inTune` follows it.
- **Left-handed** (default off; Phase 57, option A of the rough mock-up `docs/design/phase57-preview.html`): a `SwitchSetting` at the end of "Pitch and notes", with Note names, the other setting that changes what the charts show ("Chord charts and the scale neck drawn for a guitar held the other way round"). It mirrors the Chords tool's chart and the Scales neck ([Other screens](ui-other-screens.md), *Practice tab*); nothing else: the tuner's string row is a list from low to high, not a picture of the guitar, so it keeps its order (left to right, in Arabic too), and the Capo helper is a table that draws no shapes. TalkBack's words don't change.
- **Style:** `StylePicker` (`:feature:settings`), a `LookCardGrid` like the meter and wave looks: six mood cards in the owner's order, three to a row (two from 1.3× font, except on a large window: *Landscape and wide screens* in [UI basics](ui.md)), the style's name under each ([Meter, wave and styles](ui-meter-and-styles.md), *Visual styles*). It is the only place to pick a style.
- **Light or dark:** system, light or dark, plus "Wallpaper colours" (dynamic color, Android 12+, Contemporary only; on by default on a fresh install, owner's decision 2026-10-15; an accent near the in-tune green falls back to Contemporary's blue, see [Meter and styles](ui-meter-and-styles.md)). `MainActivity` reads settings before drawing, so the theme never flashes, and calls `enableEdgeToEdge` again on a change so status-bar icons follow the app. With gesture navigation the navigation bar gets no scrim (`isNavigationBarContrastEnforced = false`, Android 10+), so the style's background runs to the bottom edge under the handle: MIUI otherwise lays a white or dark strip there. Navigation buttons keep the system's scrim, so they stay readable. Which one shows comes from the secure setting `navigation_mode` (2 is gestures), read again whenever the insets change; without it, from the tappable-element insets (0 with gestures; MIUI counts its gesture bar as tappable, so they can't decide there) (`SystemBars.kt`, JVM-tested; checked on the Xiaomi 12X with gestures and with buttons, light and dark).
- **Keep screen on** (default on): `View.keepScreenOn` while the tuner is shown with the mic granted and hears playing; a window flag, not a wake lock. A quiet timer (`ScreenAwakeRule`, JVM-tested; owner, 2026-10-20) lets go after 3 minutes without playing, so a phone forgotten on a music stand goes dark: a note counts once it has sounded 1 s (a quiet room's sounds came and went as notes of about 0.2 s every few seconds on the Xiaomi 12X, which kept the screen on for good), then holds the screen on however long it sounds (the quiet time starts when it stops), a tool's new state (strum check, 12th-fret check, chord name) counts as playing, and so does any touch on the tuner (seen before the controls, never taken from them) and the tuner coming back to the screen. For the last 10 s a calm warning shows at the bottom, "Screen turns off soon" and "Tap to keep it on" over a thin bar that empties (`ScreenOffWarning`; TalkBack reads it as it shows; a step a second with animations off); a tap anywhere starts the 3 minutes afresh. Then the phone's own screen timeout has the screen, and once it is off the activity stops and the microphone closes as usual. No notification (it would need its own permission and stay in the shade) and no setting of its own. The metronome keeps the screen on while it plays, without a timer: playing is the player's own choice.
- **Vibrate when in tune** (default on): `InTuneHaptic` clicks once (`EFFECT_CLICK`, 20 ms one-shot before Android 10) when `inTune` turns true. It uses `Vibrator` directly because Compose/View haptics obey the phone-wide touch-feedback setting, which many people switch off; this needs the normal `VIBRATE` permission. `InTuneTickRule` skips a second tick for the same note within 1.5 s; the state is saved, so rotating doesn't tick.
- **Show tune up/down hint** (default on): `NoteDisplay` shows `Detected.hint` ("Tune up ↑" / "Tune down ↓") in `primary`. In the wave view it fills the empty pill; with the needle it gets its own line that keeps its height while empty, so nothing jumps. TalkBack adds it in words. The switch controls both.
- **Show signal bars** (default off): [Signal pipeline](signal-pipeline.md), *Signal bars*.
- **Language** (`LanguageSetting`, the first row under the groups): the app's language, "Phone's language" or one in its own name. A tap opens a dialog listing "Phone's language" (follows the phone) and then every language of `twangle.languages` in its own words, in alphabetical order of those names (Latin letters first, then Cyrillic, Arabic, Devanagari, Hangul and Han). Picking one sets it through AppCompat and the screen is recreated in it, still on Settings. The list takes at most 60 % of the window's height, so the dialog keeps clear of the screen's edges; it scrolls, opens at the picked language, and a thin line at its top or bottom shows there is more that way. Indonesian is "Bahasa Indonesia" (the locale data says only "Indonesia"). Details in [Languages](languages.md).
- **Show me around** (a `LinkSetting` row above About, "A short tour of the tuner"): opens the tuner and starts the first-start tour again ([Tuner screen and tour](ui-tuner.md), *Tour*).
- **About** (its own page, `AboutScreen`, opened from a `LinkSetting` row showing the version; Settings and About share `SettingsPage`): name and version (`BuildConfig.VERSION_NAME` passed from `MainActivity`), the free-forever promise, a short privacy statement (settings stay on this device, and in Android's own backup if it is on; keep it in step with PRIVACY.md), a **Help & website** row (a `LinkSetting`, "How each tool works, and answers to common questions"; Phase 54), a quiet **Rate Twangle** row (a `LinkSetting`, "Twangle on Google Play"; Phase 37), and a credit for every bundled font and library. Each credit opens an `AlertDialog` with the full licence, read from assets on `Dispatchers.IO` and reflowed (`reflowLicence`). With no internet permission every licence ships in the APK: OFL texts in `:core:designsystem` `assets/licenses` (`bundledFontCredits`, kept in step with `res/font` by a JVM test) and Apache 2.0 and Protocol Buffers' BSD 3-Clause text in `:feature:settings` `assets/licenses`. Besides AndroidX and Kotlin, the credits name the libraries that come in with them: Okio and a copy of Protocol Buffers (DataStore), kotlinx.serialization, JSpecify and Guava's ListenableFuture (AndroidX), and Google's Material Symbols for the icons; check `:app:dependencies --configuration releaseRuntimeClasspath` when a dependency is added. A new library needs its own credit, and its own licence file if it is under another licence. Licence texts are what users read, so they hold no build details (script names, source paths; `FontCreditsTest` checks the font ones). *Rate Twangle* (`openPlayPage`, passed in by `MainActivity` with the app ID) opens Twangle's Play page in the Play Store app (`market://details?id=…`, aimed at `com.android.vending` so another maker's store, such as Xiaomi's, doesn't take it), else `https://play.google.com/store/apps/details?id=…` in the browser, else nothing. It is only a link: no rating pop-up (no in-app review API, no Play library), never asked for unprompted, and no internet permission is needed, since the other app does the opening. *Help & website* (`openWebsite`, passed in by `MainActivity`) opens [the website](website.md) in the phone's browser: `AboutSection` picks the home page in the app's language from `LocalConfiguration` (`websiteLink`: `https://klaboukes.github.io/nl/` in Dutch, the English home page in every language the site doesn't have yet, which the row's summary says in those languages), and `websiteIntent` is a plain `ACTION_VIEW` of that address in the `BROWSABLE` category, aimed at no app in particular. Like *Rate Twangle* it is only a link: the browser loads the page, so the merged manifest still has no `INTERNET` permission (checked after the build, Phase 54). `SettingsContentTest` checks the row and the link it asks for in English, Dutch and German, `WebsiteIntentTest` the intent, `WebsiteTest` the language choice; the settings row that opens About says "help" too. The links need no `<queries>` entry: the opener just tries each and catches `ActivityNotFoundException`.

## Saved settings
`SettingsRepository` (`:core:settings`) exposes `settings: Flow<AppSettings>` plus one suspend setter per value. `DataStoreSettingsRepository` stores them in `files/datastore/settings.preferences_pb`; `AppContainer` creates the only instance (DataStore allows one per file). Tunings are saved by `id` and enums by `name`, so **those must never be renamed**. `FakeSettingsRepository` (`testFixtures`) keeps settings in memory for tests.

- **Forgiving reads:** a missing, unknown or out-of-range value gives its default; an unreadable file gives all defaults, and a corrupt one is replaced so saving works again. A read that fails (an I/O error) shows the defaults only if nothing was shown yet and is tried again after 0.5 s, doubling up to 30 s (`readRetryMillis`), so one failed read doesn't keep the defaults, or miss later changes, for the rest of the session. Instrument and tuning are read as a pair: no saved instrument (versions before the picker) or an unknown one gives the saved tuning's own instrument, else the guitar; a tuning that isn't one of the instrument's presets, or an unknown one, gives the instrument's standard tuning. A saved lowering out of range is cut to what the tuning can go (none below 0).
- **Migrations** (in `DataStoreSettingsRepository`, not as enum constants, so no code can pick the old names again; JVM tests cover each case): while no `tuner_display` is saved, the old switch `show_waves` gives `WAVE` (on) or `NEEDLE` (off), and saving a display removes it. A saved display `"STROBE"` reads as `WAVE` with look `STROBE`, rewritten by the first `setDisplay` or `setWaveLook`. A saved look `"STRIPES"` reads as `STROBE`. A saved style `"PREHISTORIC"` or `"MIDDLE_AGES"` (the seven styles before October 2026) reads as `ANCIENT`, rewritten by the next `setStyle`; any other unknown style gives the default.

## Custom tunings
A `CustomTuning(id, name, instrument, notes)` (`:core:settings`) is a tuning the player made; its `tuning` is a plain `Tuning` with the same id and no spelling of its own (the sharps/flats setting writes it), so the tuner, string row and pitch range treat it like a preset. `AppSettings.customTunings` holds them all in the order they were made; `customTuningsFor(instrument)` gives one instrument's (for the picker, below its presets) and `pickedCustomTuning` the picked one, or null for a preset.
- **Ids** are `custom_` plus a random UUID, made once by `addCustomTuning` and never changed, so editing keeps the tuning picked. No preset id starts with `custom_` (JVM-tested).
- **Names** are normalized on every save and read (`CustomTuning.normalizeName`: trimmed, runs of white space made one space, at most 40 characters) and may not come out empty. Duplicate names are the editor's to refuse; compare normalized names.
- **Notes** are one per string of the instrument (MIDI 0–127). The instrument is fixed when the tuning is made.
- **Repository:** `addCustomTuning(name, instrument, notes)` saves it after the others and returns it, not picked (pick it with `setTuning(it.tuning)`); `updateCustomTuning(id, name, notes)` keeps its id, instrument and place, and a picked one stays picked with the new notes (that is a tuning change, so a locked string is released); `deleteCustomTuning(id)` removes it and, if it was picked, picks its instrument's standard tuning. A picked one that was lowered starts not lowered after an edit (its new notes are the ones to tune to) or a delete. Bad input (empty name, wrong number of notes) throws `IllegalArgumentException` and saves nothing. `FakeSettingsRepository` does the same, with ids `custom_1`, `custom_2`, ….
- **Editor** (`:feature:tuner`, `editor/TuningEditorScreen.kt`, its own `Screen` in `MainActivity`, so the tuner rests and lets go of the microphone meanwhile; on the quiet background like the settings). Opened from the panel's last row, "New tuning", for the instrument shown; it also opens for an existing `CustomTuning` (`editingId`, instrument fixed) from Edit in that tuning's menu in the panel. Material form: a close button (leaves without saving) and Save along the top, the title ("New tuning" / "Edit tuning", a heading that wraps at large fonts) and "Instrument: Guitar", the name field, then the heading "Strings" and a row per string, thickest first: "E₂ string" (its standard note), then − note +. A new tuning starts from the instrument's standard notes.
  - **Notes** move a semitone per tap and stay within **B0–E6** (MIDI 23–88, `EDITOR_NOTE_RANGE`): B0 is the lowest preset string and still reads a semitone flat at A4 = 440 Hz (and in tune at 415) in the low-note window, which a tuning this low switches on by itself; E6 still reads a semitone sharp at A4 = 466 Hz (1479 Hz, under the detector's 1500). At an end the button is turned off. Notes are written in the notation setting (a custom tuning has no spelling of its own); the caption keeps the standard tuning's.
  - **Name checks** run only when Save is tapped: empty ("Give the tuning a name") or already one of the instrument's tunings ("There is already a tuning with this name": its presets' names as shown and its other custom tunings', compared as `normalizeName` gives them and ignoring case; another instrument's names are free). The message goes as soon as the name changes and comes back only on the next Save, so nothing flashes while typing. Typing stops at 40 characters.
  - **Save** (`saveDraft`, JVM-tested) adds the tuning or updates it and **picks it** in one DataStore write (`addCustomTuning` / `updateCustomTuning` with `pick = true`), and returns to the tuner, whose button names it ("Guitar · Drop D loose"; `TunerViewModel.customTunings`, passed in from the saved settings at the start so the id never shows). The save runs in `TuningEditorSaver`, a small ViewModel, so turning the phone mid-save neither cuts it off nor loses that it is done: the new screen sees `SavePhase.SAVED` and closes. Save does nothing while a save runs.
  - **Discard changes?** The close button, Back and a tap on the home-screen widget leave at once when nothing was edited, else they ask "Discard changes?" (Discard, in the error colour, or Keep editing; Back or a tap outside keeps editing). An edit is another note or a name that would be saved differently (`TuningDraft.hasChangesFrom`: spaces alone don't count, a note moved and moved back doesn't either). The editor handles Back and the widget's request itself (`closeRequest`), so `MainActivity` registers no Back handler while it shows. Its title uses the delete question's size (`DIALOG_TITLE_SCALE`).
  - The draft (`TuningDraft`, pure and JVM-tested) survives rotation, and so does the open question. TalkBack: the note says "E 2 string, D 2" (a polite live region, so it is said again after a tap; the caption is hidden), the buttons "E 2 string, a semitone lower / higher", the message is a live region. `TuningEditorTest` checks it all, Dutch ("e 2-snaar, dis 2"), and every control and text wholly shown at 2× text with eight strings in Dutch (every style in a thorough run).
- **Stored** in one string (`CustomTuningCodec`): a line per tuning, `id|instrument id|midi,midi,…|URL-encoded name`; fields added later go after the name and older readers ignore them. A line that can't be read (unknown instrument, wrong note count, bad number or note, no name, repeated id) is skipped and the rest kept; the next save writes only the good ones. A picked custom tuning that is gone, damaged or of another instrument gives the instrument's standard tuning, so damaged data always falls back to the presets.
