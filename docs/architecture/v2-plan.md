# The 2.0 plan

The plan for Twangle 2.0 ([ROADMAP](../../ROADMAP.md), *2.0 — the app designed again*), written in Phase 66 against the code of `v2` as it was branched from `main` on 2026-11-02 (1.1.0). It is the contract for Phases 67 to 76: what each module keeps, changes or loses and in which phase, what the tuner's lens is and what a look inside it may do, how 2.0 reads the settings a 1.1 install saved, where the 12th-fret check and the pitch trail tool go, the phases' order and size, and which tests go, change or stay. It lives on the `v2` branch only, with the code it describes. A phase that finds the plan wrong changes it here in the same pull request; when 2.0 lands on `main` (Phase 76) the finished parts move into the topic files they belong to and this file goes to [history](history.md).

The design itself is settled in the roadmap and in the two mock-ups' top comments ([v2-tuner-screens-preview.html](../design/v2-tuner-screens-preview.html), [v2-one-look-preview.html](../design/v2-one-look-preview.html)); the first mock-up of the other screens is [fresh-start-preview.html](../design/fresh-start-preview.html). Paths below are under `<module>/src/main/kotlin/io/github/klaboukes/twangle/<module path>/`.

## Modules: kept, changed, gone
"Kept" means the file stays as it is apart from what Phase 67 does to every file (the style branches collapse to Ink). "Changed" names the phase and what changes. "Gone" names the phase that deletes it, with its tests and its texts in every language.

**Untouched: `:core:dsp`, `:core:audio`, `:core:testing`, `:baselineprofile`'s generator.** No DSP, audio or test-helper file changes for the look, the navigation or the screens, but for one removal: `allIfThorough` (`:core:testing`), which only the style loops used, went with them in 67. Two exceptions are planned, both additions: Phase 74 runs `StrumDetector` and `ChordDetector` beside the pitch detector (a `PitchPipeline` change in `:feature:tuner`, with any detector change tested in `core/dsp/src/test` under hard rules 2 and 6; done in its first step: `StrumWatcher` (new, `core/dsp/strum/`) decides each sudden sound and reads it, `StrumListener` keeps the frame before a strum, `ChordResult` each note's salience and `ChordDetector` says which intervals lie on a harmonic, all allocation-free and tested by `StrumWatcherTest`), and `WaveMotion` / `StrobeMotion` (`core/dsp/strobe/`) and `PitchHistory` (`core/dsp/trail/`) are reused as they are by the lens. `MeterFramesBenchmark` and `TunerJourney` in `:baselineprofile` follow the new screens in Phase 76 (one benchmark per lens look instead of per meter look); since 67 `MeterFramesBenchmark` (and `scripts/meter-frames.sh`) measures `CLASSIC` and `PITCH_TRAIL`, with no settings step, and since 72 the lens's three looks, `TRAIL`, `LIGHT_ARC` and `STROBE`, each from a fresh start with the look in the launch (`MainActivity` takes `--es lensLook` in debug and the frame-time build only), `TunerJourney` finds the picker sheet's Any note row the way `MeterFramesBenchmark` does since 72 (its lowest checkable item; the profile itself is regenerated in 76), and `scripts/meter-look-screens.sh` went at the end of 67 (Phase 72 may give the lens's looks pictures of their own). Done in 76 (2026-11-03): the journeys walk 2.0's screens (the picker sheet's Any note, focus mode on and off, the Metronome tab's ruler and Start, the four Practice cards with Ear training, the gear to Settings and About, the Tune tab), `MeterFramesBenchmark` unchanged, and the profile regenerated on the Xiaomi ([performance.md](performance.md), *Baseline Profile*).

**`:core:settings`: the code changes, the storage does not.** The same two files (`settings.preferences_pb`, `this_device.preferences_pb`), the same key names and the same value spellings for everything kept; no `DataMigration` is added, and the first start writes nothing but the removal of `focus_mode`. What changes is the Kotlin: `AppSettings` loses the fields of the looks that go, two enums shrink, one enum is added, and the reader maps a few 1.1 values (the table in *Settings from 1.1*). That is a code change, not a storage change: a 1.1 file, or a 1.1 backup restored onto 2.0, is read as it lies, and keys 2.0 no longer reads stay in the file unread, as `string_lock_tip_seen` and `wave_breathes_in_tune` do today.
