# Website

Twangle's small public site (Phase 54): what Twangle is, how each tool works, and help for common problems, so a review or an email can be answered with a link. It makes the app's promise too: free (GitHub Pages, no server), no tracking, no cookies, no forms, no JavaScript, and **nothing loaded from another site**.

## Where it lives
- **Address:** https://klaboukes.github.io/ (Dutch at `/nl/`), GitHub Pages of the public repo `Klaboukes/klaboukes.github.io`, served from its `main` branch. That repo holds only the built pages; nobody edits it by hand.
- **Source:** `website/` in this repo, so a change to a tool updates its page in the same pull request (CLAUDE.md, *Conventions*).
- **Privacy policy:** stays where Play and the app link to it, https://klaboukes.github.io/twangle-privacy/ (Dutch `nl.html`), in its own repo `Klaboukes/twangle-privacy` (`scripts/publish-privacy.sh`, ARCHITECTURE.md §9). GitHub serves a project repo's pages under the user site's address, so the site links to it as `twangle-privacy/`, and the site itself must never have a `twangle-privacy` folder (the publish script refuses one). Its page frame is ours too (`website/privacy-layout.html`, copied there as `_layouts/default.html`): the GitHub Pages theme's own frame loaded a script from cdnjs.cloudflare.com, so the policy's page now keeps the site's promise as well. The policy has a section on the website itself (no cookies, no tracking, no scripts, nothing from another site; GitHub, the host, sees visitors' addresses as any web host does).
- **Linked from everywhere** (Phase 54): the app's About page has a *Help and website* row that opens the home page in the phone's browser, the Dutch one when the app is in Dutch ([Lifecycle and settings](lifecycle.md), *About*; the app keeps no `INTERNET` permission); the Play listing's website (`contact-website.txt` in `playAppDetails`, `app/build.gradle.kts`, sent with `scripts/release.sh listing`) is the home page, while the privacy-policy address in Play's *App content* stays the policy's own; README.md links it. A move to a domain of Twangle's own changes these four places too (Phase 56): About's row (`Website.kt` in `:feature:settings`), the listing's `contact-website.txt`, README.md and the privacy policy (PRIVACY.md and PRIVACY.nl.md, then `scripts/publish-privacy.sh`).
- Pages link to each other only with relative links, so moving to a domain of Twangle's own later (Phase 56) is a setting on the repo, not an edit.

## Pages and the frame
- `website/pages/<language>/<page>.html` is the inside of one page's `<main>`, plain HTML, with a header comment: `title`, `description` (the search snippet) and `nav` (which top-bar link to mark as the current one). `{play}` stands for the Play link, `{root}` for the way back to the site's root (`""` or `../`) and `{coffee}` for the owner's Buy Me a Coffee page (*Buy me a coffee* below).
- `website/build.py` (Python standard library only, `python -I website/build.py [output]`, default `website/build/`, git-ignored) wraps each page in the shared frame: head, top bar (Twangle, Tools, Help, Privacy, the other language), footer (*Made by one person. Free forever.* and, once the owner has a page, the *Buy me a coffee* link, then Help, Privacy, the other language, the contact email, Google's trademark line for the badge). The frame's own words are in `WORDS` in that file, per language. A link to a page that doesn't exist yet stays out of the frame (Help appears once `help.html` does), and a tool card on the home page (`<div data-page="tuner.html">`) stays a plain box until its page is written, then becomes a link with an arrow.
- `website/static/` is copied beside the pages: `site.css`, `img/` (the app icon, Google's badges), `shots/<language>/`. The output is plain HTML with a `.nojekyll` file, so GitHub serves it as it is.
- **Look:** from the mock-up the owner kept (`docs/design/website-preview.html`, 2026-10-27): Contemporary's colours, light or dark as the visitor's device is set, the device's own font (no web fonts), one column at phone width with no sideways scroll, words and the phone side by side on wider screens. The home page: headline, Google's *Get it on Google Play* badge, the four promises, the instruments (with a link to their page), a line on the way round the app (2.0, Phase 69: the three tabs Tune · Metronome · Practice, Practice's four cards with the one used last, Settings behind the gear at the top left), the tools in three groups (tuning, listening, practice) and a fourth, *Instruments and more* (instruments and tunings, left-handed, the widget), a few screenshots, the badge again.
- **Tool pages** (the mock-up's tuner page is the model), one per home-page card, in the cards' order: `tuner.html`, `strum-check.html`, `12th-fret-check.html`, `chord-name.html`, `pitch-trail.html`, `metronome.html`, `chords.html`, `scales.html` (the drone too), `capo.html`, `ear-training.html` (its three exercises, what is asked, no scores kept, the microphone only for Play it back), `instruments.html` (the instruments and tunings, lowering, own tunings, the 12-string's courses, the banjo's short string, which tools work where), `left-handed.html` and `widget.html`. Each has a crumb (Tools · Tuning, Listening or Practice), a lead, steps, short sections, a fold-out *For the curious* part (`details.curious`) where it helps, and links to the tools before and after it in the home page's order (`.nextprev`; the first and the last, the tuner and the widget, lead back to the tools). With a screenshot it sits beside the words (`.tool`); without one the page is one column (`.tool.solo`); a screenshot on its side goes across the column (`img.wide`). Pages say where to find a tool and walk through it, using the app's own words in italics. A tool still off in release builds (its `ToolSwitches` switch, [Threading and performance](performance.md), *Release build*) isn't walked through yet, as players can't find it: its page, or its tool's page, says in a short *Coming soon* section what it will do, and the steps come when it goes live, as Ear training's page did and the speed trainer's section on `metronome.html` did (Phase 62, 2026-10-31).
- **Help** (`help.html`, the mock-up's help page is the model; not in the tools' `.nextprev` chain, it is reached from the top bar and the footer): short answers as questions that fold open (`<details>`), grouped by topic (the microphone, tuning, the metronome, the app), the contact email at the end (`.ask`). Each answer's first paragraph has an id in English in both languages (`help.html#octave`, `nl/help.html#octave`), so a review or an email can be answered with a link that opens that answer (a browser opens a closed `<details>` to show the target inside it; `scroll-margin-top` keeps its question in view). The answers come from the app's code and strings, not from what a tuner usually does: the permission prompt's steps, the octave rule of Auto mode and the low-note window, the metronome stopping when its screen goes, the 3-minute screen rule, clearing storage to reset. New answers come from the weekly reviews (Phase 56) and the testers, in English and Dutch.
- **Facts stay true to the app:** names of instruments and tools as the app's `strings.xml` has them (in Dutch too), numbers from the code (e.g. the metronome's 30 to 250 BPM, `ClickTrack`). Pages explain ideas and walk through each tool rather than every button, so they stay true as the app changes.

## Nothing from another site
`website/build.py` checks the built output and fails, naming each problem, when:
- a page or stylesheet would load something from another host: any `src`, `srcset`, `poster`, `data` or `background` attribute, any `<link href>` (stylesheets, icons, fonts), a CSS `url()` or `@import`, in `site.css`, a `<style>` or a `style=""`, pointing at a URL with a scheme (`https:`, `http:`) or at `//host`; `data:` stays on the page and is allowed;
- a page has a `<script>` (the site works without JavaScript);
- a link inside the site leads to a page or file that isn't there, or to an `#id` the page doesn't have (`twangle-privacy/` is the one known exception, served by its own repo);
- a page exists in one language and not in another.

Plain `<a href>` links to other sites (Google Play, the email address) are allowed: they only open when the visitor taps them. Google's badge is a local copy for the same reason. To see the check work, add `<link rel="stylesheet" href="https://example.com/a.css">` to a page and build: it fails.

## Buy me a coffee
The owner asked for a *Buy me a coffee* link (2026-10-28): the app stays free with nothing to buy in it (hard rule 9), and the website is where a player who wants to can give something. `COFFEE_URL` in `website/build.py` is the page's address, empty for now (below). While it is empty nothing shows, as Help stays out until its page exists. Once it is set, the link is in the footer of every page, right after *Made by one person. Free forever.* (`coffee` in `WORDS`: *Buy me a coffee*, *Trakteer me op een koffie*), and the home page ends with a short box (`<p class="support" data-coffee>`, with `{coffee}` for the address) that `build.py` leaves out until then. It is a plain text link, so the site keeps its promise: Buy Me a Coffee's own button and widget are an image and a script from its servers, and the check above would refuse them. The app itself doesn't link the page: About's *Help and website* row opens the site, and that is enough. The first page was https://buymeacoffee.com/klaboukes, but Buy Me a Coffee pays out through Stripe, which requires a KvK number from every Dutch creator (2026-10-28). The owner chose Ko-fi, paid out to a personal PayPal account, and the link stays off the site until that page exists, after launch (ROADMAP.md, Phase 56): the mechanism stays, only `COFFEE_URL` and this paragraph change.

## Languages
English at the root, Dutch in `nl/` (`LANGUAGES` in `build.py`); every page exists in both, with the same file name, and the language link goes to the same page in the other language. On a phone the language link is in the footer only, to keep the top bar on one line. The other 14 app languages come after launch (Phase 56): add the folder to `LANGUAGES`, its frame words to `WORDS`, a Play badge in that language, its screenshots, and translate each page. Dutch is natural and short, in the app's own words (*Strumcheck*, *Toonlijn*, *Bourdon*).

## Publishing
On the `v2` branch the pages describe 2.0 (from Phase 69: its navigation) and are not published: they go live when 2.0 lands on `main` (Phase 76), while the site keeps showing 1.1 from `main`. `scripts/publish-website.sh`, after a change to `website/` has landed on `main`: it builds and checks the site (a failed check stops it), clones `Klaboukes/klaboukes.github.io`, replaces its contents with the build (so a removed page goes too), and commits and pushes only when something changed, with GitHub's no-reply address (`816876+Klaboukes@users.noreply.github.com`, never a personal one: the repo is public). GitHub Pages shows the change within a few minutes. The repo was made public with GitHub Pages on its `main` branch (2026-10-27).

To look at the pages before publishing: `python -I website/build.py`, then `python -I -m http.server 8754 --bind 127.0.0.1` in `website/build/`, and open http://127.0.0.1:8754/ at phone and desktop width.
