## Microphone, permission and lifetime
- `RECORD_AUDIO` is requested at runtime from the tuner. `rememberMicPermissionState()` tracks a `MicPermissionStatus` (rules in the pure `MicPermissionRules`, in `:core:audio` so the watch follows them too), and `PermissionPrompt` shows one action per state:
  - `NOT_REQUESTED`: asked automatically once; the prompt explains why and offers "Allow microphone".
  - `DENIED` (rationale shown): ask again.
  - `PERMANENTLY_DENIED`: "Open settings" deep-links to the app's page, and the text gives the way to the microphone there: from Android 11 "choose to allow it while using the app" (its page offers that among other choices), before it "turn on Microphone" (a switch in the Permissions list).
  - `GRANTED`: the tuner.
- **Telling a dismissed dialog from a permanent denial:** Android only says `shouldShowRequestPermissionRationale`, which is false both before the first refusal and after a permanent one, and a dialog dismissed without an answer (a tap outside, Back) comes back denied without changing it. After a request the rules look at the rationale before and after it and at `AppSettings.micRefused` (saved in DataStore on each refusal): a rationale afterwards is `DENIED`; one that went away is a real "don't ask again" (Android 10 and older) or a second refusal (11 and newer), so `PERMANENTLY_DENIED`; no rationale either side after an earlier refusal means Android answered without showing the dialog (denied for good in an earlier session), also `PERMANENTLY_DENIED`; never refused means the dialog was only dismissed, so `NOT_REQUESTED` keeps "Allow microphone".
- Checked again on every `ON_RESUME`: a grant in Settings is picked up, and a permission lost while the app was open (taken back in Settings, a one-time grant that ran out) goes back to the prompt instead of the tuner's "Microphone access was turned off" error. The same check runs when the recorder reports `MIC_PERMISSION_MISSING`; if Android still says granted, that error stays, with Try again.
- Survives rotation (`rememberSaveable`); only `micRefused` is persisted.
- The microphone is open **only while the tuner screen is visible**: `SharingStarted.WhileSubscribed(5_000)` plus `collectAsStateWithLifecycle()`, so `AudioRecord` is released in the background and the privacy indicator turns off. The 5 s grace keeps the session through a rotation. Android silences a recording the moment its app leaves the screen, which reads as busy: Home and back within those 5 s would greet the player with "Microphone is busy", so the tuner and the pitch trail listen again by themselves once their screen is back in front after a failure (`listenAgainOnReturn`; Phase 89, as the watch's `WatchTunerViewModel.shown()`). From Android 10 Android also silences it while something else is in front without stopping the app: the assistant laid over it (on the Xiaomi 12X, Gemini's overlay is an activity of its own that pauses Twangle and takes the microphone the moment it listens) or the other app of a split screen, once picked, if it records (both apps of a split screen stay resumed there, so only the window's focus tells them apart). So *in front* is resumed with the window focused (`ReportShown`: the lifecycle's `RESUMED` and `LocalWindowInfo.isWindowFocused`; Phase 91; until then only `ON_START` / `ON_STOP`, and an assistant opened and closed left "Microphone is busy" until Try again), and `ScreenFront` counts the returns to the front, so one that follows the leaving at once is never missed. Only a return after the failure starts the new try: nothing is tried while the screen is behind something, a failure while it stays in front waits for Try again (or the next return, a dialog of the app's own closing too), and the microphone is held no longer than before. `ReportShownTest` (device) checks the pause, the stop and a window taking the focus; `ReportShown`'s `ON_START` / `ON_STOP` still tell the vibration guide whether the tuner shows. `MicLifecycleTest` (`:app`, device) checks it against `AudioManager.activeRecordingConfigurations`. The tuner's state keeps no note once the microphone is let go of (Phase 91): `shownWhileWatched` shares it as `stateIn(WhileSubscribed(5_000))` does, but when the sharing stops a last note heard becomes listening (`atRest`), so a screen back after the 5 s no longer shows the old note for a frame before the new listening's first state.
- No foreground service: background capture is neither needed nor allowed.

- **Listen on the metronome** asks for the microphone only when Listen is tapped, by the same rules (`rememberListenPermission` in `:feature:metronome`, `MicPermissionRules`, the saved `micRefused`): allowed, it listens at once; otherwise Android's dialog, and listening starts if the player allows it. Nothing is asked when the screen opens. A refusal shows "Microphone is off" in the status line for 8 s, with "Open settings" once only Settings can allow it. The microphone is open only while it listens (at most 15 s): Stop, another control, leaving the screen (`ON_STOP`, another tab) or the ViewModel going all release it. It has its own `AudioRecorder` (`AppContainer.listenRecorder`), so it never waits on the tuner's, which keeps the microphone 5 s after the tuner leaves and reads on one thread. Audio stays in memory.
- **Ear training's Play it back** (Phase 55) asks as the tuner does (`rememberEarMicPermission` in `:feature:eartraining`, `MicPermissionRules`, the saved `micRefused`): once by itself the first time an exercise that listens is shown, checked again on every `ON_RESUME`; Intervals and Chord type never ask. Without it Play it back says "Microphone is off" with *Allow microphone* or, refused for good, *Open settings*. Its own recorder (`AppContainer.earTrainingRecorder`, `UNPROCESSED` with the `VOICE_RECOGNITION` fallback as every recorder) is open only while Play it back is shown and allowed: `WhileSubscribed(5_000)` plus `collectAsStateWithLifecycle()`, as the tuner ([Metronome, widget and watch](ui-other-screens.md), *Practice tab*, **Ear training**). A recorder error (Android silencing the microphone when the screen goes within those 5 s, a call, another app) is caught: "Microphone stopped", and it listens again on `ON_START` (Phase 64).
- **The metronome** plays only while its screen is shown (`StopWhenHidden` in `MetronomeScreen`: `ON_STOP` and leaving the composition both stop it), so going home, locking the phone or opening another screen stops the clicks. A configuration change (the phone turning, dark mode, the font size) recreates the activity, which stops it and disposes the composition too; while `Activity.isChangingConfigurations` neither stops the clicks, so they play on through it. `MetronomeRecreationTest` checks it. No foreground service. While it plays it keeps the screen on (`View.keepScreenOn`), so the screen timeout doesn't stop it; the volume keys set the media volume there, as on the tuner.

## The widget while Twangle isn't running
The home-screen widget is drawn by the app ([Metronome, widget and watch](ui-other-screens.md), *Home-screen widget*), so it can only follow a change Android tells the app about. Checked for Phase 91 (2026-11-11):
- **While Twangle's process runs** (an open app, or one in the background Android hasn't ended yet): everything. `TwangleApplication` follows the settings and the phone's contrast (`phoneHighContrastFlow`: a settings observer on the high-contrast text, Android 14's contrast listener) and redraws on a new language, dark mode or text size (`onConfigurationChanged`, `WidgetRedraws`). A process Android has paused in the background (its cached-app freezer) gets the change when it next runs.
- **While it isn't running, Android sends it nothing for the contrast or dark mode.** `ACTION_CONFIGURATION_CHANGED` (dark mode, text size) reaches only receivers registered by a running app, never one in the manifest; the phone's high-contrast text, Android 14's contrast level and Samsung's high-contrast theme have no broadcast at all; and since Android 8 a manifest receiver gets almost no implicit broadcast anyway (`LOCALE_CHANGED` is one of the few left, so a new language does redraw it, `TuningWidgetReceiver`). The widget's options callback (`onAppWidgetOptionsChanged`) comes only when the launcher resizes it.
- **What needs no signal:** on Android 12+ with the theme on *Same as the phone* the widget carries its light and dark colours both (`setColorInt`), and the launcher swaps them itself, running app or not. With *Light* or *Dark* picked, dark mode changes nothing.
- **So, the limit:** a change of the phone's contrast (any Android), or of dark mode before Android 12 with the theme on *Same as the phone*, made while Twangle isn't running leaves the widget in the old colours until the process next starts: opening the app (a tap on the widget does), a new language, or the phone restarting (Android sends every widget an update then). Each start redraws it at once (`TuningWidget.follow` draws first thing). Its names and the tap are right meanwhile; only the colours lag.
- **Not done:** a JobScheduler job triggered by the settings' content addresses (`high_text_contrast_enabled`, `contrast_level`, `ui_night_mode`) would start the app for such a change, but it adds a job service kept scheduled while a widget is placed, runs late for an app used rarely (Android's standby buckets) and still misses dark mode switched by the clock, all for a few colours that put themselves right at the next start; [IDEAS.md](../../IDEAS.md) keeps it should a player ask.

## Settings
Settings (`:feature:settings`) opens full screen from the gear in every tab's top corner (2.0, Phase 69; a tab of its own in 1.1, [UI basics](ui.md), *Navigation bar*), with a back arrow to where it was opened; About, opened from it, has one too. `MainActivity` switches between tuner, metronome, settings, About and the tuning editor with one saved `Screen` value (no navigation library; `navigation/Navigation.kt`) and a `SaveableStateHolder`; Back returns About → settings → tuner, metronome and editor → tuner, and from the tuner leaves the app (`Screen.back`, JVM-tested). The editor's draft is dropped on leaving it (`removeState`), so each opening starts afresh. `SettingsViewModel` saves every change at once; there is no save button.

Four short groups under headings (2.0, Phase 75, as the first 2.0 mock-up draws them, `docs/design/fresh-start-preview.html`; in Ink's title face and `primary`, marked as headings for TalkBack), the last, *Twangle*, holding Language and About, each with an arrow (they open something). No lines, inside a group or between groups (owner, 2026-11-05: until then a line divided two subjects in a group, where a rule put it, and it looked random; the headings and the room above them mark the groups). Four kinds of control and no more: the Meter cards, choice rows (Under the meter), switches, and rows that open a list (Note names, Light or dark, Language, About). Groups are 32 dp apart; rows, including the card grids, keep 16 dp from the edges. 1.1 had five groups (*Pitch and notes*, *Look*, *Tuner screen*, *While tuning*, *App*); their headings *Pitch and notes*, *Tuner screen* and *App* went from every language, and no setting or saved key changed with the move.
The groups run Look, While tuning, Tuning, Twangle (owner, 2026-11-05: what most players change comes first, so the Meter cards are what Settings opens on; until then Tuning came first, and its reference pitch slider and the note names filled the whole first screen):
- **Look:** Meter first (the meter's look as three picture cards, Classic · Light arc · Strobe, Phase 72, Classic since Phase 78; [Meter and styles](ui-meter-and-styles.md), *Meter in Settings*; first since the owner's review of 2026-11-03, as the one look a player picks), then under the meter (words or cents; in *While tuning* until 2026-11-05, moved beside the Meter cards as it decides what that part of the screen shows), then light or dark with the wallpaper colours under it, then left-handed charts. (1.1 had the style first; 1.1's meter look, in-tune effect, "Below the note" and wave look went in Phase 67; focus mode's switch in Phase 73: the tuner's button alone turns it on.)
- **While tuning:** keep screen on, vibrate when in tune, the vibration guide, tick off tuned strings.

**No Accessibility group** (Phase 85, 2026-11-07): each option for players who can't see the screen well sits where it belongs, the vibration guide in *While tuning*, Phase 86's high contrast in *Look*, because they help sighted players too (a dark room or stage, the phone in a pocket, sunlight), and the players who need them most get them without looking for them: the guide comes on by itself while TalkBack is on, high contrast follows the phone's own contrast.
- **Tuning:** note names, in-tune precision, then A4 calibration last (the setting most players never change, and the biggest). (The instrument, the tuning and Any note are picked on the tuner itself, from the picker chip at its top, and the instrument and tuning in the Practice tools from the same chip at their top: the one sheet, "What are you tuning?".)
- **Twangle** (the app's name, not translated, `translatable="false"`): Language, About.

What each does:
- **A4 calibration:** slider 415–466 Hz in 1 Hz stops, − and + (the shared stepper, `StepperButton`, framed since Phase 63), "Reset to 440 Hz", always in the accent, at 440 Hz too, where a tap changes nothing (owner, 2026-11-05: greyed out at 440 it was too faint on a dimmed screen and lit up only once the slider moved); saved when the finger lifts. Every string joins a number and "Hz" with a no-break space (`\u00A0`), so "442 Hz" never breaks across lines (`HertzStringsTest` checks every language); the value beside the title is one line. The tuner itself shows no "A4 =" line (the screen stays calm; only Settings shows the reference).
- **Note names:** automatic, sharps, flats, Do Re Mi or German: one row showing the picked one that opens the list in a dialog (`ChoiceDialogSetting`, shared with Language; owner, 2026-11-05: five full rows that hardly anyone changes, as *Automatic* follows the app's language; a `RadioGroupSetting` until then). A preset's own spelling wins in guitar mode ([Notes, tunings and audio](notes-and-audio.md), **Tuning spelling**).
- **Precise tuning** (in-tune precision): Relaxed (≤ 5 cents, default) or Precise (≤ 2), as one switch, on for Precise ("Precise tuning", "In tune within 2 cents instead of 5"; owner, 2026-11-05: a yes or no; two choice rows until then, and a segmented switch for an hour, which looked out of place, as nothing else in 2.0 uses one but the metronome's meter). `TunerInterpreter` swaps in `InTuneDetector.forPrecision` on the next frame; everything that follows `inTune` follows it.
- **Left-handed** (default off; Phase 57, option A of the rough mock-up `docs/design/phase57-preview.html`): a `SwitchSetting` at the end of *Look* (since Phase 75; until then at the end of "Pitch and notes", with Note names, the other setting that changes what the charts show) ("Chord charts and the scale neck drawn for a guitar held the other way round"). It mirrors the Chords tool's chart and the Scales neck ([Other screens](ui-other-screens.md), *Practice tab*); nothing else: the tuner's string row is a list from low to high, not a picture of the guitar, so it keeps its order (left to right, in Arabic too), and the Capo helper is a table that draws no shapes. TalkBack's words don't change.
- **Style:** none since Phase 67: 2.0 has one look, Ink, and Settings' Look group holds only the wallpaper colours and light or dark ([Meter, wave and styles](ui-meter-and-styles.md), *Visual styles*). Until then a grid of six mood cards (`StylePicker`) picked one of 1.1's styles.
- **Light or dark:** one row that opens its list, as Note names and Language (`ChoiceDialogSetting`; owner, 2026-11-05, three choice rows until then): *Same as the phone* (until then "System default"), *Light*, *Dark*; plus "Wallpaper colours" first (dynamic color, Android 12+, for every install since Phase 67, Contemporary's only before; off by default since the owner's review of 2026-11-03 (on by default from 2026-10-15, so most players never saw Ink and a green wallpaper took from the in-tune green; a 1.1 player who switched it on keeps it); an accent near the in-tune green falls back to Ink's blue, and the green and amber are never the wallpaper's, see [Meter and styles](ui-meter-and-styles.md)). `MainActivity` reads settings before drawing, so the theme never flashes, and calls `enableEdgeToEdge` again on a change so status-bar icons follow the app. The navigation bar is see-through and gets no scrim (`isNavigationBarContrastEnforced = false`, Android 10+), so the app's background runs to the bottom edge under the gesture handle and under the three navigation buttons too, upright and on its side (Phase 65; MIUI otherwise lays a white or dark strip behind the handle, and until Phase 65 the buttons stood on the system's white or dark strip, chosen from the secure setting `navigation_mode` in `SystemBars.kt`). The buttons stay readable: their icons follow the app's theme (dark on the light theme, light on the dark one), and upright the navigation bar's calm field (70 % of the background colour) lies under them (checked on the Xiaomi 12X with buttons, light and dark, both ways on its side).
- **High contrast** (Phase 86; `highContrast`, key `high_contrast`): a `SwitchSetting` right after *Light or dark* in *Look* ("High contrast", "Black and white with thicker lines; on by itself when the phone's contrast is high"; NL "Hoog contrast", "Zwart-wit met dikkere lijnen; vanzelf aan als het contrast van de telefoon hoog staat"), a switch of its own beside *Light or dark* rather than a fourth choice in it (the owner's pick, 2026-11-08), so it follows light or dark: white on black or black on white ([Meter and styles](ui-meter-and-styles.md), *High contrast*). While the player has never flipped it, it shows (and is) on while the phone asks for high contrast and off otherwise, as the vibration guide follows TalkBack: `phoneWantsHighContrast` (`:core:designsystem`, `PhoneContrast.kt`) is true when Android 14's contrast level is high (`UiModeManager.getContrast()` 0.75 or more; Android's *High* is 1, *Medium* 0.5 stays Ink) or the phone's high-contrast text is on (`AccessibilityManager.isHighContrastTextEnabled` on Android 16+, the secure setting `high_text_contrast_enabled` before it, the only sign there is on the Xiaomi 12X's Android 13); `phoneHighContrastFlow` follows both while the app shows (a contrast listener and a settings observer). `MainActivity` reads it at once for the first frame (no flash), passes `settings.highContrastOn(phone)` to `TwangleTheme(highContrast)` and the phone's state to `SettingsScreen(phoneHighContrast)`. The first flip saves the player's choice, which then holds whatever the phone does. With it on, *Wallpaper colours* is hidden: high contrast sets the wallpaper's colours aside. Samsung's high-contrast theme can't be read by an app; its players find the switch here. A look, like light and dark, not a tool, so it has no tool switch. The widget follows the same rule (`WidgetState.highContrast`, the player's choice else the phone's): while Twangle's process runs, a change of the phone's contrast redraws it (Phase 91, `phoneHighContrastFlow` in `TwangleApplication`); while it doesn't, the widget catches up when it next starts (*The widget while Twangle isn't running* below).
- **Under the meter** (2.0, Phase 78; the owner, 2026-11-05: Tighten / Loosen is a beginner's hint, and to an experienced player it repeats what the needle shows while the number they look at stays small): a `RadioGroupSetting` of two, "Words: Tighten or Loosen" (the default) and "Cents: −12" (NL "Onder de meter", "Woorden: Strakker of Losser", "Cent: −12"). With Cents the tuner shows the signed cents big in the word's place and nothing under them; "In tune" and "Play a string" stay words, and TalkBack still says the direction ([Tuner screen](ui-tuner.md), *Under the meter*). `underMeter`, key `under_meter`; while it is missing 1.1's `show_tune_hint` decides once: a player who had turned "Show tune up/down hint" off gets Cents (*Saved settings* below).
- **Keep screen on** (default on): `View.keepScreenOn` while the tuner is shown with the mic granted and hears playing; a window flag, not a wake lock. A quiet timer (`ScreenAwakeRule` in `:core:dsp`, shared with the watch app; JVM-tested; owner, 2026-10-20) lets go after 3 minutes without playing, so a phone forgotten on a music stand goes dark: a note counts once it has sounded 1 s (a quiet room's sounds came and went as notes of about 0.2 s every few seconds on the Xiaomi 12X, which kept the screen on for good), then holds the screen on however long it sounds (the quiet time starts when it stops), a tool's new state (strum check, 12th-fret check, chord name) counts as playing, and so does any touch on the tuner (seen before the controls, never taken from them) and the tuner coming back to the screen. For the last 10 s a calm warning shows at the bottom, "Screen turns off soon" and "Tap to keep it on" over a thin bar that empties (`ScreenOffWarning`; TalkBack reads it as it shows; a step a second with animations off); a tap anywhere starts the 3 minutes afresh. Then the phone's own screen timeout has the screen, and once it is off the activity stops and the microphone closes as usual. No notification (it would need its own permission and stay in the shade) and no setting of its own. The metronome keeps the screen on while it plays, without a timer: playing is the player's own choice (the watch's stops by itself 30 minutes after its last touch, Phase 91: a wrist forgotten with it playing has no one to see the screen; [Metronome, widget and watch](ui-other-screens.md), *The metronome page*).
- **Vibrate when in tune** (default on): `InTuneHaptic` clicks once (`EFFECT_CLICK`, 20 ms one-shot before Android 10) when `inTune` turns true. It uses `Vibrator` directly because Compose/View haptics obey the phone-wide touch-feedback setting, which many people switch off; this needs the normal `VIBRATE` permission. `InTuneTickRule` (`:core:dsp`, shared with the watch's wrist tap) skips a second tick for the same note within 1.5 s; the state is saved, so rotating doesn't tick. Never while the vibration guide is on: its long buzz says "in tune" instead (`TunerViewModel.vibrateInTune` is false then).
- **Vibration guide** (Phase 85; `vibrationGuide`, key `vibration_guide`): taps while the tuner hears a string, one to tighten, two to loosen, quicker as it nears pitch, a long buzz in tune ([Tuner screen](ui-tuner.md), *Vibration guide*). A `SwitchSetting` right after *Vibrate when in tune* ("Vibration guide", "Taps while you tune: one to tighten, two to loosen, long when in tune"; NL "Stemmen op gevoel", "Tikjes tijdens het stemmen: één = strakker, twee = losser, lang = zuiver", the word's own Strakker, Losser and zuiver). While the player has never flipped it, it shows (and is) on while a screen reader is on and off otherwise (`ScreenReaderSpeech.screenReaderOn`, touch exploration, passed to `SettingsScreen` by `MainActivity`); the first flip saves their choice, which then holds whatever TalkBack does. An option inside the tuner, so it goes with the tuner's switch and has none of its own.
- **Tick off tuned strings** (2.0, Phase 71, the string tick-off: a beginner's help, default **off**; `stringTickOff`, key `string_tick_off`, off when missing): each peg gets a check once its string is in tune, and "In tune. Play." shows once all have one ([Tuner screen](ui-tuner.md), *Strings ticked off*, *Pegs*). Its line: "A check on each string once it's in tune, and “In tune. Play.” when all are" (NL "Gestemde snaren afvinken", "Een vinkje op elke snaar zodra die zuiver is, en “Zuiver. Speel maar.” als ze allemaal zuiver zijn"). It replaced **Show tuning help** (1.1, default on, `show_tune_hint`, "Show tune up/down hint" until 2026-11-01), which turned the "Tune up / Tune down" hint and, from Phase 65, the ticks on and off: 2.0's word under the lens always shows (owner, 2026-11-02), and the owner wanted the ticks a toggle off by default, so the ticks don't read `show_tune_hint` and a 1.1 player starts without them; its switch and texts went from every language ([history](history.md)). Only *Under the meter* reads it, once (above).
- **Language** (`LanguageSetting`, the first row of the *Twangle* group): the app's language, "Phone's language" or one in its own name. A tap opens a dialog listing "Phone's language" (follows the phone) and then every language of `twangle.languages` in its own words, in alphabetical order of those names (Latin letters first, then Cyrillic, Arabic, Devanagari, Hangul and Han). Picking one sets it through AppCompat and the screen is recreated in it, still on Settings. The list takes at most 60 % of the window's height, so the dialog keeps clear of the screen's edges; it scrolls, opens at the picked language, and a thin line at its top or bottom shows there is more that way. Indonesian is "Bahasa Indonesia" (the locale data says only "Indonesia"). Details in [Languages](languages.md).
- **About** (its own page, `AboutScreen`, opened from a `LinkSetting` row showing the version; Settings and About share `SettingsPage`): name and version (`BuildConfig.VERSION_NAME` passed from `MainActivity`), a short row on where the name comes from, *The name* (Phase 79, a row like the promise's so it doesn't read as part of the name and icon; the owner's yes to the branding review: "twang" is English, so most players don't know it; every language says that it is the English word, as Dutch does; the "angle" and "tangle" in the name are left unsaid), the free-forever promise, a short privacy statement (settings stay on this device, and in Android's own backup if it is on; keep it in step with PRIVACY.md), a **Help and website** row (a `LinkSetting`, "How each tool works, and answers to common questions"; Phase 54), a quiet **Rate Twangle** row (a `LinkSetting`, "Twangle on Google Play"; Phase 37), and a credit for every bundled font and library, each with the › of the rows above it (since Phase 63), as it opens something too. Each credit opens an `AlertDialog` with the full licence, read from assets on `Dispatchers.IO` and reflowed (`reflowLicence`). With no internet permission every licence ships in the APK: OFL texts in `:core:designsystem` `assets/licenses` (`bundledFontCredits`, kept in step with `res/font` by a JVM test) and Apache 2.0 and Protocol Buffers' BSD 3-Clause text in `:feature:settings` `assets/licenses`. Besides AndroidX and Kotlin, the credits name the libraries that come in with them: Okio and a copy of Protocol Buffers (DataStore), kotlinx.serialization, JSpecify and Guava's ListenableFuture (AndroidX), and Google's Material Symbols for the icons; check `:app:dependencies --configuration releaseRuntimeClasspath` when a dependency is added. A new library needs its own credit, and its own licence file if it is under another licence. Licence texts are what users read, so they hold no build details (script names, source paths; `FontCreditsTest` checks the font ones). *Rate Twangle* (`openPlayPage`, passed in by `MainActivity` with the app ID) opens Twangle's Play page in the Play Store app (`market://details?id=…`, aimed at `com.android.vending` so another maker's store, such as Xiaomi's, doesn't take it), else `https://play.google.com/store/apps/details?id=…` in the browser, else nothing. It is only a link, and no internet permission is needed, since the other app does the opening; Google's own rating window, asked for once from the tuner, is the next item. *Help and website* (`openWebsite`, passed in by `MainActivity`) opens [the website](website.md) in the phone's browser: `AboutSection` picks the home page in the app's language from `LocalConfiguration` (`websiteLink`: `https://klaboukes.github.io/nl/` in Dutch, the English home page in every language the site doesn't have yet, which the row's summary says in those languages), and `websiteIntent` is a plain `ACTION_VIEW` of that address in the `BROWSABLE` category, aimed at no app in particular. Like *Rate Twangle* it is only a link: the browser loads the page, so the merged manifest still has no `INTERNET` permission (checked after the build, Phase 54). `SettingsContentTest` checks the row and the link it asks for in English, Dutch and German, `WebsiteIntentTest` the intent, `WebsiteTest` the language choice; the settings row that opens About says "help" too. The links need no `<queries>` entry: the opener just tries each and catches `ActivityNotFoundException`.
- **Google's rating window** (Phase 50; the owner's pick B of the rough mock-up `docs/design/rating-moment.html`, 2026-10-28: the About row stays, and Google Play's In-App Review is asked for once at a good moment, because ratings weigh most in Play search). No setting, no switch (it is not a tool) and no text of Twangle's own: no "Do you like Twangle?" first, which Google forbids since it filters out unhappy players.
  - **When:** at most once ever (`ratingAsked`), never on the first day after `firstUseMillis` (`RatingMoment.mayAsk`, `FIRST_DAY_MILLIS`), and only right after every string of the tuning has been in tune in one go: `AllStringsInTune` follows the tuner's own states in one listening session (guitar mode, locked or not; chromatic mode and the tools count nothing; a new tuning or A4 starts afresh; the same strings are ticked off on their buttons, [Tuner screen](ui-tuner.md), *Strings ticked off*) and says true at the state where the last string comes in tune. `TunerViewModel` then waits for the strings to fall quiet (`QUIET_MILLIS`, 2 s of `Listening`; a note heard meanwhile starts the wait again), so the window never comes mid-tuning and only after the in-tune effect, and sets `ratingDue`. Leaving the tuner ends the wait. `TunerScreen` asks `RatingWindow` (not while the instrument panel is open) and calls `onRatingAsked`, which saves `ratingAsked` before Google even answers, since Twangle never learns whether the window showed. `RatingMomentTest` covers the rule, the tracker and the ViewModel with synthetic strings.
  - **First use:** `MainActivity` calls `noteFirstUseOnce(now)` at every start. An update from a version before Phase 50 notes its first use at its first start in the new version, so it waits a day too.
  - **The window** is Google's: `PlayRatingWindow` (`:app`, the only class that knows the Play library; `AppContainer.ratingWindow`, `testRatingWindow` for tests) calls `ReviewManager.requestReviewFlow` and `launchReviewFlow`; the Play Store app draws the window and talks to Google. Google keeps a quota and decides whether it shows at all; an install from the PC never shows it (internal app sharing or a Play track does). Every failure is silent. `RatingWindow.NONE` stands in for previews and tests.
  - **The library** (`com.google.android.play:review`, with `core-common`, `play-services-basement` and `play-services-tasks`) adds **no permission**: checked in the merged manifest when it was added (2026-10-28), it adds only Play's hidden `PlayCoreDialogWrapperActivity` (not exported) and the `com.google.android.gms.version` meta-data. Check again after a version bump. It is under Google's own terms (the Play Core SDK Terms of Service, the Android SDK License), not an open-source licence, so it has no credit under "Fonts and open-source software". GPL 3 alone wouldn't let anyone convey Twangle combined with it, so `LICENSE` opens with a **GPL 3 section 7 additional permission** (owner, 2026-11-12, Phase 93) from the copyright holder, Klaboukes: anyone may combine Twangle with this library and the Play libraries it brings in, and convey the result; it covers those libraries only, extends to modified versions, and whoever conveys a copy may remove it. So anyone may build the Play version, and the owner's own Play build stays sound once others' code is in it (the GPL text below the notice is unchanged; README's *Licence* says it in one sentence). A new non-free library would need its own permission, which needs every contributor's yes once there are others, so it is better avoided. For F-Droid there is still a **free build** without it: `-Ptwangle.foss=true` (for F-Droid's recipe, its `gradleprops`) puts `app/src/foss/kotlin` in place of `app/src/play/kotlin`, so `storeRatingWindow` gives `RatingWindow.NONE` instead of `PlayRatingWindow`, and leaves the library out of the dependencies; a guard in `app/build.gradle.kts` stops that build if anything of `com.google.android.play`, `com.google.android.gms`, `com.google.firebase`, `com.google.android.datatransport` or `com.google.mlkit` (the last two since Phase 91, as F-Droid's scanner flags them too) comes in another way. A Gradle property rather than a product flavour, so every task keeps its name (the scripts, the release, the Baseline Profile); if F-Droid's scanner still flags the library's line in `gradle/libs.versions.toml`, its recipe removes that line before building, or the property becomes a flavour then. The nightly CI builds its release (`:app:assembleRelease -Ptwangle.foss=true`, unsigned; its debug build until Phase 90), so its own R8 shrinking is checked too, as F-Droid will build it, also on a night whose main step failed. Same app ID and version as the Play build; the About row that opens Google Play's page stays (a link, not a library).
  - **Privacy:** PRIVACY.md and its Dutch copy say the window is Google Play's, that Twangle sends nothing to it and never learns whether or how the player rated, and that the first-use time and `ratingAsked` are kept.

- **Forgiving reads:** a missing, unknown or out-of-range value gives its default; an unreadable file gives all defaults, and a corrupt one is replaced so saving works again (`DataStoreSettingsRepositoryTest` checks both files through the app's own factory, `create`). A read that fails (an I/O error) shows the defaults only if nothing was shown yet and is tried again after 0.5 s, doubling up to 30 s (`readRetryMillis`), so one failed read doesn't keep the defaults, or miss later changes, for the rest of the session. Instrument and tuning are read as a pair: no saved instrument (versions before the picker) or an unknown one gives the saved tuning's own instrument, else the guitar; a tuning that isn't one of the instrument's presets, or an unknown one, gives the instrument's standard tuning. A saved lowering out of range is cut to what the tuning can go (none below 0).
- **Writes that never crash** (Phase 64): every write goes through one private helper, `save`, which catches the `IOException` that `dataStore.edit` throws on a full phone or a storage error and logs it (`Log.w`, tag `Settings`), so nothing changes and the app keeps running with the old value. No setter throws, so its ~50 callers may launch their writes bare, the first-use notes in `MainActivity.onCreate` among them, which would otherwise crash every start on a full phone. Only a write the player waits for says it failed: `addCustomTuning` and `updateCustomTuning` return null, and the tuning editor stays open (below). `FakeSettingsRepository.failWrites` does the same for tests; `DataStoreSettingsRepositoryTest` calls every write of the interface against a store whose writes throw.
- **A change of several settings is one write** (Phase 89): what one tap changes together is saved in one DataStore edit, through one repository call, so nothing that follows `settings` (the tuner, the widget, the other screens) ever sees half of it: a pick in Practice's tuning panel switches the tuner to guitar mode in the same write (`setInstrument`, `setTuning` and `setLoweredBy` with `guitarMode = true`), the drone's menu saves its sound, notes and octave as one (`setDrone`), and a row of the capo helper's table saves Chords' root, chord type and Chords as the tool used last as one (`openInChords`); custom tunings were already saved and picked as one (`pick = true`). `MainActivity`'s writes run in `AppContainer.save`, a scope that lives as long as the app (on the main thread, so they keep their order; a failure is logged), not in the activity's own, which a turn of the phone ends mid-way. `DataStoreSettingsRepositoryTest` counts the edits of each.
- **Read once per change** (Phase 65): about 40 collectors follow `settings` (every ViewModel's options, the widget, the app's theme). DataStore hands each the same `Preferences` after a write, and the repository turns them into `AppSettings` once for all (`parse` keeps the last pair of files read and its settings), not once per collector; `DataStoreSettingsRepositoryTest` counts it with ten readers. A state shared in `AppContainer` (`stateIn`) was the other way, but it lags a write: a read right after one could still give the old value, and tests and `TuningEditorSaver` read right after writing.
- **Seeded at start:** `MainActivity` reads the settings before it draws anything (*Light or dark* above) and hands them to `TunerScreen` as `saved`; `TunerViewModel` starts every saved option from them (mode, instrument, in-tune precision, focus mode, hint and the rest) until its own reading arrives, so the first frames never show the defaults (before Phase 65 the looks flashed theirs for a frame or two).
- **The watch** keeps its own (`:wear`, nothing from the phone): whether the microphone was refused (`twangle_wear.xml`, below) and, since Phase 80, the metronome's tempo and whether its speaker clicks (`WatchMetronomeStore`, DataStore `watch_metronome`, 120 BPM and taps only by default). Both are left out of Android's backup and device transfer (`wear/src/main/res/xml/`), so the policy's "on the watch itself" holds ([Metronome, widget and watch](ui-other-screens.md), *The metronome page*).
- **This phone only** (Phase 65): `mic_refused` lives in `files/datastore/this_device.preferences_pb`, which the backup rules leave out (`app/src/main/res/xml/backup_rules.xml` for Android 8–11, `data_extraction_rules.xml` for 12 and newer, both cloud backup and device transfer). A phone restored from a backup has never asked for the microphone; with the old flag it would give up asking at the first dismissed dialog. Versions before Phase 65 kept it with the settings: a DataStore migration (`MoveMicRefused`) moves it into this phone's file before the settings are first read. The watch's only store, the shared preferences `twangle_wear.xml` (the same flag), is left out the same way (`wear/src/main/res/xml`).
- **Migrations** (in `DataStoreSettingsRepository`, not as enum constants, so no code can pick the old names again; JVM tests cover each case): **the lens look's rule** ([2.0 plan](v2-plan.md), *Settings from 1.1*): a saved `meter_look` of `TRAIL`, `LIGHT_ARC` (1.1's Light arc) or `STROBE` is that look; else, where 1.1 showed its strobe wave under the meter, the strobe: 1.1's display `tuner_display` the wave (`WAVE`; while none was saved the older switch `show_waves`, else 1.1's default, the wave) with the wave look `wave_look` `STROBE` (or the older `STRIPES`), or the older display `STROBE`; else the trail, the default. `setLensLook` removes `tuner_display`, `show_waves` and `wave_look`, so the rule stops once a look is picked. 1.1's `in_tune_effect` (Calm or Bold) is left in the file unread: one glow. (Until Phase 67 a saved style `"PREHISTORIC"` or `"MIDDLE_AGES"` read as `ANCIENT`, and a saved meter look `SPIRIT_LEVEL` as Pointers, `ECLIPSE` as Loupe; 2.0 reads no style at all.)

## Custom tunings
A `CustomTuning(id, name, instrument, notes)` (`:core:settings`) is a tuning the player made; its `tuning` is a plain `Tuning` with the same id and no spelling of its own (the sharps/flats setting writes it), so the tuner, string row and pitch range treat it like a preset. `AppSettings.customTunings` holds them all in the order they were made; `customTuningsFor(instrument)` gives one instrument's (for the picker, below its presets) and `pickedCustomTuning` the picked one, or null for a preset.
- **Ids** are `custom_` plus a random UUID, made once by `addCustomTuning` and never changed, so editing keeps the tuning picked. No preset id starts with `custom_` (JVM-tested).
- **Names** are normalized on every save and read (`CustomTuning.normalizeName`: trimmed, runs of white space made one space, at most 40 UTF-16 chars, cut at a whole character by `CustomTuning.cutName` (`java.text.BreakIterator`), never inside an emoji or between a letter and its accent; Phase 65) and may not come out empty. Duplicate names are the editor's to refuse; compare normalized names.
- **Notes** are one per string of the instrument (MIDI 0–127). The instrument is fixed when the tuning is made.
- **Repository:** `addCustomTuning(name, instrument, notes)` saves it after the others and returns it, not picked (pick it with `setTuning(it.tuning)`); `updateCustomTuning(id, name, notes)` keeps its id, instrument and place, and a picked one stays picked with the new notes (that is a tuning change, so a locked string is released); `deleteCustomTuning(id)` removes it and, if it was picked, picks its instrument's standard tuning. A picked one that was lowered starts not lowered after an edit (its new notes are the ones to tune to) or a delete. Bad input (empty name, wrong number of notes) throws `IllegalArgumentException` and saves nothing. `FakeSettingsRepository` does the same, with ids `custom_1`, `custom_2`, ….
- **Editor** (`:feature:tuner`, `editor/TuningEditorScreen.kt`, its own `Screen` in `MainActivity`, so the tuner rests and lets go of the microphone meanwhile; on the quiet background like the settings). Opened from the panel's last row, "New tuning", for the instrument shown; it also opens for an existing `CustomTuning` (`editingId`, instrument fixed) from Edit in that tuning's menu in the panel. Material form: a close button (leaves without saving) and Save along the top, the title ("New tuning" / "Edit tuning", a heading that wraps at large fonts) and "Instrument: Guitar", the name field, then the heading "Strings" and a row per string, thickest first: "E₂ string" (its standard note), then − note +. A new tuning starts from the instrument's standard notes.
  - **Notes** move a semitone per tap and stay within **B0–E6** (MIDI 23–88, `EDITOR_NOTE_RANGE`): B0 is the lowest preset string and still reads a semitone flat at A4 = 440 Hz (and in tune at 415) in the low-note window, which a tuning this low switches on by itself; E6 still reads a semitone sharp at A4 = 466 Hz (1479 Hz, under the detector's 1500). At an end the button is turned off. Notes are written in the notation setting (a custom tuning has no spelling of its own); the caption keeps the standard tuning's.
  - **Name checks** run only when Save is tapped: empty ("Give the tuning a name") or already one of the instrument's tunings ("There is already a tuning with this name": its presets' names as shown and its other custom tunings', compared as `normalizeName` gives them and ignoring case; another instrument's names are free). The message goes as soon as the name changes and comes back only on the next Save, so nothing flashes while typing. Typing stops at 40 chars, cut by `cutName` too, so a typed emoji is kept whole or not at all.
  - **Save** (`saveDraft`, JVM-tested) adds the tuning or updates it and **picks it** in one DataStore write (`addCustomTuning` / `updateCustomTuning` with `pick = true`), and returns to the tuner, whose button names it ("Guitar · Drop D loose"; `TunerViewModel.customTunings`, passed in from the saved settings at the start so the id never shows). The save runs in `TuningEditorSaver`, a small ViewModel, so turning the phone mid-save neither cuts it off nor loses that it is done: the new screen sees `SavePhase.SAVED` and closes. Save does nothing while a save runs. When the phone can't write it (`SavePhase.FAILED`), the editor stays open with its edits and one line in the error colour under the name field (where its name messages go, so the keyboard can't hide it; the name itself isn't marked wrong), "Couldn't save the tuning. Is the phone's storage full?" (a polite live region, so TalkBack reads it), until the next Save, which tries again; a tuning edited that was deleted meanwhile still just closes. The saver is shared by every opening (the activity's ViewModel), so each opening calls `opened()` once (a `rememberSaveable`, so a turn of the phone isn't a new opening), which drops an earlier opening's failed save: leaving after a failed save and opening the editor again, for this tuning or another, shows no old error (Phase 89).
  - **Discard changes?** The close button, Back and a tap on the home-screen widget leave at once when nothing was edited, else they ask "Discard changes?" (Discard, in the error colour, or Keep editing; Back or a tap outside keeps editing). An edit is another note or a name that would be saved differently (`TuningDraft.hasChangesFrom`: spaces alone don't count, a note moved and moved back doesn't either). The editor handles Back and the widget's request itself (`closeRequest`), so `MainActivity` registers no Back handler while it shows. Its title uses the delete question's size (`DIALOG_TITLE_SCALE`).
  - The draft (`TuningDraft`, pure and JVM-tested) survives rotation, and so does the open question. TalkBack: the note says "E 2 string, D 2" (a polite live region, so it is said again after a tap; the caption is hidden), the buttons "E 2 string, a semitone lower / higher", the message is a live region. `TuningEditorTest` checks it all, Dutch ("e 2-snaar, dis 2"), and every control and text wholly shown at 2× text with eight strings in Dutch (every style in a thorough run).
- **Stored** in one string (`CustomTuningCodec`): a line per tuning, `id|instrument id|midi,midi,…|URL-encoded name`; fields added later go after the name and older readers ignore them. A line that can't be read (unknown instrument, wrong note count, bad number or note, no name, repeated id) is skipped and the rest kept; the next save writes only the good ones. A picked custom tuning that is gone, damaged or of another instrument gives the instrument's standard tuning, so damaged data always falls back to the presets.
