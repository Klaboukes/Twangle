**A unit test that reads a file names it as an input.** Gradle skips a test task whose inputs haven't changed (`UP-TO-DATE`, or `FROM-CACHE`), and those inputs are the compiled code and the R class, which holds a text's id but not its words. So every Android module's tests count its own `src/main/res`, `src/main/assets` and manifest (root `build.gradle.kts`), and a test that reads further declares that too: `:app`'s the language lists, the store texts, `translations/`, every module's texts and code, `scripts/ui-tests.sh` and `app/proguard-rules.pro` (`app/build.gradle.kts`); `:wear`'s `:core:designsystem`'s texts; `:feature:settings`'s `gradle.properties`; `:core:dsp`'s `compose-stability.conf`. Until Phase 90 (2026-11-10) a broken keep rule, a changed licence file or text value passed on the earlier result. A test that reads a new file outside these adds it next to them; the nightly CI's skip rule (`.github/workflows/android.yml`) keeps the build for any such file under `scripts/`, `docs/`, `website/` or a `.md`. A path handed to a test (a system property) is relative to the module, never a full path: the property is an input too, and a full path differs in every worktree, so each would run the tests again instead of sharing the build cache's result (`:core:dsp`'s, until Phase 91).

## Scoped runs
With no module given, `scripts/ui-tests.sh` runs only the modules the branch's change (since it left `main`, uncommitted work included) can reach; `scripts/ui-test-scope.py` decides. A module's own main or androidTest sources reach it, and a feature module's main sources also `:app`, whose tests show every screen. A changed Kotlin file of `:core:dsp`, `:core:settings`, `:core:audio` or `:core:designsystem` (main or testFixtures) reaches only the modules whose code uses what changed: each changed line belongs to a class member (a `fun`, `val`, `var` or nested class at the class's first indentation) or else to the whole top-level declaration; a member reaches the modules that name it and can see its class (they name the class, or something in the core modules that names it), a whole declaration every module that names it, and core code that uses what changed counts as changed too, and so on. Comments, imports and lone closing brackets change nothing, and members Kotlin calls without their name (operators, `equals`, `toString`) count as the whole class. The broad set (every module that depends on that core module) stays where names can't tell: core resources, manifests and build files, a file that can't be read as Kotlin, anything in `:core:testing`, and `TwangleTheme`, which every screen draws. It reads names, not types, so a name used for something else too only widens the set; the rare miss (a constructor argument moved between two of the same type) is left to the full check, which tests everything. `--since-pass` uses the same mapping from each module's last pass. `--dry-run` prints the pick and a reason per module without a build or the phone; `python -I scripts/ui-test-scope.py --why <base> [<head>]` does it for any two commits, and `--self-check` checks the parser and one known case.

Until 2026-10-28 any change in those four core modules ran every feature module and `:app`. The Play it back increment (Phase 55: a new `core.dsp.eartraining` file and new settings keys) ran six modules, about 12 minutes on the Xiaomi (tuner 213 s, practice 158 s, app 170 s, settings 81 s, metronome 46 s, Ear training), where `:feature:eartraining` and `:app` are what use it.

## Fast UI tests
Compose UI tests use `createSharedActivityComposeRule()` (`:core:testing`): one activity for the whole run, a fresh composition (own recomposer, test clock and `ViewModelStore`) per test. `SharedActivityTestRunner` stops AndroidJUnitRunner closing every activity after each test, which took ~0.7 s per test on the Xiaomi 12X; together they cut the tuner suite from ~8½ to ~3 minutes. Every module with UI tests uses that runner, `:app` too since 2026-10-28: with the plain one its shared-window tests (`NavigationBarTest`, `TourStylesTest`) closed and reopened the window for each of their 25 tests, which looked like the app restarting over and over. `:app`'s tests of the real app still open `MainActivity` once or twice per test (`ActivityScenario.launch(…).use`), on purpose: they check starts, restarts and the lifecycle. Pixel checks take one capture and cut it up (a capture costs a frame), and build assertion messages only on failure. A test that changes the activity itself (rotation, recreation, window flags) still uses `createComposeRule()` or `ActivityScenario`. How to write them: [writing-tests.md](../../.claude/skills/ui-test/writing-tests.md).

## Any phone
Every on-device UI test gives the same answer on any phone and fails only when Twangle itself is wrong (owner, 2026-10-20: users have all kinds of phones). The first overnight run on the Galaxy S26 (360 × 780 dp, three-button navigation, edge to edge forced by Android 15+) gave 99 failures in 21 tests that passed on the Xiaomi 12X (393 × 873 dp, gestures): the tests had quietly assumed the Xiaomi. The rules since:

- **A test that sets a window size goes through `PhoneScreen`** (`:core:testing`): `PhoneScreen(area, bars, fontScale, locale) { … }`. The window is `area` plus the `SystemBars` around it, forced with `DeviceConfigurationOverride.ForcedSize`. Where the phone's screen is smaller, everything is drawn at a lower density (a 393 dp window on a 360 dp phone at 2.74 instead of 3.0) but laid out in the window's own dp, so every size is checked on every phone and none is skipped. Bounds read through `getBoundsInRoot()` and the like use the node's own density, so they are in the window's dp too; px values (text layouts, captures) are the phone's own. A test without a size of its own gets a fixed one (`TunerContentTest.PHONE`, 360 × 780; `SettingsContentTest.PHONE`, 360 × 730), never the phone's screen.
- **Fake system bars, the same on every phone.** The shared activity is edge to edge, as the app and every phone from Android 15 on. `PhoneScreen` hands the content its bars as window insets in the window's dp (`DeviceConfigurationOverride.WindowInsets`), replacing the phone's own: a 24 dp status bar, a 24 dp gesture bar or 48 dp of navigation buttons (at the bottom upright, on the right on its side), the camera on the left on its side. `SystemBars.tab()` is what one tab's screen gets in the app (the app's bar or rail takes the bars on its side), `SystemBars.phone()` the whole screen (the navigation bar tests); `inside()` turns a whole phone's size into the area. Fit tests alternate buttons and gestures (light and dark). Checks of "inside the window" use `safeArea()`, the part the bars leave clear. Screens that pad for the bars themselves (Metronome, Settings, Practice) get the tab's bars; `TunerContent` gets none, as `TunerScreen` pads for it.
- **One root more.** The fake bars come through a view of their own, so a `PhoneScreen` test has two compose roots: `onRoot()` is ambiguous, `onPhoneScreen()` is the window (captures, touches across it).
- **Menus escape the forced size.** A Material dropdown (the Chords and Scales panel) is a window of its own, laid out on the phone's real screen, so whether it fits under its button differs from phone to phone: in Dutch at 2× text the chord panel fits under the name on the Xiaomi 12X but not on the S26, and Material moves it up there. `assertMenuUnder` (`:core:testing`) checks a menu opened under its button wherever it fits (its height against the room down to the app window's bottom, less Material's 48 dp margin) and lets it move up only where it doesn't.
- **Menus follow their screen.** A `DropdownMenu` is a window of its own and takes the phone's density, not the forced one: on the S26 the Scales panel came one to a row at 393 dp. The app's menus keep their screen's density inside (`ScreenDensity`, `:core:designsystem`), which changes nothing in the app, where the two are the same. Dialogs and the tuning panel still take the phone's text size and language (checked on the phone).
- **Px rounding.** At a forced density text and boxes round to whole px differently: a 48 dp row exactly as tall as its 2× line is a px short at 1.44. `assertWhollyShown` allows one px each way (`isCutOffAtTheBottom`: a line lost, or the lines more than a px taller than the box; a line at most a px wider than its box). A line the line breaker could have broken (it holds a space) but judged to fit may be up to 2 % wider: Samsung's Hindi font draws such lines a little wider than their measure (4 px of 984, 8 of 444, drawn whole); a word too long for its box gets the px alone. Pixel checks measure in dp where a phone's density moves a feature across a px boundary (`MeterLooksTest`: a clip is a step along at least 3 dp of the box's edge; Classic's in-tune tick, 0.8 dp under its top, landed in the sampled row at 3.0 and not at 2.75).
- **The test's language is the text's language.** Compose lays text out (line breaks, Japanese line-breaking rules) by the process's default language, not the configuration's, so `PhoneScreen` sets the default to the language it shows and the shared rule puts the phone's back after each test. Without it the screen showed Japanese in 6 lines while the layout TalkBack reads (and the checks) broke it into 7, on a phone set to English.
- **UI Automator on the real app:** wait until a list has come to rest before tapping in it (a tap on a gliding list only stops it); scroll with swipes rather than the first scrollable it finds.

What the S26 found in the app itself: focus mode flickered (the layout chose compact or not by width, and hiding the rail and bars changed the width: 578 ↔ 663 dp with navigation buttons, ~40 switches a second; [Tuner screen](ui-tuner.md)), the menus above, and the Practice name button: its height, two and a half lines of 12 sp, was turned into dp in one go (30 sp), and from Android 14 large text sizes grow less than small ones (nonlinear font scaling), so at 2× text the button was shorter than its two lines (Space Age's Dutch "A♭ majeur-pentatonisch" on a 320 dp phone; the Xiaomi, Android 13, scales linearly). One line's size is turned into dp first now. With realistic bars (72 dp less height on a 360 × 800 dp phone with navigation buttons) the tour's note balloon in Space Age, German and Indonesian at 2× text, found room on no side and lay over the note; it now widens to 8 dp from the screen's sides where that lets it fit ([Tuner screen](ui-tuner.md), *Tour*).

## Every screen light and dark
`TunerStylesTest`, `SettingsStylesTest` and `MetronomeStylesTest` check each screen in Ink, light and dark (1.1 ran them in each of its six styles, a parameter of each class; 2.0 has one look, so since Phase 67 they are plain classes and loop over light and dark themselves): the tuner upright (a short narrow phone at 1×: 360 × 570 dp, what a 360 × 720 dp phone with navigation buttons leaves under its bars and the app's; the owner's Xiaomi 12X at 1.25×, less 80 dp for the navigation bar) and in its full layout on its side (less the 80 dp rail) fits without scrolling, nothing overlaps; at 2× text every part, Settings row, card name and About text can be scrolled to and is then wholly shown (`assertWhollyShown` in `:core:testing`: nothing clipped, no line cut off or ellipsized), and the string buttons fit the longest names (solfège flats); TalkBack hears the reading once, nothing in the meter, the mode switch, strings and light-or-dark choices by name with which one is picked. `CompactLandscapeStylesTest` covers the compact layout; the lens's looks get `LensLooksTest` (Phases 71, 72). `StyleScreenshots` (`scripts/style-screens.sh`) pictures the tuner light and dark for the owner.

**And in high contrast** (Phase 86, 2026-11-08): the full check runs the screens' tests a second time in the high-contrast look, after the Ink sweep (`scripts/full-check.sh`'s *contrast* stage, `scripts/ui-tests.sh <the six screen modules> --high-contrast --thorough --cool`; `--contrast` runs only it). `--high-contrast` passes `-e highContrast true` (`isHighContrastPass` in `:core:testing`), and the shared rule then provides `LocalHighContrastByDefault` = true round every test's content, the look a `TwangleTheme` with no `highContrast` of its own takes; so every test that loops over light and dark checks the look's white-on-black and black-on-white faces in the one pass, at no extra cost per face. A test that names its look (`TunerContentTest`'s and `SettingsContentTest`'s own high-contrast checks, which compare it with Ink) keeps it. `:app`'s tests start the real app, so `HighContrastPassRule` (around `MainActivity` in `TunerTabTest` and `PracticeTabTest`) turns the look on through its setting and puts back what it found. `:core:testing` and `:core:audio` draw nothing of the look and are left out; the watch has no high-contrast look. Light and dark faces both, rather than one, because they are different colours (white or black ink, two greens, two ambers) and a fit or overlap test costs the same in either; one pass rather than two, because the tests already loop over both. It passes with `-a`, so it notes no module as passed (the Ink sweep does), and the every-language checks stay in Ink: the look changes colours, line widths and weights, not the length of texts, and its extra-bold ruler names are drawn, not text. It takes about 12 minutes on the Xiaomi (2026-11-08: the tuner 3½, Practice 2½, `:app` 2, Settings, the metronome and Ear training about 1 each), so the full check runs about 45 minutes when every screen changed.

## Every language
`@EveryLanguage` tests (`:core:testing`) show the tuner (a note with the meter, and listening), Settings, About, the metronome (with each of Listen's status lines, under a header as 1.1's Practice tool button), the Practice cards and the Chords tool and the navigation bar (with and without Practice) in each of the languages in `twangle.languages` (`shippedLanguages`, from `BuildConfig` of `:core:testing`) at 2× text, upright on a 360 dp phone and on its side, and check every text TalkBack can find, scrolled to in turn, is wholly shown (`assertEveryTextWhollyShown`: no letter cut off, no line lost, no ellipsis); a text taller than its scrolling column must fill it. Texts that are only measured, never placed (a status line keeping the room of its longest wording, `TallestOf` and `Kept` in the tuner's tools), are not on screen and are skipped. The Practice checks also fail a word broken across two lines (`assertNoWordBroken`; Chinese and Japanese may break anywhere): Android breaks "majeur-pentatonisch" at its hyphen only with hyphenation on, so Practice puts a zero-width space after hyphens (`breakableAtHyphens`). A failure saves a picture of the screen to the run's extra output, which the script copies to the module's `build/outputs/connected_android_test_additional_output`. `assertEveryTextWhollyShown` fetches a screen's texts once and checks each as fetched; only a text not wholly in view is scrolled to, to the top of its column so the next ones are in view too, and the texts fetched again after that scroll (2026-10-30: fetching them all again for each text, and scrolling each only just into view, took two thirds of a check; Ear training's Dutch went from 51 s to 19). In every language they took about an hour per 1.1 style before that (25 languages, 2026-10-30: Ear training 19 minutes, the tuner 14, Practice 13, Settings 10, the metronome 3, `:app` 1), so all of them run only with `--all-languages`, in the full check, right after that run's `/translate` has filled in the texts the day left in English and Dutch only. There a module's checks that passed whole are noted, and later runs skip them while nothing the module shows changed since (`scripts/ui-test-scope.py`, as for `--since-pass`) and the pass is under a week old, so a missed change still comes up within a week (owner, 2026-10-30: all 36, six modules in six styles, took 6 of the night's 8 hours; 2.0 has six, one a module, about 17 minutes together on 2026-11-05; `scripts/full-check.sh --dry-run` says which run, `--full` runs all). By day `--languages` runs them in the testers' languages only, English and Dutch (`checkedLanguages`: the script passes `-e languages en,nl`, `DAY_LANGUAGES`, from `twangle.dayLanguages` in `gradle.properties`), about a minute per module: Dutch has the long words, and a text too long in another language waits for the night (owner, 2026-10-26). Dialogs, menus and the tuning panel are windows of their own that take the phone's language and text size rather than a test's, so those are checked on the phone.

## Quick and thorough UI runs
A normal run is quick: it leaves out the double checks. In 1.1 the style test classes (`TunerStylesTest`, `SettingsStylesTest`, `CompactLandscapeStylesTest`, `StringRowStylesTest`, `TourStylesTest` and others) ran in the default style only, all six styles only in a thorough run (`allIfThorough`, gone with the styles in Phase 67); `@Thorough` tests (variants of a quicker test in another font size, language, orientation or view) are skipped; `--thorough` runs everything. This cut the tuner suite from ~3 minutes to ~1. Each family keeps its hardest case in the quick run (e.g. Dutch at 2× font on a phone on its side), so most layout breaks still show at once. The thorough run belongs to the full check (`scripts/full-check.sh`, which passes `--thorough`), so daytime work never waits for it (owner, 2026-10-16: limited tests during normal work, the full suite and its fixes overnight). Thorough runs do find what quick runs miss: the first one (overnight 2026-10-15/16) found tests written while their runs were deferred, and the tour stuck on step 2.

## Real recordings
Every accuracy figure so far rests on synthetic sound, so Phase 46 records real plucked strings for the `:core:dsp` tests. The recorder is a test, never Twangle: `PluckRecorder` in `:core:testing`'s on-device tests (its test APK alone declares the microphone permission and depends on `:core:audio`; the app's merged manifest is unchanged), so the app still writes no audio anywhere (hard rule 7). It records through the tuner's own `AndroidAudioRecorder`, so the files hold what Twangle hears: the same input (unprocessed, else voice recognition; hard rule 5) at the same rate (48 kHz on the Xiaomi 12X).

`scripts/record-plucks.sh` runs it through `scripts/ui-tests.sh`, which holds the phone's lock (a UI test run and a recording never clash), keeps Xiaomi's app-op set, installs it with the microphone permission (`-g`) and pulls its output. Without the instrumentation argument `pluckPlan` the test is skipped, so UI test runs pay nothing. The phone guides the player, big enough to read from a chair: each step shows the string and how to play it (hard with a pick, softly with a finger, then with a pick in a noisy room) and waits for a tap on the screen; each pluck shows "Pluck now" in green once the microphone runs and records a fixed length (4 s by default, `--seconds`), never more and never in a loop. Its prompts also go out as instrumentation statuses (`pluck=`, code 2, which `ui-tests.sh` doesn't count as results), and the script prints them in the terminal as they come. Each take is written whole (under another name first) as a 16-bit mono WAV, `fmt ` and `data` first so the simplest reader finds the samples, then a `LIST`/`INFO` chunk whose `ICMT` names the phone, Android version, input and rate. The script moves them to `core/dsp/src/test/resources/fixtures/` as `guitar-<string>-<pick|finger|pick-noisy>-<n>.wav` and prints each file's length, rate, format and peak; the phone warns about a clipped or very quiet take. A whole session is 6 strings × (2 pick + 2 finger + 1 noisy) = 30 files of about 384 KB (about 11 MB). Stopped halfway (Ctrl+C stops the test on the phone, the one the script picked through `scripts/devices.sh` and handed to the run, so also with the watch connected; what was recorded comes to the PC), it carries on where it stopped: strings already in the fixtures folder are skipped (`--redo` records them again). `--test` records one 2 s file without a tap or playing, checks it arrived and deletes it: the end-to-end check of the recorder (2026-10-28 on the Xiaomi: 48000 Hz, `UNPROCESSED`, room noise peaking at −35 to −15 dB in two runs).

**The recordings (2026-10-29).** The owner's steel-string acoustic guitar, tuned first, the Xiaomi 12X on a table about 30 cm away: 30 files, `guitar-<E2|A2|D3|G3|B3|E4>-<pick|finger>-<1|2>.wav` (a quiet room, hard with a pick and softly with a finger) and `guitar-<string>-pick-noisy-1.wav` (a pick with a TV on across the room, 20–25 dB under the pluck's peak), 4.0 s each at 48 kHz, 12 MB in git. Each file starts with 50 ms of digital silence (the microphone opening) and a small bump at 0.3 s (the tap on the screen, 20 dB under the pluck), and the pluck starts 0.1–2 s in, so `RealPlucks.onsetOf` takes the onset from the signal: an attack is a rise of 12 dB or more in 10 ms to within 10 dB of the file's loudest 10 ms, the pluck is the attack that rings longest (until the level falls 25 dB under the attack's peak, or the file ends: a first try the player muted loses to the pluck after it, and in the noisy room, where nothing dies away, the first attack wins), and the onset is that attack's foot. Peaks −14 to −30 dBFS; the quiet room's floor 30–45 dB under the peak before the pluck. Ten takes were recorded again the same day: four quiet ones that held a muted first try and a second pluck, and the six noisy ones, whose TV had been within 3–8 dB of the pluck at the phone and drowned the string after half a second.

**The test and the report.** `RealPluckTest` runs every take through `TunerChain` at the file's rate and asserts: the session complete and as the recorder writes it (rate, length, the `ICMT` comment, an onset inside the file, a sane peak); on all 30 takes, its own note from the first reading and never another note in any frame (the octave flips to E5 that the picked high E showed 2.2 s in, its fundamental gone into the room's noise, and the G2, B2 and A2 the noisy takes showed as the strings sank into the TV, were the smoother's: [Signal pipeline](signal-pipeline.md), *Smoothing*); the first reading within 0.25 s of the pluck (measured 0.10–0.20) in the quiet room and 0.35 in the noisy one (0.11–0.16, the picked A 0.30); on the quiet takes, from 0.5 s to the settled reading (2 s in, or the last reading shown from 1.5 s) every reading within a per-string figure of it: 2 cents on the G and high E strings and the finger-plucked D, where the roadmap's figure holds, else the measured worst on this guitar plus a margin (the picked low E 4.4 → 5, the finger-plucked E 4.7 → 5.5, the picked A 6.5 → 7.5, the finger-plucked A 4.0 → 5, the picked D 3.5 → 4.5, the B 2.9 → 3.5), which is the string's own glide, not the detector (*Edge cases*, **A real guitar**, in the signal-pipeline doc); the needle settled, every later reading within 2 cents of the settled one (`RealPlucks.settleSeconds`), by a per-string time, the measured worst of the two takes plus a margin (a finger on the D, G or high E 0.13–0.24 → 0.25–0.35; a pick on the G or high E 0.4 → 0.5–0.55; the B 0.65 → 0.8; a picked D 0.93 → 1.1; the A and low E 1.05–1.6 → 1.25–1.8); and on the noisy takes, once the string is lost the needle stays blank, lost to the detector finding nothing rather than to another note. `RealPluckReport` (`./gradlew :core:dsp:benchmark --tests '*RealPluckReport*'`, 10 s) prints each take's trajectory at 0.1, 0.25, 0.5, 1, 1.5, 2 and 3 s after the onset, three rows a take (what the tuner shows; the string's own partial 1, the recording low-passed at 1.3 × the pitch and read by YIN; the chain without the refinement on the lowest partials), the first reading and when, when the needle settles, the settled reading, the roadmap's figure and the worst stray from 0.5 s, the frames showing another note and the frames the detector read a whole number of periods off (which the smoother held), for the noisy takes when the string was last shown and what the detector found after, and the frames after 0.5 s with nothing shown; then the real partials against the models (`Partials`, a Hann window of 8192 samples zero-padded eight times, each partial at the loudest bin near k × partial 1 with a parabola over the log magnitudes): each partial's level relative to partial 1 at 0.15 s and its drop by 1 s, the inharmonicity B and the series fundamental fitted through partials 3 and up, partial 1 beside it, and per string and touch the mean levels against 1/k or 1/k² and the mean B against the model's. What it found is in the signal-pipeline doc; the models' constants stay (every real B lies between the model's and three times it, which the tests run), and `EdgeCaseTest`'s stiff-string cases gained the weak-fundamental partials the real low strings have.
