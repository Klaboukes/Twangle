# Twangle — Architecture

Twangle is a chromatic and guitar-string tuner for Android. It listens to the microphone, finds the fundamental frequency of the note being played, and shows how far that note is from the target pitch, in cents.

This file holds the design decisions, the numbers that define behaviour and the reasons behind them. The code is the source of truth for everything else (exact geometry, colours, test lists). Keep it that way: when a decision changes, update the matching section here in the same change, and leave history to git and [ROADMAP-ARCHIVE.md](ROADMAP-ARCHIVE.md).

## 1. Tech stack

| Concern | Choice | Why |
|---|---|---|
| Language | **Kotlin 2.x** | First-class Android language, null safety, coroutines. |
| UI | **Jetpack Compose + Material 3** | A screen that redraws ~30–60×/s from one state object; custom drawing with `Canvas`. |
| Audio capture | **`android.media.AudioRecord`** (PCM float, mono) | Raw samples, no dependencies. A tuner tolerates ~50–100 ms latency, so Oboe/AAudio isn't needed. |
| Pitch detection | **YIN in pure Kotlin** (`:core:dsp`) | Sub-cent accuracy on monophonic signals, resistant to octave errors, unit-testable on the JVM. |
| Async | **Coroutines + Flow / StateFlow** | Audio frames → pitch → UI state is a stream. |
| State holder | **AndroidX ViewModel** | Survives configuration changes and owns the pipeline's lifetime. |
| DI | **Manual (`AppContainer`)** | The graph is tiny; Hilt would cost build time. Revisit if it grows. |
| Persistence | **DataStore (Preferences)** (`:core:settings`) | Saved settings (see §5). |
| Build | **Gradle 9 + AGP 9 (built-in Kotlin), Kotlin DSL + version catalog** | Versions live only in `gradle/libs.versions.toml`. |
| Testing | JUnit 4, kotlinx-coroutines-test, Compose UI test | DSP checked with synthesized signals (see §8). |
| CI | **GitHub Actions** (`.github/workflows/android.yml`) | test + lint + assembleDebug + unsigned assembleRelease/bundleRelease; debug APK uploaded as an artifact. |
| Min / target SDK | **26** (Android 8.0) / 37 | `ENCODING_PCM_FLOAT` and `UNPROCESSED` work from API 24+; 26 covers ~97 % of devices and needs no PNG icon fallbacks. |

### Name, app ID and icon
- **Name:** Twangle (InTune until October 2026, which clashed with Microsoft Intune). Names with "free" in them are out: Google Play bans price words in titles.
- **App ID:** `io.github.klaboukes.twangle`; packages and module namespaces live under it.
- **Launcher icon:** a dark-brown string on gold that comes in at an angle, makes one loop and leaves straight (tangled, then in tune). Adaptive icon (`res/drawable/ic_launcher_foreground.xml` + `ic_launcher_background`); the same foreground is the monochrome layer for themed icons. The artwork stays within 32.2 dp of the centre, inside the 33 dp safe zone, so no launcher mask clips it.
- **Opening screen:** `androidx.core:core-splashscreen` (`installSplashScreen()`, theme `Theme.Twangle.Starting`), so Android 8–11 look like 12+: the icon's string on a gold tile, on gold (light) or `#1C1510` (dark, `values-night`). It follows the phone's dark mode, because the app's theme setting isn't read yet, and stays up until the settings are read and the first frame is composed (`setKeepOnScreenCondition`).

### Rejected alternatives
- **Flutter / React Native:** microphone DSP through platform channels adds latency and complexity for a single-platform app.
- **C++/Oboe via NDK:** lower latency a tuner doesn't need. `PitchDetector` is an interface, so a native version could replace the Kotlin one. Phase 21 measured whether anything asks for it and decided no (2026-10-15): the Kotlin chain takes at most 13 % of a little core on a watch-like CPU, 3.5 % of a phone's big core with the low-note window, and strum check about 3 % (§4, *Watch CPU and the native detector*).
- **FFT peak picking:** fooled by strong harmonics (low E often has a weaker fundamental than its 2nd harmonic) and coarse at low frequencies. Time-domain YIN handles both.

Rules:
- `:core:dsp` is a plain `kotlin("jvm")` module and never imports `android.*`, so the most important code stays fast to test and portable.
- `:core:audio` knows Android audio, nothing about notes or UI (a tone is asked for in Hz). `:core:settings` knows how settings are saved, nothing about audio or UI.
- `:core:designsystem` holds everything both screens draw with (including the meter and wave art, so the settings previews draw exactly what the tuner draws), and nothing about audio.
- `:feature:*` modules never depend on each other, and `:wear` uses none of them. Only `:app` wires implementations together (`AppContainer`) and switches screens (`MainActivity`).
- `:baselineprofile` runs only on demand with a phone connected (§4). CI never runs it.

## 3. Signal pipeline

```
 Microphone
    │  AudioRecord.read()  (dedicated thread, 48 kHz mono float, blocking; built-in mic while a
    │                      Bluetooth headset is connected)
    ▼
 AudioRecorder ──Flow<FloatArray>(chunk = one hop ≈ 21 ms, 1024 samples at 48 kHz)──►
    ▼
 FrameAssembler        ring buffer → overlapping analysis window (≈ 85 ms, 4096 samples at 48 kHz;
                       ≈ 171 ms, 8192 samples, when the tuning goes below the guitar: see Low notes)
    ▼
 SignalGate            RMS level check (< ~-50 dBFS → "no signal"), DC offset removal
    ▼
 SustainCheck          newest hop vs the window's loudest (energy and peak): a tick that has
    │                  died away (> 12 dB down, or > 4 dB and back at the room) is not analysed
    ▼
 PitchDetector (YIN)   [upsample to ≥ 32 kHz if the rate is lower] → 4 kHz low-pass → difference fn
    │                  → CMNDF → absolute threshold → whole-period checks → above-range check
    │                  → least-squares refinement → PitchResult(frequencyHz, confidence), or NONE
    ▼
 NoiseFloorTracker     note-free frames' levels → median of 5 → minimum over 2 s = room's floor;
 + Clarity             with a pitch: SNR over that floor, clarity 0..1 from YIN's confidence
    ▼
 ReceptionTracker      level, SNR and clarity scored 0..1, each smoothed (fast up, slow down);
                       reception = the lowest of the three (needle and wave crisp ↔ faint)
    ▼
 PitchSmoother         Hz → fractional MIDI (NoteMapper.midiOf, honours A4) → onset: 3 agreeing
    │                  frames → octave-jump rejection → median of 5 → EMA (snaps on a new note,
    │                  smaller steps when unsure) → note with ±15-cent hysteresis; a passed
    │                  tick's frames neither start a note nor count as its dropout
    ▼
 NoteMapper / Tuning   note name + octave; in Auto mode → nearest string in tuning, cents from it
    ▼
 TunerViewModel        combine with settings → StateFlow<TunerUiState>
    ▼
 Compose UI            meter, note name, cents or wave, string row, in-tune indicator + haptic
```

### Key numbers
- **Sample rate:** 48 000 Hz, the native rate on most phones. `SampleRateSelector` uses `AudioManager.PROPERTY_OUTPUT_SAMPLE_RATE` if it is 44 100–48 000 Hz (higher only costs CPU), then tries 48 000, 44 100, 32 000, 16 000 and 8 000; the first rate `AudioRecord.getMinBufferSize` accepts is expected. If no input opens at it, `AndroidAudioRecorder` tries the other accepted rates in that order (`openFirst`: every input at a rate before the next rate) and its `config` moves to the rate that opened; the pipelines read the rate again with the first chunk. Any rate from 8 to 96 kHz works end to end (see *Other sample rates*).
- **Analysis window:** 4096 samples (≈ 85 ms), about 7 periods of low E (82.41 Hz); YIN needs at least 2. Tunings that go lower (7- and 8-string guitar, bass, cello) use **8192** (≈ 171 ms, see *Low notes*).
- **Hop:** 1024 samples (≈ 21 ms), ~47 estimates per second.
- **Detection range:** 62–1500 Hz for guitar (τ_max = sampleRate / f_min). The floor sits above 60 Hz mains hum and below drop C (65.4 Hz). With the low-note window: **28–1500 Hz**, so B0 (30.9 Hz) reads even a semitone flat.
- **YIN threshold:** 0.15 (the paper suggests 0.10–0.15).
- **Accuracy target:** ±1 cent on synthetic signals, ±3 cents on recorded guitar.
- **"In tune":** |cents| ≤ 5 held for 300 ms (15 hops at 48 kHz), released past 7 cents, so a note hovering at 5 doesn't flicker. That is **Relaxed**, the default; **Precise** is ≤ 2, released past 3 (§5, Settings). The shown "in tune" goes through the steady hint line (see *Audio capture*), so it also lasts at least 0.5 s.

### Other sample rates
`AnalysisSettings.forSampleRate(rate)` (8–96 kHz) scales window and hop so they always last ≈ 85 ms and ≈ 21 ms and the smoother's frame counts keep their meaning (44.1 kHz: 3763 / 941 samples). `PitchPipeline` builds its `FrameAssembler` and detector from it, and `AudioConfig.forSampleRate` makes the recorder's chunks one hop long. A rate outside 8–96 kHz ends the flow with `InitializationFailed`.

Below 32 kHz a period spans too few samples for ±1 cent, so `UpsamplingPitchDetector` first interpolates by an integer factor to ≥ 32 kHz (polyphase windowed-sinc FIR: Kaiser β = 8, 32 taps per phase, cut-off 0.45 × input rate), and YIN's low-pass drops to 0.4 × the input rate so no images get through. Measured: every rate from 8 to 96 kHz within 1 cent on sines, saws, plucks and weak fundamentals; 8 kHz costs 0.5 ms per frame on the JVM.

### Frame assembly
`FrameAssembler` keeps a ring buffer of `capacity` samples (4096 by default). `push()` takes chunks of any size and stops as soon as a frame is ready, so none is skipped; `readFrame(out, length)` copies the latest `length` samples (by default the 4096-sample window) oldest-first into a caller-owned array, and `skipFrame()` passes on a frame. First frame after one full window, then one per hop. `PitchPipeline` gives it a capacity of the low-note window (8192 at 48 kHz) so either window can be read at every hop; `available` says how much audio it holds since the mic opened. Allocated once.

### Low notes
Phase 15. `PitchRange` (`:core:dsp`) says how low the detector listens:
- **`STANDARD`:** 62–1500 Hz, 4096 samples. Every guitar tuning, ukulele, violin, viola, mandolin.
- **`LOW`:** 28–1500 Hz, **8192 samples** (`AnalysisSettings.forSampleRate(rate, PitchRange.LOW)`; ≈ 171 ms at any rate). 28 Hz is below B0 at −50 cents (30.0 Hz); τ_max = 1715 lags at 48 kHz, which with the filter's start-up and the fit's margin needs ≈ 8000 samples (W = 6276, ≈ 3.7 periods of the lowest note, like the standard window's 4). The hop stays 1024, so readings still come ~47 times a second and the smoother's frame counts keep their meaning.

`PitchRange.forLowestNote(hz)` picks `LOW` when the tuning's lowest string, **a semitone flat**, is below 62 Hz, at the current A4. So 7- and 8-string guitars, both basses and the cello (C2, 65.4 Hz: a semitone flat is 61.7 Hz) get `LOW`; no guitar preset does, even at A4 = 415 Hz (drop D's D2 at 69 Hz). `TunerOptions.pitchRange` works it out once per tuning or A4 change; `TunerViewModel` passes `{ options.pitchRange }` to `PitchPipeline.readings(range)`, which reads it every frame. The pipeline keeps a frame buffer and a detector for each range (made once per listening session, ≈ 200 KB for the low one) and one assembler holding the long window, so switching the tuning changes the window on the next hop without reopening the mic or losing audio. After the mic opens, low-range readings start once a whole long window has arrived (171 ms instead of 85). Chromatic mode follows the tuning too, so a bass player's chromatic mode also reads low.

The cost: twice the window, about 2.3× the CPU per frame (bigger FFT), and a reading that reflects audio ≈ 43 ms further back on average. Measured in §4 (*Low-note window on the Xiaomi 12X*).

**Measured (`LowPitchRangeTest`, 48 kHz):** sines 30–1500 Hz within 0.09 cents; sawtooth, square, pluck and weak fundamental within 0.52; every string of every low instrument within 1 cent from a semitone flat to 50 cents sharp, the right note even with a weak fundamental; 20 dB SNR within 0.33, 10 dB within 0.83; nothing below 28 Hz; 8, 16 and 44.1 kHz also within 1 cent; no allocation. *Known limit:* 50 and 60 Hz mains hum are inside the low range, so hum alone shows as a note (G1 / B♭1) and hum 10 dB below a B0 string pulls it up to 8 cents (≈ 2–3 cents from E1 up). A notch filter would fix it if real rooms need it.

### Signal gate
`SignalGate.process(frame)` first measures the **peak** as the mic delivered it (`peakDbfs`, to detect clipping), then removes the DC offset in place and measures the RMS level as `20 · log10(rms)` dBFS (full-scale square 0 dBFS, sine ≈ −3; silence floored at −120). It opens at **−50 dBFS** and closes below **−56 dBFS** (6 dB hysteresis), so a decaying note doesn't flicker. Only frames with the gate open reach the detector.

### Sustain check (ticks and clicks)
A tap on the desk, a clock's tick or a mouse click often rings at a pitch for a few milliseconds. YIN reads that ring, and it stays in the 85 ms window for four hops, so each tick used to show a note for ≈ 0.1 s (a 1–1.5 kHz ring sits nearest the high E string, far sharp: "the needle jumps to E4"). A string sustains; a tick dies away. `pitch/SustainCheck` cuts the window from its newest end into blocks of one hop, or one period of the lowest note where that is longer (the low range: 1715 samples, 36 ms, since a bass note's 32 ms cycle doesn't fit in a 21 ms hop and its energy per hop swings by up to 12 dB), and `dropDb` is how far the newest block is below the loudest. It measures both energy and peak and takes the larger drop: energy sees a 30 ms ping fade 12 dB within three hops; the peak sees a 2 ms tick louder than the string by its full height, where in energy it is only ≈ 6 dB. Every block holds a whole cycle, so a steady note reads ≈ 0 dB (up to 2.5 dB of energy on bass notes). The idea is energy-envelope onset detection (Bello et al. 2005) turned around: a pitch is only trusted while the envelope says the sound is still there.
A frame is **not sustained**, so it isn't analysed (`PitchReading.sustained` = false), when its sound had died away by its end:
- **more than 12 dB down** (`SustainCheck.DEFAULT_MAX_DROP_DB`): a loud tick has passed. A note that starts in the newest block is the loudest block, so new notes pass at once; on the phone a played E4 never dropped more than 1.8 dB across a window, a synthetic 24th-fret E fading fast about 7.
- **more than 4 dB down and the newest block within 6 dB of the room's background** (`ROOM_DROP_DB`, `ROOM_MARGIN_DB`, the floor from `NoiseFloorTracker`): a quiet tick has passed. A tick just above the room can't drop further than the room's level (6.6–8 dB on the phone, as little as that fast high note), but a note is still well above the room. Room noise alone varies by 1–2 dB, so it is sustained and ends a reading as usual.

While a note shows, a frame that isn't sustained doesn't count as a dropout (`PitchSmoother.noReading(sustained = false)`): a tick louder than the string hides it until the tick leaves the window. With the smoother's onset (*Smoothing*) a tick can't start a reading: it gives at most 2 analysed frames, and a new reading also needs frames loud enough to open the gate by themselves. On the phone the laptop speaker rang on at 1400 Hz for ≈ 70 ms after a tick, −48 to −55 dBFS: the gate stayed open on its hysteresis after the tick and three sustained frames read 1400 Hz, "E4 +25 semitones".

Measured (`EdgeCaseTest`, `SustainCheckTest`, 48 kHz): ticks (2 ms rings at 330 Hz–5 kHz, a knock, a clock tick, a digital click, a noise burst) and pings (the same rings lasting 8 or 30 ms), at peak −1 dBFS over a −70 or −55 dBFS room: **nothing shown**. Before, most rang at a pitch and showed for 5–36 frames per three of them. **On the Xiaomi 12X** (2026-10-15), 45 ticks of seven kinds from the laptop speaker: none shown; a played E4 shows on its third frame, on pitch. Ticks every 0.4 s over a ringing string, 12 dB quieter or 13 dB louder (peak): the reading is never lost and stays **within 0.26 cents**; ticks as loud as the string move it up to 3.5 cents for a frame or two. *Known limits:* a ping ringing 8–30 ms over a string is a pitched sound of its own (like a glass clink) and can pull the reading off, even onto its own note, for a moment, as before; and in the low range a ping ringing ≈ 30 ms fades too little within a 36 ms block, so on its own it may show briefly. Cost: under 0.01 ms per frame.

### Noise floor, SNR and clarity
How well the tuner hears the guitar. Every `PitchReading` carries these besides the level; *Reception* turns them into what the display shows.
- **Noise floor** (`level/NoiseFloorTracker`): the room's background in dBFS. Only frames without a pitch count, gate open or not. Their levels pass a running median of 5 (ignores a glitch), and the floor is the lowest of those over the last **2 s of note-free frames** (scaled with the hop by `AnalysisSettings.newNoiseFloorTracker()`). This is Martin's (2001) minimum statistics on one band, with a median in place of his recursive smoothing (which took ~0.6 s to follow a 20 dB drop). The floor drops within a few frames, rises only once a louder room lasts 2 s, and notes never move it. NaN until the first note-free frame; reads a little low on fluctuating noise.
- **SNR** while a note sounds: `10 · log10(10^((level − floor) / 10) − 1)`, the frame's power minus the background's (as in Boll's spectral subtraction), at least −20 dB; NaN without a pitch or floor. Measured within 1 dB from 0 to 40 dB SNR.
- **Clarity** (`pitch/Clarity`): 0..1 from YIN's confidence `c = 1 − d′(τ)`. `d′(τ)` is the aperiodic share of the power, so `10 · log10(c / (1 − c))` is a periodic-to-aperiodic ratio in dB, like Boersma's (1993) harmonics-to-noise ratio. It depends only on the noise, not pitch or timbre, and sits ≈ 7.8 dB above broadband SNR (YIN's low-pass removes most hiss). Mapped linearly from 7.5 dB (`d′` = 0.15: 0) to 20 dB (`d′` = 0.01: 1): 20 dB SNR or cleaner gives 1, 10 dB ≈ 0.8, 6 dB ≈ 0.5, 0 dB ≈ 0.

All allocation-free (byte-counting tests). **No meters** for these (owner's decision, 2026-10-12): they become one *reception* figure the display shows, tips only when the player can fix something, and optional signal bars behind a setting.

### Reception
`level/ReceptionTracker` (pure, counted in frames) turns each pitched frame's level, SNR and clarity into one steady 0..1 figure: 1 for a strong, clean note, towards 0 when it is quiet, sinks into the room or loses its period.
- **Scores:** level 0 at −50 dBFS to 1 from −35 dBFS; SNR 0 at 0 dB to 1 from 20 dB (unknown room counts as 1); clarity as is. Linear in dB.
- **Smoothing:** a one-pole filter per factor, 0.15 s towards better and 0.5 s towards worse, so a rough frame or two barely dims it. In a note's first 0.1 s a factor rises at once (the window still holds the silence before it). `reset()` (note gone) returns to 1.
- **The figure** is the lowest of the three; `limit` (`ReceptionLimit`: `NONE` from 0.95, else `LEVEL`, `NOISE`, `CLARITY`) names the one holding it down. The smoothed scores and a smoothed `levelDbfs` are public for the signal bars.

`TunerInterpreter` feeds one tracker every pitched frame and resets it when the reading is lost; `Detected.reception` carries it. On screen (`components/ReceptionLook.kt`) it changes **only opacity and sharpness**, never colour, shape or motion, which stay the tuning cue: at worst reception the needle layer and wave fade to 0.62 of their opacity with up to 2 dp blur (`BlurEffect`, 8 steps made once; Android 12+, older phones only fade). The effect scales with how far the picture is from its resting look, so resting looks unchanged, and `HeldReception` keeps the last value while a note fades out. Text never fades.

### Tips
`TipCue` (`ReceptionTip.kt`, pure, counted in frames) picks the `ReceptionTip` the sound asks for, with separate on and off limits so a level hovering at a limit can't flicker:
- **Too loud** ("Too loud, move the phone back"): peak reaches −0.5 dBFS (clipping), until it stays below −3 dBFS. A pluck that clips only in its attack is shorter than the tip's settle time. Comes first, because clipping distorts everything else.
- **Too soft** ("Play a bit louder"): the note's *loudest* level so far is below −44 dBFS, so a well-played note's fading tail never asks.
- **Too noisy** ("Too noisy here"): room background ≥ −38 dBFS, until below −42 dBFS (also between notes); or the note's best SNR stays below 8 dB. Too soft comes first, since playing louder also beats noise.
- A note's verdict holds 2.5 s after it ends, so a tip stays through the gap to the next pluck.

The wanted tip passes through its own `SteadyHint<ReceptionTip>` (not restarted per note): settles in 0.5 s (loud), 0.6 s (soft) or 1 s (noisy), stays at least **3 s**, then the line stays tip-free for 1 s. `Detected.tip` and `Listening.tip` carry it.

On screen (`NoteDisplay`) a tip **replaces something less needed, so nothing moves**: "Play a string" without a note, the direction in the wave's pill, or the frequency under the needle (so "Tune up/down" stays). One line, set smaller (down to 11 sp) when it doesn't fit; its line keeps the height of a full-size line (measured with a `TextMeasurer`), the shrunk text centred in it. Without that it came out a pixel taller at 1.25× text and pushed the note up: under Android 14's non-linear font scaling Compose keeps an sp line height in proportion to the font size, and a smaller font is enlarged by a larger factor. TalkBack: "E 2, 12 cents flat, Play a bit louder".

### Signal bars (optional)
Behind "Show signal bars" (off by default). Four bars in the free slot at the right end of the note's pill (mirroring the check mark), so they add and move nothing in any layout.
- **Count** (`SignalBars`, pure): reception lights bars 1–4 from 0.05, 0.35, 0.65 and 0.9, each going out 0.08 below its threshold. Without a note the last count stays, dimmed to 45 %.
- **Drawing** (`components/SignalBarsButton.kt`): a `Canvas` in the pill's text colour, unlit bars at 20 %; the count is a `derivedStateOf`, so only a changed count recomposes. Hosted in `movableContentOf`, so the count and an open panel survive layout changes.
- **Touch area:** the button around the bars is 48 × 48 dp, centred on their 24 dp slot and reported to the pill as the slot's size (`touchArea`), so it is easy to hit and moves nothing. To let it reach past the pill's edge, the pill's fill is clipped on a layer of its own behind the row instead of clipping the row. `SIGNAL_BARS` tags the button, `SIGNAL_BARS_ICON` the drawn bars (the layout tests' bounds).
- **Figures:** a tap (TalkBack "Signal bars: 3 of 4", action "show the figures") opens a small panel "How well Twangle hears you": volume, background and clarity. `TunerViewModel.signalFigures` updates them 4×/s, only while the setting is on.

### Pitch detection (YIN)
`YinPitchDetector` follows de Cheveigné & Kawahara (2002), steps 2–5, with `d(τ)` computed by FFT (`FftDifference`, §4) and two additions that synthetic measurements showed were needed for ±1 cent:
1. **Low-pass pre-filter:** 4th-order Butterworth at 4 kHz (two RBJ biquads), skipping its ~92-sample start-up transient. Without it very bright tones near 1.4 kHz give a V-shaped dip that parabolic interpolation misjudges by ~2.5 cents. Also removes hiss.
2. **Adaptive least-squares refinement:** a cubic fitted to raw `d` over the lags `τ ± k` within 5 % of the way from the dip to the mean (`k` ≤ τ/16). Sharp dips use k = 1 (the classic parabola); broad dips (low pure notes) average dozens of lags. At 20 dB SNR this cut the worst low-E error from ~23 cents to under 1; the cubic term removes a ~0.3-cent bias.

**Range edges and whole-period checks.** The first dip is followed to its minimum; if it is still falling at τ_max, the pitch is below 62 Hz and the frame has none (this keeps 60 Hz hum out). Two checks then catch a period off by a whole factor, on raw `d`, and a third drops tones above the range:
- *Too long (noise):* heavy noise inflates `d′` at short lags, so the first accepted dip can be 2–3 periods. If `d` at a local minimum near τ/k is at most 15 % above `d(τ)` (and `d′` < 0.5), τ/k is taken.
- *Too short (harmonics):* a note with a strong 2nd and weak odd harmonics nearly repeats every half period. If the dip floor at 2τ or 3τ is below a quarter of the floor at τ, that lag is the period. *Dip floors* are the minimum of `d` between whole lags, from the quartic through `d` at τ ± 2 (a parabola misjudged a sharp dip by up to 0.3 % of the mean of `d` at a low analysis rate; the quartic is within 0.02 %). A floor under 0.2 % of the mean of `d` is a tone that repeats at τ and is left alone. This used to compare raw `d` and skip every tone with `d′(τ)` < 0.05, so a G string heard through the phone, its fundamental and odd harmonics faint (0.5–2 % of the mean left at its half period), read G4 in every frame; a true G4 leaves under 0.2 % even at 20 dB SNR, and its floor at 2τ is as high (in noise) or barely lower.
- *Above the range:* a tone above 1500 Hz has no dip in range at its own period, but one at 2, 3 or 4 periods, so a 2 kHz whistle or a tick ringing at 3 or 5 kHz read as 1000, 1500 or 1250 Hz. After the two checks above, the frame has no pitch if the dip at τ_min is still falling towards shorter lags, or a dip of `d` below τ_min (from lag 4) divides τ a whole number of times and is about as deep. That is the *too long* test, on parabola-interpolated dip floors (a period of 10–30 lags falls well between whole lags, which alone makes `d` there several times `d(τ)` on a clean tone) plus 1 % of the mean of `d`. A note with a strong 2nd harmonic keeps its odd harmonics at the half period, ≥ 4 % of the mean of `d` in every test tone, so it still reads. Measured: sines and bright tones 1.6–5 kHz give nothing, also at 20 dB SNR; 1318–1500 Hz still within 1 cent.

Search range τ = 32…775 (1500…62 Hz) plus 50 lags for the fit; integration window `W = 4096 − 92 − 825 = 3179`. In the low-note range τ = 32…1715 (1500…28 Hz) plus 109 lags, `W = 8192 − 92 − 1824 = 6276`, FFT size 8192. Confidence = 1 − d′(τ). `PitchResult` is a value class packing two floats into a `Long`, with `PitchResult.NONE` instead of null, so it never boxes. Measured: ≈ 0.1 cent for sines, ≈ 0.5 for saw/square/pluck/weak fundamental, < 1 at 20 dB SNR, < 5 at 10 dB; no octave errors. `detect()` is allocation-free (byte-counting test).

### Smoothing
`PitchSmoother` works in fractional MIDI, so cents are ×100 and A4 is already applied:
0. **Onset:** without a reading, a new one starts only once **3 readings in a row** agree within 50 cents, each from a frame loud enough to open the gate by itself (≥ −50 dBFS; the gate's hysteresis keeps a fading note, it doesn't start one); a frame without a pitch, one too quiet, or one far from the last starts the count over. A tick gives at most 2 such frames (see *Sustain check*). The reading starts at the median of the three, so a new note shows ≈ 43 ms later than before (76 ms after the pluck instead of 33; 119 instead of 76 for the low strings, whose first frames have no pitch yet) and its first value is closer (worst 0.59 cents instead of 1.28 on a C6 pluck).
1. **Octave-jump rejection:** a reading a whole number of octaves (±30 cents) from the running median is dropped; if it holds 3 frames (~64 ms), the filters restart there.
2. **Median of 5** (~107 ms) removes other outliers.
3. **EMA, α = 0.3,** snapping when the median is > 50 cents away (a new string). Steps are weighted by confidence: 1 from 0.97 up, falling linearly to 0.2 at 0.88 and below. This roughly halves needle wobble in a noisy room and at the end of a decay without slowing clean notes.
4. **Note hysteresis:** the shown note changes only past 65 cents (50 + 15), so displayed cents can reach ±65.

`noReading()` keeps the last reading for up to 4 missed frames (~85 ms), then clears it; frames that aren't sustained (*Sustain check*) don't count. Allocation-free.

### Edge cases (measured, `EdgeCaseTest`)
What the user sees after the whole chain on synthetic signals:
- **White noise:** always the right note; worst error 0.8 cents at 10 dB SNR, 1.7 at 6, 2.5 at 3, ≈ 10 at 0 dB (low notes; high notes stay under 2).
- **Mains hum 10 dB below the string:** within 3 cents; hum alone shows nothing. *Known limit:* hum within ~6 dB of the string can lock YIN onto a shared period or hide low strings. A notch filter would fix it if real rooms need it.
- **Ticks, knocks and clicks:** alone, never shown; over a ringing string, within 0.26 cents (see *Sustain check*).
- **High strings with strong 2nd/3rd harmonics** (B3–C6): within 1 cent, no octave flips while decaying.
- **Sustain decay:** stays within 1 cent until the gate closes (once); over −60 dBFS room noise the last frames wobble up to 6 cents, never another note.
- **Bluetooth-like audio** (300–3400 Hz or 100–7000 Hz band, native 8 or 16 kHz): within 1 cent.

### Note math
```
midi  = 69 + 12 · log2(f / A4)        (A4 default 440 Hz, configurable 415–466)
note  = ceil(midi − 0.5)               (round half down, so exactly half-way reads +50)
cents = 100 · (midi − note)            range (−50, +50]
```
Scientific pitch notation (MIDI 60 = C4). `Note` is a value class over the MIDI number. `Notation` (`SHARPS`, `FLATS`, `SOLFEGE`, `GERMAN`) names a pitch class with real ♯ and ♭ (C♯ / D♭ / Do♯; fixed-do, B is Si); each entry holds its names in both spellings so `nameOf()` returns the same instances every frame. `GERMAN` calls B "H" and B♭ "B" (Half step down reads E♭ A♭ D♭ G♭ B E♭); its other black keys keep the signs (C♯, E♭), as German players write them even though they say Cis and Es, so only the B/H letters differ from `SHARPS`/`FLATS`.

**Notation by language.** The notation is a default that follows the app's language until the player picks one. `Notation.forLanguage(language)` (`:core:dsp`, JVM-tested) gives `GERMAN` for `de`/`pl`/`ru` (Polish and Russian players write H for B too), `SOLFEGE` for `fr`/`it`/`es`/`pt`/`tr`/`ar` (Turkish and Arab players learn Do Re Mi; Arabic shows the Latin syllables, like every note name, and TalkBack says them in Arabic script), and `SHARPS` for every other language (a new language with its own habit is one line there; owner's rule: what is most common in that country). The saved setting is `AppSettings.notationChoice: Notation?`: null (no saved key) means Automatic, so existing installs that never touched the setting simply get their language's default, and an explicit pick, including the one that equals the default, sticks across language changes. `AppSettings.notationFor(language)` resolves it. The language comes from the screen's configuration (`appLanguage()` in `:core:designsystem`, `LocalConfiguration.locales[0].language`, which follows the per-app language): `TunerViewModel` takes it at creation (so the first frame is right) and the screen passes changes with `setLanguage`; the tuning editor and Settings read it directly. Settings lists Automatic first, labelled with a sample of what it gives ("Automatic: C, C♯, D … B", "Automatique : Do, Do♯, Re … Si", "Automatisch: C, C♯, D … H"; built from `settings_notation_sample`, B's name last because that's where the notations differ); choosing it clears the key. The watch has no notation setting and follows its own locale (`WatchNoteName.letter`), drawing a solfège syllable smaller (`sizeFor`) so "Sol♯4" fits the ring. The home-screen widget shows no note names.

**Tuning spelling.** A preset is written the way players write it, and that wins over the sharps/flats setting: Half step down is E♭ A♭ D♭ G♭ B♭ E♭, Open D keeps F♯. `Tuning.spelling` comes from how the preset is written in `Tunings` (`"Eb2"` flats, `"F#3"` sharps; mixing is refused), and `Notation.nameIn(tuning, …)` applies it in the string row, tuning menu, hint and big note in guitar mode. Chromatic mode follows the setting alone.

**Auto (guitar) mode** targets the closest string of the tuning, in cents; **Chromatic** the nearest equal-tempered note.

### Tunings
`Tuning(id, strings)` lists open-string `Note`s lowest first; `id` is the saved key (never rename). Names live in string resources, so `:core:dsp` has no UI text. `Tunings` holds the presets (Standard, Drop D, Half-step down, Full-step down, DADGAD, Open G, Open D, Open E), `DEFAULT` = Standard, `byId()` to restore.
- `nearestStringIndex(midi)` follows A4 calibration; smallest |Δ| in semitones, ties to the lower string, no allocation.
- `centsFromString(midi, index)` is **not** wrapped to ±50, so a string far off shows the full distance.
- Strings are in instrument order, thickest first. That is lowest pitch first except on re-entrant tunings (standard ukulele G4 C4 E4 A4), so `lowestNote` / `highestNote` scan all strings.

### Strobe model
`StrobeMotion` (`strobe/`) is the drift of a strobe pattern, one animation frame at a time; every wave look runs one (via `WaveMotion`). A mechanical strobe drifts at the beat rate in Hz, so high strings move faster; here the drift comes from cents, so every string looks the same. `driftSpeed(cents)` in stripe periods per second: **0 within ±0.5 cent** (finer than the ±1 cent target, so an in-tune string stands perfectly still), then **0.4/s per cent beyond**, up to **4/s** from 10.5 cents; positive when sharp. It ignores the in-tune flag (2–5 cents wide) because the strobe exists to show the last cent. `advance(seconds, cents)` eases the shown cents towards the reading (rate 20/s) and moves `phase` (0..1, wrapping); a step is capped at 0.1 s. Without a reading the view stops calling it and the pattern freezes. Tests feed sines 0, ±1, ±3, ±5 and ±30 cents off every string through `TunerChain`.

### Audio source selection
1. `MediaRecorder.AudioSource.UNPROCESSED` if `PROPERTY_SUPPORT_AUDIO_SOURCE_UNPROCESSED` is `"true"`.
2. Otherwise `VOICE_RECOGNITION`, which must have AGC and noise suppression off.
3. Never `MIC` or `VOICE_COMMUNICATION`: their AGC and noise suppression distort pitch and level.

`AudioSourceSelector.candidates()` returns these in order; `AndroidAudioRecorder` opens the first whose `AudioRecord` initializes, so a failed `UNPROCESSED` still falls back.

**Bluetooth headsets.** A headset mic only records over SCO/HFP or LE Audio: 8 or 16 kHz, band-limited, often noise-suppressed. Twangle never asks for that route, and in case something else opened it, `InputDeviceSelector` pins the built-in mic with `setPreferredDevice` whenever a Bluetooth input is present. Wired headsets and USB interfaces keep normal routing. Without a built-in mic routing is left to Android; low-rate audio is still handled. *Not yet verified with a real headset* (owner check).

### Audio capture
`AudioRecorder.chunks()` is a cold `Flow<FloatArray>`: the mic opens when collection starts and is released when it stops. `AndroidAudioRecorder` reads one-hop chunks with `READ_BLOCKING` on its own single-thread dispatcher (buffer ≥ 4 chunks). To avoid ~47 arrays a second it fills a **pool of 4 arrays** behind a channel of capacity 2, so **a chunk is only valid until the collector takes the next one**: downstream code copies samples out inside `collect` and must not `buffer()` the chunks.

`PitchPipeline` (`:feature:tuner`, since it joins audio and DSP) collects the chunks into a `FrameAssembler` and runs gate, detector, `NoiseFloorTracker` and `Clarity` on `Dispatchers.Default`, emitting one `PitchReading(frequencyHz, confidence, levelDbfs, gateOpen, noiseFloorDbfs, snrDb, clarity)` (plus peak) per hop. The window follows the tuning (`readings(range)`, see *Low notes*). DSP objects are created once per collection; only the small reading is new each frame.

`TunerViewModel` creates a `TunerInterpreter` per listening session, which feeds `PitchSmoother` and turns the smoothed MIDI into a `TunerUiState`, on the same coroutine as the detector. Mode and saved settings are combined into one immutable `TunerOptions` (mode, tuning, A4, locked string, notation, precision), rebuilt only on change. Listening waits until settings have loaded. Changes take effect on the next frame without reopening the mic; only a new A4 restarts the smoother.
- **Chromatic:** the smoother's note and cents.
- **Auto:** the closest string and `centsFromString`. The target is sticky: it changes only once another string is closer by more than 15 cents. A reading within 50 cents of an octave above or below the string being tuned, with no string within 50 cents of it, stays on that string, moved by the octave (same cents). As a G3 fades, its faint odd harmonics sink into the room's noise and no single frame can tell it from G4 any more; nearest to no string, it used to jump to high E at +300 cents. A 12th-fret harmonic reads as its string this way too. Only the string already tracked is kept (from scratch an octave reads as before), and only one octave away, so in open D plucking D3 after D2 is the D3 string. A locked string takes an octave of itself the same way.
- **Auto, string locked:** tapping a string locks the target to it (`toggleString`, `TunerOptions.lockedString`); tapping again unlocks. Kept in memory only, survives a mode switch, released when the tuning changes.
- The frequency shown is the smoothed one (`NoteMapper.frequencyOf(smoother.midi)`).
- `InTuneDetector` (`:core:dsp`, `smoothing`, shared with the watch) decides "in tune" from smoothed cents and frame duration, and restarts when the note stops or the target changes. The phone's precision setting picks its window through `InTuneDetector.forPrecision` (an extension in `:feature:tuner`, since `:core:dsp` knows no settings).
- **Steady hint line** (the owner saw "Tune up/down" flicker near the note). Two pure layers, counted in frames:
  - `TuningCue` (`TunerHint.kt`) picks the *wanted* hint: `IN_TUNE` while `InTuneDetector` says so, else up or down from the rounded cents. Inside the in-tune window the previous direction is kept, so a wobbling reading doesn't swap; a note starting inside it shows no direction.
  - `SteadyHint<T : SteadyMessage>` adds timing: a message shows once wanted for its `settleSeconds` without a break and stays at least its `minShowSeconds`; an empty line after a message also stays 0.5 s. After a reset the first message shows at once. `IN_TUNE` settles at once (the detector already held 300 ms), `TUNE_UP` / `TUNE_DOWN` after 0.2 s; each stays ≥ 0.5 s.
  - `Detected.inTune = hint == IN_TUNE`, so colour, check mark, haptic tick, glow, TalkBack and hint always agree. Tips use a second `SteadyHint` (see *Tips*).

Failures end the flow with a typed `AudioRecorderException`, mapped by `toTunerError()` to a `TunerError` that the UI shows with a "Try again" button:
- `PermissionMissing` → `MIC_PERMISSION_MISSING`.
- `InitializationFailed` (no input opens at the rate) → `MIC_UNAVAILABLE`.
- `MicrophoneBusy` → `MIC_BUSY`. Before Android 10 `startRecording()` fails. From 10 the mic is shared and an app with priority (a call, an assistant, another recorder in front) silences us with zeros instead, at the start or mid-session. `ChunkReader` (pure, behind a `MicInput`, so JVM-tested with a fake mic) ends the flow with `MicrophoneBusy` when (a) the recording is silenced: `isClientSilenced` right after `startRecording()`, then an `AudioRecordingCallback` (Android 10+, registered only while recording) that sets a volatile flag the read loop checks per chunk, or (b) **2 s of exact zeros** arrive: a muted or blocked mic (the privacy switch, another app muting it) delivers digital silence, while a working mic always has some noise, even in a quiet room. Without this the tuner said "Play a note" forever.
- `ReadFailed(code)` (e.g. `ERROR_DEAD_OBJECT` when the audio server restarts) → `MIC_STOPPED`; collecting again reopens the mic. Reads that keep returning nothing (50 in a row, 5 ms apart: ≈ 0.25 s) are `ReadFailed(0)` instead of a loop that spins forever. The players' `AudioTrack` writes use the same loop (`transferFully`): 50 empty writes in a row end their session quietly.

**Measured on the Galaxy S26 (Android 16):** no `UNPROCESSED`, so `VOICE_RECOGNITION` at 48 kHz with no effects attached; a 440 Hz tone read 439.98 Hz (−0.1 cents) at −31 dBFS; quiet room noise −52 to −56 dBFS, right at the gate.

### Reference tone
Phase 17: the app can play a string's note so it can be tuned by ear. `TonePlayer` (`:core:audio`) has `play(frequencyHz)`, `stop()` and `isPlaying: StateFlow<Boolean>`; the caller turns the note into Hz with its `NoteMapper`, so the tone follows the A4 calibration.
- **Sound:** `PluckSynth` (`:core:dsp`, pure) adds up harmonics of an ideal plucked string (Fletcher & Rossing, ch. 2): harmonic k starts at 1/k and decays exponentially with time constant 1.5 s / (1 + (k − 1)/2), so the tone starts bright and mellows like a string. Harmonics stop below 6 kHz and 0.45 × the rate (at most 32), so low notes keep enough harmonics to be heard on a phone speaker that can't play their fundamental. Each harmonic is a decaying phasor turned by a fixed complex step per sample: exact pitch, no tables, no allocation.
- **Length and envelope:** 4 s from pluck to silence: a 5 ms raised-cosine attack (harmonics at 1/k starting together would jump like a sawtooth), then a 0.6 s raised-cosine fade that ends on exactly 0. `release()` fades out over 30 ms from the current level; a new note releases the old one first. The level is scaled so the sum of all harmonic amplitudes is 0.8 (about −2 dBFS), so it can never clip.
- **Playback:** `AndroidTonePlayer` streams `ENCODING_PCM_FLOAT` mono at the phone's native output rate through an `AudioTrack` with `USAGE_MEDIA` / `CONTENT_TYPE_MUSIC`, so the media volume sets its loudness. The track exists only while a tone sounds. `AudioTrack.write` blocks, so a session runs on its own single-thread dispatcher and renders 10 ms chunks into one buffer (buffer ≥ 4 chunks); `play` and `stop` only set a request field under a lock and return. At the end the session pads one buffer of silence (a very short tone otherwise might never start), waits for the playback head to pass the last sample, releases the track, and only then `isPlaying` turns false. It turns true on `play`. A track that fails ends the session quietly (logged).
- **Playing a string** (`TunerViewModel.playString`): a long-press on a string button plays that string of the current tuning at the current A4 (`NoteMapper(a4Hz).frequencyOf(note)`); a long-press on another string while one sounds switches to it. `soundingString` is the played string while `isPlaying`, else null. A tap on *any* string while a tone sounds only stops it (`toggleString` → `stopTone`): the lock stays as it was, so stopping the sound never changes what the tuner listens for, and the next tap locks as before. A new tuning, a switch to chromatic mode (no strings to show), the tuner leaving the screen (`ON_STOP`, or another screen taking its place) and `onCleared` all stop the tone too. A long-press gives Android's own long-press haptic (`combinedClickable`).
- **The mic ignores the tone:** the microphone stays open (hard rule 4 is unchanged: no reopening, no privacy-indicator flicker), but while `isPlaying` and for `TONE_TAIL_SECONDS` = 0.3 s after (counted in frames, for the room's echo) `listen()` sets the readings aside and emits the listening state; when the tail ends it starts a fresh `TunerInterpreter`, so no smoothing, hint or reception of the tone carries over.
- **Sounding string:** rings in the style's accent (`primary`) and the button's own shape grow out of it and fade, two at a time like sound waves, every 1.2 s (`soundingRings`, `StringSelector.kt`); drawn outside the clip in the draw phase, so nothing moves (`aSoundingStringMovesNothing`). With Android's animations off: one still ring. TalkBack: the long-press is the named action "Play A 2" (double-tap and hold, or the actions menu); the sounding string's state is "Playing" ("Locked, playing"), and every string's tap action reads "Stop the tone" while one sounds. In Dutch: "a 2 laten horen", "Klinkt", "Toon stoppen" (`dutchTalkBackCanPlayAStringAndHearsItSound`). `SoundingRingsTest` pictures the row on each style's background, light and dark, with and without a sounding string: the rings clearly show round that button in all six styles and change nothing elsewhere.
- **"Playing D3":** while a string's tone sounds, the tuner's hint line (where "Play a string" stands; the state is `Listening` then, since the mic is set aside) says "Playing D3" (`tuner_hint_playing`, NL "D3 klinkt"), the string named in the player's notation like the locked-string hint, and TalkBack hears "Playing D 3" through the note block's polite live region. It takes a reception tip's place for as long as the tone sounds, and goes back to "Play a string" (or "Play the A2 string") when the tone ends or is stopped (a few seconds: no flicker). The tour's strings step says how: "Tap to lock, hold to hear" (*Tour*, below). Tests: `aSoundingToneIsNamedInTheHintUntilItStops`, `aSoundingToneIsNamedInThePlayersNotation`, `aSoundingToneTakesATipsPlace` (`TunerContentTest`).
- **Audio focus:** each session asks for `AUDIOFOCUS_GAIN_TRANSIENT` (not `…_MAY_DUCK`: tuning by ear needs the tone alone, so another app's music pauses, and resumes when the session gives focus back as it ends). A loss (`LOSS`, `LOSS_TRANSIENT`: a call, another app that won't share) stops the tone like `stop()`; a loss that may duck (a notification) is left to Android, which lowers the tone by itself. Refused focus (during a call) means no tone: the session ends at once, quietly.
- **Volume:** the tone plays at the media volume. While the tuner is shown (`MainActivity`, a `DisposableEffect` in the tuner's branch) `volumeControlStream = STREAM_MUSIC`, so the volume keys set the tone's loudness even between tones; on Settings, About and the tuning editor the keys do what they do elsewhere. Only on the tuner, because only it makes sound. At media volume 0 a session shows the phone's own volume panel (`adjustStreamVolume(ADJUST_SAME, FLAG_SHOW_UI)`, the level unchanged), so a silent tone explains itself without a message of ours.
- **Measured on the Xiaomi 12X:** a long-press starts a `USAGE_MEDIA` float `AudioTrack` at 48 kHz (`dumpsys audio`), the tuner showed "Play a string" throughout (since Phase 26 "Playing A2"), the track is gone about 4.3 s later, within 0.5 s of a stopping tap, and within a second of pressing Home.
- **Measured on the Xiaomi 12X (focus and volume):** a long-press holds `GAIN_TRANSIENT` focus with `USAGE_MEDIA` (`dumpsys audio`, focus stack) and gives it back when the tone ends; the volume keys reach `STREAM_MUSIC` on the tuner and the phone's default stream in Settings (`adjustSuggestedStreamVolume`); at media volume 0 MIUI's volume panel opens on the long-press. `VolumeKeysTest` checks the tuner's stream on the phone; Settings isn't, since the ever-moving tuner keeps a Compose test rule from going idle.
- **Measured:** every preset string of every instrument, at A4 = 415, 432, 440 and 466 Hz, reads within 1 cent with the app's YIN (`PluckSynthTest`), also 3 s into the tone and at 44.1 kHz.

### Strum check (polyphonic)
Phase 18. Three parts in `:core:dsp` `strum/`, all allocation-free (byte-counting tests), used by the strum check view (§6, *Strum check view*):
- **`StrumListener`** turns mic chunks into frames timed from each strum (below, *Timing*).
- **`StrumDetector`** reads every string of one strum from one frame, given the frequencies to expect: the tuning's open strings at the current A4, for any instrument up to 8 strings, in any order. `detect(frame, expectedHz, count, result)` fills a `StrumResult` per string: Hz, cents from the expected note, level in dB below the loudest string, `present` and `shadowed`.
- **`StrumVerdict.of(result, string, toleranceCents, previous)`** turns a reading into `NOT_HEARD`, `FLAT`, `IN_TUNE` or `SHARP` (below, *Verdict*).

**Method.** A Hann window over the frame, a 2× zero-padded FFT, then five steps per string, steps 2–5 repeated 4 times because each string's result depends on the others':
1. **Coarse search:** weighted harmonic summation (Hermes 1988; Klapuri 2006), `Σ_k |X(k·f)| / k` over the first 8 harmonics, on a 1-cent grid ±100 cents around the expected note. Searching near the expected strings keeps the other fundamentals out. The 1/k weight was needed: unweighted, A2 at −22 cents locked onto E4's fundamental landing on its 3rd harmonic.
2. **Partial peaks:** each harmonic of the estimate is followed to its peak within half a main lobe; quadratic interpolation of the log magnitude (Smith & Serra 1987) gives its frequency and amplitude. A peak further off belongs to another string. **Joint fit** (`PartialFit`): when other heard strings' partials lie ½ to 3 main-lobe half-widths away (2.9–17.6 Hz at 341 ms), close enough to bend the peak but far enough apart to tell, the partial is fitted together with them instead. The complex spectrum around it is modelled as Hann-windowed sinusoids at the others' known frequencies plus ours; the amplitudes come from linear least squares and a golden-section search finds our frequency with the smallest residual (nonlinear least squares with all frequencies but one known; Stoica & Moses 2005, §4.3). The window's exact transform comes from the Dirichlet kernel, its angles stepped by rotation from bin to bin. Partials closer than half a lobe (1/T, 2.9 Hz at 341 ms) can't be told apart and stay one merged peak; fitting them too (tried down to a tenth of a lobe) only added errors. If the fit finds nothing between the others, the plain peak is used.
3. **Isolation:** each partial gets weight 0 within one main-lobe half-width (2 bins of the unpadded FFT: 5.9 Hz at 341 ms) of another heard string's partial, 1 from two. The joint fit could allow closer, but these weights gave the best clear strings.
4. **Estimate:** the mean of `f_k / k` weighted by power × isolation (power favours the low partials, which inharmonicity bends least). A string with no clear partial is **shadowed** and reads its lowest partial as it is: the other string's partial there is one of its own higher, weaker harmonics.
5. **Presence**, judged on the first two partials: a clear partial counts with its amplitude, a shadowed one with what is left after the other strings' expected share of the partials merged with it (their nearest clear partial, falling as 1/j), and not at all when the other string's harmonic number is ≤ ours (else a missing string's search settles where its upper harmonics hit other fundamentals). Partials fitted apart in step 2 are already out of its amplitude, so they don't count in that share. Heard: within 25 dB of the loudest string (a Hann window's highest sidelobe is −31 dB, so a sidelobe never counts) and above −74 dBFS.

**Overlapping harmonics are the core problem.** Equal temperament puts many partials of different strings within 2 cents. In standard tuning B3 ≈ 3 × E2 (1.96 cents apart), E4 = 4 × E2 and ≈ 3 × A2, A2's 4th ≈ D3's 3rd, D3's 4th ≈ G3's 3rd. Telling apart two partials 2 cents apart at 247 Hz (0.3 Hz) would take a window of seconds. So:
- **B3 and E4 are shadowed** in standard tuning: every partial of theirs sits on one of E2's. They read the merged peak, pulled towards E2's harmonic by its share: in tune +0.4 to 0.6 cents (part of the 2-cent gap). A lower string's partial within half a lobe is merged too and pulls them by up to 2.3 cents at 341 ms (0.5 at 683 ms): A2 10 cents flat puts its 3rd harmonic 0.33 lobe from E4. From half a lobe on, the joint fit separates it. A detuned string itself separates: 20 cents is 2.9 Hz at 247 Hz but 11 Hz at its 4th harmonic.
- **Octave strings** (drop D, DADGAD, open D, open G: D2 D3 D4, A2 A3, G2 G3) are shadowed the same way. An octave pair detuned against each other (A2 −20, A3 +15 in DADGAD) read 7.3 cents off at 341 ms in the research spike: A3's fundamental sat 0.75 lobe from A2's 2nd harmonic. The joint fit brings it to **0.44**.
- **Uneven octave strings** (found in this phase; the spike's detector did the same): when the upper string of an octave pair is within half a lobe of the lower one's harmonic (35 cents at 147 Hz, D3 over D2) and clearly softer, the merged peak is mostly the lower string's harmonic, and the reading lands between the two. In drop D, with every string random within ±30 cents and struck at 0.3–1 of full strength, D3 read up to 18.6 cents off (rms 3.2) while the other strings stayed within 0.2 (E4 3.6). The 683 ms frame halves that (10.2) but loses more strings; masking the lower string's partials and searching again didn't help. The phone check with a real guitar (Phase 18's last item) will show how much it matters in real strums. `shadowed` marks these readings.
- **Unison strings** (one note on two strings, as on a 12-string's unison pairs or in a custom tuning; Phase 26) have every partial in common, so no frame tells them apart. `StrumDetector` reads them as one course (expected frequencies within 1 cent) and gives both strings the course's reading: both show the pair's pitch, and a pair with one string left out still reads as heard. Before, each knocked the other out in every other refine pass, so they were heard only because the pass count is even. `StrumDetectorTest`: a G3 pair in tune, +15 and −20 cents, one of it left out, and an E4 pair listed first and last.
- **A missing shadowed string** is filled in by the lower string's partials, and coinciding partials add with unknown phases (anywhere from the difference to the sum of their amplitudes). The 1/j share catches a missing B3 or E4 in synthetic strums, but a missing D4 in DADGAD or open D reads as heard, and real guitars' harmonics don't fall as 1/j. Counting less of the share (tried 0.4–0.8 of it) or the merged amplitude as the share both made things worse. In DADGAD, open D and open G with uneven strums, 16–23 of 600 present strings read as missing (43–44 with the spike's detector) and 7–12 of 100 missing strings as heard (3–6).

**Frame and latency.** Accuracy comes from resolving partials: a Hann main lobe is 2/T wide each side (11.7 Hz at 171 ms, 5.9 at 341, 2.9 at 683). Default **16 384 samples (341 ms, four tuner windows)**; `frameLengthFor(rate, PitchRange.LOW)` doubles it for instruments below the guitar, like the tuner's window. 171 ms is too short for the shadowed strings.

**Timing** (`StrumListener(sampleRate, range)`). Mic chunks go in through `push` (like `FrameAssembler`, it stops as soon as a frame is ready) and are checked one tuner hop (1024 samples, 21 ms) at a time. A **strum** is a hop at or above −50 dBFS (the tuner's gate) and 8 dB louder than the quietest of the 6 hops before it (130 ms), at least 150 ms after the last strum (a strum's strings start up to ≈ 0.1 s apart). The first hop after construction or `reset` only sets that history to its own level, so whatever already sounds when listening starts (strings still ringing when strum check is switched on, a steady note, a fan) is never taken for a strum. The first frame comes once 50 ms of attack and a whole frame have arrived after the hop the strum was noticed in: it starts 50–93 ms after the strum and is ready **0.39–0.44 s after it** (0.73–0.78 s for `PitchRange.LOW`). If that first frame (its RMS, `frameLevelDbfs`) is under the gate (`MIN_FIRST_FRAME_DBFS`, −50 dBFS), the strum is not read at all: on the phone, the click of a sound stopping at once and a dying strum's beating near the gate were taken for strums, and their one faint reading replaced a good one. Then a new frame every **0.1 s** while the strings ring, until the level falls 6 dB below the gate. A new strum, also over a ringing one, starts over. `readFrame(out)` copies the frame out; `strumCount`, `readingsSinceStrum`, `samplesSinceStrum` (a `Long`: as an `Int` it overflowed 12.4 hours after a strum at 48 kHz, and no strum counted after that; Phase 26), `isRinging`, `levelDbfs` and `frameLevelDbfs` (the frame's level, which weighs readings, §6 *Strum check view*) tell the view where it is. The `FrameAssembler` inside holds one frame, and its new `copyLatest(out, length)` reads it at any hop without taking the hop's own frame. `StrumListenerTest`: no frame from room noise alone, nor from a sound already there when listening starts, the frame's start and readiness, a frame every 0.1 s while ringing and none after, a re-strum 10 dB over a ringing one, a click over strings dying away noticed but not read, a soft strum 3 dB over the first frame's limit read, any chunk size, chunks through to verdicts, a strum still noticed 13 hours after the last.

**Verdict** (`StrumVerdict`). In tune within the tolerance, 5 cents by default (the tuner's Relaxed; pass 2 for Precise), else flat or sharp; not heard when the string isn't present. A shadowed string gets 2.5 cents more (the merge's measured pull with equal strings), so it is only called out of tune when the merge alone can't explain it. A string that was in tune in the previous reading of the same strum stays so 1 cent further, so readings every 0.1 s don't flicker at the edge (like the tuner's 5 / 7). A string more than 100 cents off reads at the edge of its search, which still gives the right direction, or as not heard.

**CPU.** One detection: JVM 2.6 ms (341 ms frame) / 4.4 ms (683 ms). Xiaomi 12X (`scripts/dsp-phone-benchmark.sh`): **2.6 / 5.3 ms** (1.9 / 4.2 before the joint fit). At a reading every 0.1 s that is about 3 % of a big core while the strings ring, so Phase 21's native detector isn't needed for this. Most of it is the 32 768-point FFT and the fits.

### Metronome
Phase 19 (finished 2026-10-14). The engine, the screen (§6, *Metronome screen*) and the navigation bar (§6, *Navigation bar*).
- **Meters** (`Meter`, `:core:dsp` `metronome/`): 2/4, 3/4, 4/4, 5/4, 6/8 and 7/8. One click per beat of the bar, and the tempo counts clicks, so in 6/8 and 7/8 it counts eighth notes (as most practice metronomes do). Beat 1 is the accent (`BeatAccent.DOWNBEAT`); the start of each later beat group gets a middle accent (`GROUP`): 5/4 as 3 + 2 (beat 4), 6/8 as 3 + 3 (beat 4), 7/8 as 2 + 2 + 3 (beats 3 and 5), the most common groupings. The other beats are `PLAIN`.
- **Clicks** (`ClickSounds`): a 40 ms wood-block "tock", two decaying modes of a struck free bar at 1 : 2.756 (Fletcher & Rossing §2.15), the upper one decaying twice as fast, with a 0.8 ms raised-cosine attack and an 8 ms fade that ends on exactly 0. The accent is told apart by pitch and level: downbeat A6 (1760 Hz) at peak 0.8 (never clips), group E6 at 0.6, plain A5 at 0.45. Rendered once per sample rate, so playing a click is a copy.
- **Sample-exact timing** (`ClickTrack`): beat n starts on sample `A + round((n − a) · 60 · rate / bpm)`, worked out in integer arithmetic from the beat a and sample A where the tempo was last set, never by adding up rounded intervals. Each beat is within half a sample of its ideal time and the error never builds up (`ClickTrackTest`: every beat of ten minutes at 97 BPM / 44.1 kHz, 233 BPM / 48 kHz and 31 BPM / 16 kHz, whatever the chunk size). The tempo is an integer, clamped to 30–250 BPM, so beats are ≥ 0.24 s apart and clicks never overlap.
- **Changes while playing** take effect from the next beat: a new tempo puts it one new interval after the last beat (or at once if that moment has passed), and the tempo counts on from there; a new meter makes it a downbeat without moving it. `render` and the setters allocate nothing (byte-counting test).
- **Playback** (`MetronomePlayer`, `AndroidMetronomePlayer` in `:core:audio`): like the reference tone (*Reference tone*, above; both share `AudioOutput`), a mono float `AudioTrack` at the native rate, `USAGE_MEDIA` / `CONTENT_TYPE_SONIFICATION`, on its own single writer thread, existing only while it plays. It keeps 12 chunks of 10 ms queued: a busy moment can't starve the speaker (a gap would shift every later beat), and a change is heard ≈ 0.12 s after it is asked for. Underruns are logged. `start(bpm, meter)`, `setTempo`, `setMeter` and `stop` only set fields under a lock, read before every chunk. It never touches the microphone.
- **Plays over other music: no audio focus** (owner's decision 4, 2026-10-15; until then it took `AUDIOFOCUS_GAIN`, which paused other apps' music). Players often practise with a backing track from another app, which must keep playing at full volume, so the metronome asks for no focus at all: `AUDIOFOCUS_GAIN_TRANSIENT_MAY_DUCK` would still make Android lower the other app's music (or pause it, for apps that pause when ducked), and any `GAIN` pauses it. Without focus nothing tells it about a call, so the session reads the phone's audio mode (`AudioManager.getMode()`, `isCallMode`: anything but `MODE_NORMAL`, i.e. ringing, a phone call, a voice or video chat) before it starts (then it stays silent, as before when focus was refused) and every 25 chunks (4× a second) while it plays, and stops; it doesn't come back by itself after the call. Another app taking focus doesn't stop it. `addOnModeChangedListener` would tell sooner, but only from Android 12; the check costs one binder call per 250 ms on the writer thread. The reference tone keeps its transient focus (*Reference tone*, above): tuning by ear needs the tone alone.
- **Headphones unplugged** (`ACTION_AUDIO_BECOMING_NOISY`, also when a Bluetooth headset goes): a receiver registered for each session (not exported from Android 13; only the system sends it) stops the clicks, so they never carry on out of the speaker, as music players do.
- **Beats for the screen** (`beats: SharedFlow<MetronomeBeat>`, with `index`, `beatInBar`, `accent`, `heardAtNanos` on the `System.nanoTime()` clock): each rendered beat waits in a small ring; once `AudioTrack.getTimestamp` runs, its moment is known about one buffer ahead and a timer emits it then (the writer thread only wakes when the speaker takes a block, every 10–40 ms, which told beats up to 35 ms late); before the first timestamp it is emitted when the playback head reaches it. So beat lights and vibration can match the sound. `FakeMetronomePlayer` (`testFixtures`) emits beats on request.
- **Tap tempo** (`TapTempo`, pure, allocation-free): the tempo of the last taps, the time from the oldest of the last six to the newest over the intervals between them (so one late tap only shifts it by its share), whole BPM within 30–250; a pause of more than 2 s (slower than 30 BPM) starts afresh. A tap counts when the finger touches, not when it lifts. **Tempo markings** (`TempoMarking`): the Italian name under the tempo, from Grave (under 40) through Largo, Larghetto, Adagio, Andante, Moderato, Allegro (120–167), Presto to Prestissimo (200 and up), the mock-up's bounds. `TapTempoTest`.
- **Measured on the Xiaomi 12X** (`AndroidMetronomePlayerTest`, 240 BPM): a float track at 48 kHz, no underruns; beats heard 250 ms apart within ±0.02 ms by the output's timestamps, and told 2–4 ms after their sound.
- **Ten minutes on the Xiaomi 12X** (`scripts/metronome-drift.sh`, on demand: `MetronomeDriftMeasurement` in `:core:audio`'s instrumented tests, skipped unless `-a metronomeDrift=true`; the real player at 120 BPM in 4/4 at media volume 1 of 150, put back after; 1,200 beats, 2026-10-14):
  - *Sample clock*: every beat of ten minutes rendered at 48 kHz in the player's 10 ms chunks lands on its ideal sample (largest error 0.000 samples): no drift, by construction.
  - *Speaker clock against the system clock*: the heard moments fitted to a line give one beat every 500.000005 ms of `System.nanoTime()`, **0.0 ppm** (+0.1 ppm in a one-minute run); after 1, 5 and 10 minutes the beats are +0.02, −0.01 and +0.00 ms from a perfect wall-clock grid. The output's frame clock and the system clock come from the same crystal on this phone, so the metronome keeps time with the phone's clock, not just with itself.
  - *Jitter of the reports*: heard gaps 500 ms −0.28 … +0.26 ms (rms 0.05 ms), scatter about the line at most 0.27 ms (rms 0.04 ms), which is the timestamps' own noise, not the sound; each beat reaches the screen 1.0–6.0 ms after its sound (median 2.4, 95 % within 3.4). No missed beats, no underruns.
  - Not measured acoustically: the microphone runs off the same audio clock, so recording the clicks could not tell more than the timestamps do. The owner's play-along check is under *Owner checks* in ROADMAP.md.

## 4. Threading & performance
- `AudioRecord.read()` blocks, so it runs on `Dispatchers.IO.limitedParallelism(1)`. DSP runs on `Dispatchers.Default`. The reference tone's and the metronome's blocking `AudioTrack.write()` each have their own single thread too (§3, Reference tone, Metronome).
- **No allocations in the per-frame loop.** Buffers are allocated once; per-frame garbage at ~47 Hz causes GC jank.
- **YIN difference function via FFT.** The direct O(W·τ_max) sum (~2.6 M multiply-adds per frame) took 69 % of the app's CPU cycles on the S26 (~7 ms per frame). `FftDifference` computes `d(τ) = e(0) + e(τ) − 2·r(τ)` (paper, eq. 7): energies as a running sum, the cross-correlation from one complex FFT carrying both real inputs plus one inverse (N = 4096, or 8192 for low notes; radix-2 `Fft`, doubles, no allocation). `FftDifferenceTest` checks it within 1e-10 of the direct sum. `./gradlew :core:dsp:benchmark` (kept out of CI): YIN **1.05 → 0.48 ms** per frame on the JVM. Budget: 2 ms.
- **FFT passes block by block** (Phase 15). `Fft` used to run each pass twiddle by twiddle, sweeping the whole arrays once per twiddle; at N = 8192 (128 KB of doubles) they no longer stay in the CPU's cache, and the low-note window cost 4× the standard one on the JVM. Walking each pass block by block, in memory order, gives identical results and: JVM 0.48 → **0.18 ms** (4096), 2.0 → **0.49 ms** (8192).
- **Only visible changes reach the main thread:**
  - **Silence:** equal `Listening` states are dropped with `distinctUntilChanged()` on the DSP dispatcher.
  - **ViewModel:** `distinctUntilChanged { old, new -> old.looksLike(new) }` drops readings that would look the same as the last one *sent*: same text (whole cents, 0.1 Hz) and the needle within `NEEDLE_STEP_CENTS` = 0.03 cents (below a pixel) or pinned at the same edge, reception within `RECEPTION_STEP` (0.02). `looksLike` allocates nothing; `TunerUiStateShownTest` fails if `Detected` gains a field it doesn't compare.
  - **Composition:** `TunerScreen` composes from `state.asShown()` through `derivedStateOf`, so it recomposes only when text changes. Exact cents and reception reach the meter and wave as lambdas read only in layer and draw phases.
  - **Needle:** `MeterFrame` follows the lambda with `snapshotFlow` into an `Animatable` spring (each new target `launch`ed so the spring keeps its speed). Moving parts sit in their own `graphicsLayer` and only change its transform, so a moving needle neither recomposes nor re-records drawing.
  - **Frame rate:** on Android 15+ a plain Compose animation gets the "normal" rate category (60 Hz on the S26), so the meter asks for 120 Hz with `Modifier.preferredFrameRate(120f)`, which only counts while it draws.

On the phone the tuner runs on a big core at under 4 %.

**Decision: no native detector.** Nothing comes near the budget: the dearest case, the low-note strum check pinned to a little core, still finishes in a third of its 0.1 s, and the phone's scheduler gives it a big core. A C++ YIN would at best halve these numbers while adding the NDK to the build, JNI, and a second detector to keep within ±1 cent. Phase 21 closed without its build items. Look again only if a real watch drops readings or warms up, or a new feature runs YIN many times per frame; `scripts/dsp-phone-benchmark.sh` repeats these numbers in about a minute.

### Release build: shrinking and signing
- **Shrinking:** R8 (`isMinifyEnabled`) and resource shrinking; the APK went from 9.3 MB to 1.8 MB. The app uses no reflection; `app/proguard-rules.pro` only keeps the enums settings save by name (`TunerMode`, `InTunePrecision`, `ThemeMode`, `VisualStyle`, `TunerDisplay`, `WaveLook`, `MeterLook`, `InTuneEffect`, `Notation`, and the metronome's `Meter`) as a safety net; a new enum saved by name gets a rule too. **Never rename saved enum constants.**
- **Signing:** the release builds of both apps (phone and watch, which share an app ID) use the owner's **upload key**, never in the repo; the root `build.gradle.kts` reads it once and both modules sign with it: `~/.twangle-keys/` (`twangle-upload.jks`, alias `upload`, with `keystore.properties` and a README), or the path in the Gradle property `twangle.keystoreProperties`. Without it (CI, other machines) the release builds are unsigned and nothing fails; CI builds them anyway (`assembleRelease bundleRelease`) so R8, resource shrinking or bundle breakage shows up on every change. `.gitignore` excludes `*.jks`, `*.keystore` and `keystore.properties`. The Play Store will use Play App Signing, so a lost upload key can be reset.
- `./gradlew assembleRelease` (APK) or `bundleRelease` (AAB); check with `apksigner verify --print-certs`.
- **Version:** one place for both apps, `twangle.version` in `gradle.properties` (`1.0.0` now; major.minor.patch, each 0–99, no suffix). The root `build.gradle.kts` makes it the `versionName` and `versionCode` = major × 10000 + minor × 100 + patch (10000 now); the watch's code adds 1,000,000 (1,010,000). Every build that leaves the PC needs a higher version. About shows `versionName`.
- Release and debug APKs have different signatures: switching on a phone means uninstalling first, which clears saved settings.

## 5. Lifecycle & permissions
- `RECORD_AUDIO` is requested at runtime from the tuner. `rememberMicPermissionState()` tracks a `MicPermissionStatus` (rules in the pure `MicPermissionRules`, in `:core:audio` so the watch follows them too), and `PermissionPrompt` shows one action per state:
  - `NOT_REQUESTED`: asked automatically once; the prompt explains why and offers "Allow microphone".
  - `DENIED` (rationale shown): ask again.
  - `PERMANENTLY_DENIED`: "Open settings" deep-links to the app's page, and the text gives the way to the microphone there: from Android 11 "choose to allow it while using the app" (its page offers that among other choices), before it "turn on Microphone" (a switch in the Permissions list).
  - `GRANTED`: the tuner.
- **Telling a dismissed dialog from a permanent denial** (Phase 26): Android only says `shouldShowRequestPermissionRationale`, which is false both before the first refusal and after a permanent one, and a dialog dismissed without an answer (a tap outside, Back) comes back denied without changing it. After a request the rules look at the rationale before and after it and at `AppSettings.micRefused` (saved in DataStore on each refusal): a rationale afterwards is `DENIED`; one that went away is a real "don't ask again" (Android 10 and older) or a second refusal (11 and newer), so `PERMANENTLY_DENIED`; no rationale either side after an earlier refusal means Android answered without showing the dialog (denied for good in an earlier session), also `PERMANENTLY_DENIED`; never refused means the dialog was only dismissed, so `NOT_REQUESTED` keeps "Allow microphone". Until Phase 26 a dismissed first dialog sent the player to Settings.
- Checked again on every `ON_RESUME`: a grant in Settings is picked up, and a permission lost while the app was open (taken back in Settings, a one-time grant that ran out) goes back to the prompt instead of the tuner's "Microphone access was turned off" error. The same check runs when the recorder reports `MIC_PERMISSION_MISSING`; if Android still says granted, that error stays, with Try again.
- Survives rotation (`rememberSaveable`); only `micRefused` is persisted.
- The microphone is open **only while the tuner screen is visible**: `SharingStarted.WhileSubscribed(5_000)` plus `collectAsStateWithLifecycle()`, so `AudioRecord` is released in the background and the privacy indicator turns off. The 5 s grace keeps the session through a rotation. `MicLifecycleTest` (`:app`, device) checks it against `AudioManager.activeRecordingConfigurations`.
- No foreground service: background capture is neither needed nor allowed.

- **The metronome** plays only while its screen is shown (`StopWhenHidden` in `MetronomeScreen`: `ON_STOP` and leaving the composition both stop it), so going home, locking the phone or opening another screen stops the clicks. A configuration change (the phone turning, dark mode, the font size) recreates the activity, which stops it and disposes the composition too; while `Activity.isChangingConfigurations` neither stops the clicks, so they play on through it (until Phase 26 every rotation stopped them). `MetronomeRecreationTest` checks it. No foreground service. While it plays it keeps the screen on (`View.keepScreenOn`), so the screen timeout doesn't stop it; the volume keys set the media volume there, as on the tuner.

### Settings
Settings (`:feature:settings`) is one of the three tabs of the navigation bar (§6, *Navigation bar*), so it has no back arrow; About, opened from it, keeps one. `MainActivity` switches between tuner, metronome, settings, About and the tuning editor with one saved `Screen` value (no navigation library; `navigation/Navigation.kt`) and a `SaveableStateHolder`; Back returns About → settings → tuner, metronome and editor → tuner, and from the tuner leaves the app (`Screen.back`, JVM-tested). The editor's draft is dropped on leaving it (`removeState`), so each opening starts afresh. `SettingsViewModel` saves every change at once; there is no save button.

Four groups under headings (in the style's title face and `primary`, marked as headings for TalkBack), then Language, Show me around and About, each with an arrow (they open something). Groups are 32 dp apart; rows, including the card grids, keep 16 dp from the edges. Phase 26 split the old Look group in two, so no group holds more than two card grids.
- **Pitch and notes:** A4 calibration, note names, in-tune precision. (The instrument and tuning are picked on the tuner itself, from the navigation bar's Tuning item; the group was called "Tuning" until Phase 26, which clashed with it.)
- **Look:** style, light or dark, wallpaper colours.
- **Tuner screen:** meter look, in-tune effect (with a one-line explanation), "Below the note" (numbers or wave; "Display: Needle" until Phase 26, though the saved value is still `TunerDisplay.NEEDLE`), wave look, full layout on its side.
- **While tuning:** keep screen on, vibrate when in tune, tune up/down hint, signal bars.

What each does:
- **A4 calibration:** slider 415–466 Hz in 1 Hz stops, − and + buttons, "Reset to 440 Hz"; saved when the finger lifts. Every string joins a number and "Hz" with a no-break space (`\u00A0`), so "442 Hz" never breaks across lines (`HertzStringsTest` checks every language); the value beside the title is one line. The tuner itself shows no "A4 =" line (Phase 14: the screen stays calm; only Settings shows the reference).
- **Note names:** sharps, flats or Do Re Mi (`RadioGroupSetting`). A preset's own spelling wins in guitar mode (§3, Tuning spelling).
- **In-tune precision:** Relaxed (≤ 5 cents, default) or Precise (≤ 2). `TunerInterpreter` swaps in `InTuneDetector.forPrecision` on the next frame; everything that follows `inTune` follows it.
- **Style:** `StylePicker` (`:feature:settings`), a `LookCardGrid` like the meter and wave looks: six mood cards in the owner's order, three to a row (two from 1.3× font), the style's name under each (§6, Visual styles). It is the only place to pick a style; the tuner's palette button went in Phase 14.
- **Light or dark:** system, light or dark, plus "Wallpaper colours" (dynamic color, Android 12+, Contemporary only; on by default on a fresh install, owner's decision 2026-10-15). `MainActivity` reads settings before drawing, so the theme never flashes, and calls `enableEdgeToEdge` again on a change so status-bar icons follow the app. With gesture navigation the navigation bar gets no scrim (`isNavigationBarContrastEnforced = false`, Android 10+), so the style's background runs to the bottom edge under the handle: MIUI otherwise lays a white or dark strip there. Navigation buttons keep the system's scrim, so they stay readable. Which one shows comes from the secure setting `navigation_mode` (2 is gestures), read again whenever the insets change; without it, from the tappable-element insets (0 with gestures; MIUI counts its gesture bar as tappable, so they can't decide there) (`SystemBars.kt`, JVM-tested; checked on the Xiaomi 12X with gestures and with buttons, light and dark).
- **Keep screen on** (default on): `View.keepScreenOn` while the tuner is shown with the mic granted; a window flag, not a wake lock.
- **Vibrate when in tune** (default on): `InTuneHaptic` clicks once (`EFFECT_CLICK`, 20 ms one-shot before Android 10) when `inTune` turns true. It uses `Vibrator` directly because Compose/View haptics obey the phone-wide touch-feedback setting, which many people switch off; this needs the normal `VIBRATE` permission. `InTuneTickRule` skips a second tick for the same note within 1.5 s; the state is saved, so rotating doesn't tick.
- **Show tune up/down hint** (default on): `NoteDisplay` shows `Detected.hint` ("Tune up ↑" / "Tune down ↓") in `primary`. In the wave view it fills the empty pill; with the needle it gets its own line that keeps its height while empty, so nothing jumps. TalkBack adds it in words. The switch controls both.
- **Show signal bars** (default off): §3, *Signal bars*.
- **Language** (`LanguageSetting`, the first row under the groups): the app's language, "Phone's language" or one in its own name. A tap opens a dialog listing "Phone's language" (follows the phone) and then every language of `twangle.languages` in its own words, in alphabetical order of those names (Latin letters first, then Cyrillic, Arabic, Devanagari, Hangul and Han). Picking one sets it through AppCompat and the screen is recreated in it, still on Settings. The list takes at most 60 % of the window's height, so the dialog keeps clear of the screen's edges; it scrolls, opens at the picked language, and a thin line at its top or bottom shows there is more that way. Indonesian is "Bahasa Indonesia" (the locale data says only "Indonesia"). Details in §6, *Languages*.
- **Show me around** (a `LinkSetting` row above About, "A short tour of the tuner"): opens the tuner and starts the first-start tour again (§6, *Tour*).
- **About** (its own page, `AboutScreen`, opened from a `LinkSetting` row showing the version; Settings and About share `SettingsPage`): name and version (`BuildConfig.VERSION_NAME` passed from `MainActivity`), the free-forever promise, a short privacy statement (settings stay on this device, and in Android's own backup if it is on; keep it in step with PRIVACY.md), and a credit for every bundled font and library. Each credit opens an `AlertDialog` with the full licence, read from assets on `Dispatchers.IO` and reflowed (`reflowLicence`). With no internet permission every licence ships in the APK: OFL texts in `:core:designsystem` `assets/licenses` (`bundledFontCredits`, kept in step with `res/font` by a JVM test) and Apache 2.0 and Protocol Buffers' BSD 3-Clause text in `:feature:settings` `assets/licenses`. Besides AndroidX and Kotlin, the credits name the libraries that come in with them: Okio and a copy of Protocol Buffers (DataStore), JSpecify and Guava's ListenableFuture (AndroidX); check `:app:dependencies --configuration releaseRuntimeClasspath` when a dependency is added. A new library needs its own credit, and its own licence file if it is under another licence. Licence texts are what users read, so they hold no build details (script names, source paths; `FontCreditsTest` checks the font ones).

### Custom tunings
Phase 16. A `CustomTuning(id, name, instrument, notes)` (`:core:settings`) is a tuning the player made; its `tuning` is a plain `Tuning` with the same id and no spelling of its own (the sharps/flats setting writes it), so the tuner, string row and pitch range treat it like a preset. `AppSettings.customTunings` holds them all in the order they were made; `customTuningsFor(instrument)` gives one instrument's (for the picker, below its presets) and `pickedCustomTuning` the picked one, or null for a preset.
- **Ids** are `custom_` plus a random UUID, made once by `addCustomTuning` and never changed, so editing keeps the tuning picked. No preset id starts with `custom_` (JVM-tested).
- **Names** are normalized on every save and read (`CustomTuning.normalizeName`: trimmed, runs of white space made one space, at most 40 characters) and may not come out empty. Duplicate names are the editor's to refuse; compare normalized names.
- **Notes** are one per string of the instrument (MIDI 0–127). The instrument is fixed when the tuning is made.
- **Repository:** `addCustomTuning(name, instrument, notes)` saves it after the others and returns it, not picked (pick it with `setTuning(it.tuning)`); `updateCustomTuning(id, name, notes)` keeps its id, instrument and place, and a picked one stays picked with the new notes (that is a tuning change, so a locked string is released); `deleteCustomTuning(id)` removes it and, if it was picked, picks its instrument's standard tuning. Bad input (empty name, wrong number of notes) throws `IllegalArgumentException` and saves nothing. `FakeSettingsRepository` does the same, with ids `custom_1`, `custom_2`, ….
- **Editor** (`:feature:tuner`, `editor/TuningEditorScreen.kt`, its own `Screen` in `MainActivity`, so the tuner rests and lets go of the microphone meanwhile; on the quiet background like the settings). Opened from the panel's last row, "New tuning", for the instrument shown; it also opens for an existing `CustomTuning` (`editingId`, instrument fixed) from Edit in that tuning's menu in the panel. Material form: a close button (leaves without saving) and Save along the top, the title ("New tuning" / "Edit tuning", a heading that wraps at large fonts) and "Instrument: Guitar", the name field, then the heading "Strings" and a row per string, thickest first: "E₂ string" (its standard note), then − note +. A new tuning starts from the instrument's standard notes.
  - **Notes** move a semitone per tap and stay within **B0–E6** (MIDI 23–88, `EDITOR_NOTE_RANGE`): B0 is the lowest preset string and still reads a semitone flat at A4 = 440 Hz (and in tune at 415) in the low-note window, which a tuning this low switches on by itself; E6 still reads a semitone sharp at A4 = 466 Hz (1479 Hz, under the detector's 1500). At an end the button is turned off. Notes are written in the notation setting (a custom tuning has no spelling of its own); the caption keeps the standard tuning's.
  - **Name checks** run only when Save is tapped: empty ("Give the tuning a name") or already one of the instrument's tunings ("There is already a tuning with this name": its presets' names as shown and its other custom tunings', compared as `normalizeName` gives them and ignoring case; another instrument's names are free). The message goes as soon as the name changes and comes back only on the next Save, so nothing flashes while typing. Typing stops at 40 characters.
  - **Save** (`saveDraft`, JVM-tested) adds the tuning or updates it and **picks it** in one DataStore write (`addCustomTuning` / `updateCustomTuning` with `pick = true`; before Phase 26 the pick was a second write), and returns to the tuner, whose button names it ("Guitar · Drop D loose"; `TunerViewModel.customTunings`, passed in from the saved settings at the start so the id never shows). The save runs in `TuningEditorSaver`, a small ViewModel, so turning the phone mid-save neither cuts it off nor loses that it is done: the new screen sees `SavePhase.SAVED` and closes. Save does nothing while a save runs.
  - **Discard changes?** (Phase 26): the close button, Back and a tap on the home-screen widget leave at once when nothing was edited, else they ask "Discard changes?" (Discard, in the error colour, or Keep editing; Back or a tap outside keeps editing). An edit is another note or a name that would be saved differently (`TuningDraft.hasChangesFrom`: spaces alone don't count, a note moved and moved back doesn't either). The editor handles Back and the widget's request itself (`closeRequest`), so `MainActivity` registers no Back handler while it shows. Its title uses the delete question's size (`DIALOG_TITLE_SCALE`).
  - The draft (`TuningDraft`, pure and JVM-tested) survives rotation, and so does the open question. TalkBack: the note says "E 2 string, D 2" (a polite live region, so it is said again after a tap; the caption is hidden), the buttons "E 2 string, a semitone lower / higher", the message is a live region. `TuningEditorTest` checks it all, Dutch ("e 2-snaar, dis 2"), and every control and text wholly shown at 2× text with eight strings in Dutch (every style in a thorough run).
- **Stored** in one string (`CustomTuningCodec`): a line per tuning, `id|instrument id|midi,midi,…|URL-encoded name`; fields added later go after the name and older readers ignore them. A line that can't be read (unknown instrument, wrong note count, bad number or note, no name, repeated id) is skipped and the rest kept; the next save writes only the good ones. A picked custom tuning that is gone, damaged or of another instrument gives the instrument's standard tuning, so damaged data always falls back to the presets.

```kotlin
        val notation: Notation,
        val phase: StrumPhase,         // WAITING, HEARING, RINGING, DONE
        val strings: List<StrumString>, // per string: verdict, whole cents, sure; empty until the first reading
        val toleranceCents: Float,     // 5 (Relaxed) or 2 (Precise)
    ) : TunerUiState
}
```

`TunerViewModel` exposes `state: StateFlow<TunerUiState>` plus `mode: StateFlow<TunerMode>`, so the mode switch reacts instantly, and `instrument: StateFlow<Instrument>` for the instrument and tuning panel (the tuning in `state` is always one of its presets). Inputs: `onPermissionChanged(granted)`, `setMode`, `setStrumCheck(on)` (with `strumCheck: StateFlow<Boolean>`), `setInstrument`, `setTuning`, `setStyle`, `toggleString(index)`, `playString(index)`, `stopTone()`, `retry()`; `soundingString: StateFlow<Int?>` says which string's reference tone sounds (§3, *Reference tone*). Picking another instrument switches to its standard tuning, which releases a locked string like any tuning change and, for low strings, the longer window follows on the next frame. Until permission is granted the state is `PermissionRequired` and the pipeline isn't started; the permission status itself lives in the UI (`rememberMicPermissionState`).

`reception` is never composed (`asShown()` sets it to 1); `TunerScreen` passes it as a lambda read in layer and draw phases only.

**No first-frame flips.** `MainActivity` has already read the settings, so it passes saved values in as each flow's first value: `TunerScreen(savedMode = …)` (otherwise Guitar showed for ~90 ms before Chromatic), `savedKeepTwoPaneLandscape` and `savedInstrument` (the button never shows the guitar first). `setMode` switches at once and saves in the background.

### Strum check view
Phase 18: strum once and every string of the tuning shows flat, in tune or sharp at once (the detector: §3, *Strum check (polyphonic)*).
- **Entry point:** a switch above the strings, at the end of a row of its own in line with the last string (`StrumCheckToggle`: strings with a sweep across them, in the style's button outline and shape, filled with `primaryContainer` while on), so it lives with guitar mode's controls and leaves the top corners alone for Phase 19's navigation bar. Until 2026-10-15 it sat at the end of the instrument-and-tuning button's row; that button moved into the navigation bar. Not saved: the app always opens on the tuner. Switching to chromatic turns it off; switching it on from chromatic goes to guitar mode. In the compact layout on its side it is reached like the other controls (tap the screen).
- **Audio** (hard rules 2–4 unchanged): one `AudioRecorder` collection serves both. `PitchPipeline.listen(range, strumStrings)` asks for every chunk whether strum check runs (`TunerOptions.strumChecking`, and no reference tone or its 0.3 s tail); while it does, chunks go to a `StrumListener` + `StrumDetector` (`StrumAnalysis`, made the first time and again only for another range; the frame follows the tuning's lowest string like the tuner's window) instead of YIN. It emits a `StrumReading` when strum check starts or starts over (other strings or A4), when a strum is heard or stops ringing, and with each reading (every 0.1 s). Back on the tuner, its window and smoothing start afresh. The switch never reopens the mic.
- **State:** `StrumCheckInterpreter` (pure, JVM-tested) makes `TunerUiState.StrumCheck`: verdicts from `StrumVerdict` at the tuner's own tolerance (5 cents Relaxed, 2 Precise; +2.5 for shadowed strings), the previous reading of the same strum holding "in tune" 1 cent longer. Each string shows **all readings of the strum so far together**, weighted by their frame's power (`StrumReading.levelDbfs`), so the loud start counts most and the noisy readings as the strings die away barely count (the phone check in §3): heard when heard in more than half the weight, its cents the weighted median of the readings that heard it, less sure when more than half of those were (up to 100 readings, 10 s). A strum's first reading must hear at least half the strings, or it is taken for another sound (a voice, a knock) and what was shown stays. A new strum keeps the last strum's strings (faded) until its own first reading. A reference tone starts the strum check over.
- **Panel** (`StrumPanel`, in the meter's place at its 2:1 shape, so every layout places it like the meter): one column per string, in the string row's order: its name (octave low, as on the string buttons), a short upright scale (±50 cents, sharp up, flat down; ♯ and ♭ once at the panel's start; the in-tune band round the centre mark, faint and in the muted colour until the string reads in tune, then in the style's "in tune" colour, and the centre mark muted until the string is heard, so a panel waiting for its strum never looks like six strings in tune (Phase 26: green only ever means in tune)), a marker at the reading (the "in tune" colour, else the accent) and under it a check mark, the cents ("−12", "+8", up to ±99) or "–" for a string not heard (its scale faded). A **less sure** (shadowed) string has a hollow marker and paler figures. On a calm field like the meter's, in the style's colours, display face and number face, sized by the panel's width (u = width / 340, like the meter), not the font size. Markers glide for 250 ms.
- **Line under it** (`StrumStatus`, in the note's place): "Strum all the open strings", "Listening…", then "2 strings to tune", "Not every string was heard" or "All strings in tune" (in the "in tune" colour), with a smaller line: what the strings show, "Tap a string to tune it", "Strum again, or tap a string to tune it". Each line takes the room of its longest text (`TallestOf`), so nothing moves between phases. A polite live region.
- **Strings:** no target is highlighted. Tapping one, on the string row or its column in the panel, leaves strum check and locks the tuner to that string, to tune it (both call `onStringClick`, the ViewModel's `toggleString`; while a reference tone sounds, a tap stops it, as anywhere). ### Meter
The meter above the note is the first thing anyone sees, so players pick one of six looks (setting `meterLook`), in the owner's order: *Classic* (default), *Light arc*, *Spirit level*, *Eclipse*, *Arrows*, *Light bars*. Phase 25 (October 2026, the approved mock-up [docs/design/meter-looks-round2-preview.html](docs/design/meter-looks-round2-preview.html)) makes every look show the note its own way: Classic keeps the only numbered scale; *Rolling scale*, *Comet* and *Studio meter* went (a saved one reads as Classic); Light arc and Spirit level lose their numbers; *Eclipse*, *Arrows* and *Light bars* join.
- **One frame** (`:feature:tuner` `components/MeterFrame.kt`): every look sits in `MeterFrame`, so changing looks moves nothing else. It owns the 2:1 box (`METER_ASPECT_RATIO`; each look draws its ♭ and ♯ inside it, at its scale's ends), the ±50-cent range (beyond it the marker pins at the edge, `meterCents`; without a reading it rests in the centre at 0.3 opacity), the look's spring (`meterFeel(look)`), the in-tune amount `tuned` (smoothstep, 0.4 s in, 0.6 s out), the in-tune `glow`, the reception fade and blur, and `clearAndSetSemantics {}` (`NoteDisplay` speaks the reading). It hands the look one `MeterReading`: cents, `velocity` (from the spring, without boxing), `presence`, `tuned`, `glow` and `applyMarkerLook(layer)`, read only in layer and draw phases.
- **Art in the design system** (`:core:designsystem` `meter/`): `MeterLookArt` draws each look, so the tuner and the settings cards draw exactly the same thing and `:feature:settings` needs no `:feature:tuner`. A part that only turns or slides gets its own `graphicsLayer` and only changes its transform; a part that changes shape is redrawn in its `Canvas` from paths, brushes and strokes made once. The art is not clipped: the calm field and the glow fade out past the box (up to ~110u). The settings cards clip their preview to its box so the names stay clean.
- **Shared pieces** (`meter/MeterArt.kt`, named like the mock-up's helpers): `MeterRoles` (the colour roles and number face), `FieldArt` (`meterField`, the same calm field under every look, so switching looks changes nothing round the box), `ContactShadowArt`, `GlassArt`, `ScaleMarks` (with `numberFit`, which keeps neighbouring numbers 8u apart by setting them up to 30 % smaller), the style's finish (chosen in `meter/MeterFinish.kt`, drawn by `NeedleArt`, `HubArt` and `TrackArt`), `SignsArt` (♭ and ♯), `markerShadowPaint`, `GlowArt`, `StaticArt`, plus `mix` and `blurRadius`. Everything is built in `drawWithCache`, so only a size or colour change rebuilds it; drawing allocates nothing. Shadows need hardware-accelerated `BlurMaskFilter` (Android 9+); on Android 8 the meter has no shadows. `meter/MeterLooks.kt` holds Classic and its dial (`DialGeometry`, `DialUnder`, `DialCentre`).
- **The looks:**
  - *Classic:* the dial with the style's needle; needle and shadow drawn once and only rotated by their layers, the style's hub over the pivot in a layer that doesn't turn (it redraws only while it fades to "in tune"). Slightly underdamped, so it swings ~9 % past a new string and settles within a second, like a mechanical needle. The unit "CENTS" (`meter_cents_label`, translated; it was the studio meter's) sits 42u above the pivot under the needle, 7.5u in the number face with 0.3 em letter spacing, muted at 90 % (`CentsLabelArt`).
  - *Light arc* (`LightArc.kt`, Phase 25): a fan of little lights like an LED pedal's, no dial and no numbers. 17 rays (one every 6.25 cents, ±50 at ±1.2 rad) from a pivot 6u under the box, each of 5 lights 78u to 148u out (3.4u to 5.6u across), unlit in the track colour (75 % dark, 70 % light) like dark LEDs. The rays from the centre out to the reading light as a wedge (`lightArcGoal`): the reading's ray all five lights at full, rays nearer the centre fewer (down to 1.6) and dimmer (to 40 %); the ray just past the reading lights part of the way, so the wedge grows smoothly. A lit light is the accent (a little whiter in dark), 8 % larger, with a halo 3.4× its radius. The middle ray is the centre mark in its own layer: its two inner lights at 45 % and the rest at 14 % off the note, all five in the centre colour as it's reached, and the rays beside it light half way. `LightArcHeat` (one preallocated array of 85) gives a 0.22 s fading trail; its frame loop (`withFrameNanos`) runs only while a light is still changing, then waits on `snapshotFlow`, so a steady reading moves nothing and UI tests settle. ♭ and ♯ in the box's lower corners.
  - *Spirit level* (`SpiritLevel.kt`, straight since Phase 25): a big straight vial (86 % of the box wide, 38 % high, round ends, its middle 45 % down) of liquid tinted by the accent, with no scale or numbers. The bubble stays at the vial's middle height and slides 92u for 50 cents (pinned at ±52); it is drawn once and its layer only moves and stretches it (up to 25 % while moving fast, from `velocity`). In tune it rests between two lines etched 3u clear of its ends, so a cent or two off it touches one; the lines fade to "in tune". A highlight streak along the upper inside; ♭ and ♯ under the vial's ends. No drop shadow (air in liquid).
  - *Eclipse* (`Eclipse.kt`, Phase 25): the target is the sun (44u, the accent lit from its upper left, with a halo 2.4× its radius) in the middle, 47 % down; the note is the moon (45.5u, a disc of the background colour with a faint ink rim) sliding along a dotted path, 118u for 50 cents (pinned at ±52). They start to overlap within about ±38 cents; in tune the moon covers the sun whole. At rest (Phase 26) the moon fades out with `presence` and the sun is the muted colour dimmed 45 % toward the background (a third set of brushes), so a meter with no note never shows a total eclipse. The moon is drawn once and only moved by its layer. As the note is reached the sun blends 60 % to "in tune" (two sets of brushes made once, cross-faded), its halo dims and the moon's rim turns "in tune"; the in-tune glow is a corona round the moon (a ring from its edge to 2.1× its radius at 1.9× the usual glow strength, in its own layer moved with the moon, alpha from `glow`, larger and stronger in Bold). ♭ and ♯ under the path's ends.
  - *Arrows* (`Arrows.kt`, Phase 25, after a pedal tuner's converging wedges): four chevrons each side (tips 26u + 30u·k from the middle, 7 % smaller each, 7.5u round strokes) point at a 9u × 100u centre bar. On the side the note is off they light one after another, the inner one first, each over 10.5 cents from 2 cents off (`arrowLight`), in the accent with a halo of themselves 2.2× as wide; the other side and unlit chevrons are the track colour. In tune the inner pair lights at 90 % in the centre colour and the bar (outlined in the centre colour, filled 18 %) fills in. No shimmer (the mock-up had one): a steady reading must draw nothing new, and UI tests must settle.
  - *Light bars* (`LightBars.kt`, Phase 25, after a pedal tuner's display): 41 bars (one every 2.5 cents, ±150u, 3.6u round), mirrored about the middle line, 5u each way when dark (the centre bar 12u, part way to the accent). A Gaussian peak (σ 4.5 cents, widening to 6.5 as the note is reached; `lightBarPeak`) round the reading grows the bars by up to 62u each way, lit in the accent at 1.25× their share, fading to 30 % toward their tips (one vertical brush per colour made once), with a soft accent halo (72u) under the peak that gives way to the in-tune glow; near the middle the lit bars blend to "in tune" as the note is reached. The peak is pinned at ±51.5 cents, so the end bar stays lit past the range.
- **Feel per look** (`meter/MeterFeel.kt`, frequency / damping ratio, stiffness = (2π f)²): Classic 1.6 Hz / 0.6, Light arc 2.2 / 0.9, Spirit level 1.0 / 0.5, Eclipse 1.2 / 0.8, Arrows 2.0 / 0.9, Light bars 1.8 / 0.8.
- **The in-tune moment** (owner: smooth, not gimmicky): a soft glow eases in with the haptic tick, holds while the note rings and fades when it leaves.
  - *When:* `InTuneGlowRule` (pure) lights it on the update that raises `Detected.inTune`, never restarts it while the note holds, and bridges a dropout of the same note for 600 ms (shorter than the tick's 1.5 s, so a bridged dropout never ticks twice). Another note or drifting out of tune puts it out at once, and so does the same note coming back while the hint asks to tune it (a re-pluck often starts sharp), so the glow never lights with "Tune down" on screen. `rememberInTuneGlow` runs it in `TunerScreen` (saved over rotation) → `TunerContent(meterGlow)` → `MeterFrame(glow)`, eased 0.4 s in, 0.6 s out.
  - *Remove animations:* `rememberAnimationsOff()` (`:core:designsystem`, `AnimationsOff.kt`, shared with Settings' look cards) reads `ANIMATOR_DURATION_SCALE` and follows changes; at 0 `tuned` and `glow` snap.
  - *Drawing:* the shared `TuneGlow`, a `GlowArt` in the "in tune" colour drawn once in its own layer under the marker; `glow` only sets the layer's alpha (`CompositingStrategy.ModulateAlpha`), so easing it redraws and allocates nothing. Never clipped (Phase 14): it fades out past the box, behind the controls around the meter.
  - *Calm or Bold* (`InTuneEffect`): Bold is the same glow and timing at 1.7 × the alpha, capped at 52 % (`BOLD_GLOW_MAX_ALPHA`) so the scale stays readable, and 1.35 × the radius (`BOLD_GLOW_SIZE`). It travels into `meterRoles(effect)`, so changing it rebuilds each look's cached art once and is never read per frame.
- **Picker** (setting "Meter", above the display choice): `MeterLookPicker` draws each look's `MeterLookArt` in a 3 × 2 grid of cards (two to a row from 1.3× font). It shares `LookCardGrid` with `WaveLookPicker`: the ring on the picked card, names on one line shrinking to 8 sp, one selectable radio group for TalkBack, test tags, and `LookDemo`, an infinite animation (UI tests skip it). With "Remove animations" the cards hold still on the loop's first second (`holdStill`: the meter 18 cents flat, the wave drawn, the style strips in place), or where they were when it is switched on, and move again when it is off. The cards play one loop (`MeterDemo`): 18 cents flat, tuned up slowing like a peg, in tune, drifting 14 sharp, tuned down. Each card previews the chosen in-tune effect.
- **Tests:** JVM tests for each look's maths (`MeterReadingTest`, `MeterFeelTest`, `LightArcHeatTest`, `SpiritLevelTest`, `EclipseTest`, `ArrowsTest`, `LightBarsTest`, `TuneGlowTest`, `InTuneGlowRuleTest`, `MeterDemoTest`, `NumberFitTest`, `MeterFinishTest`). UI: `MeterLooksTest` (every look × style × light/dark: clearly drawn in its box, fading out around it with no edge at the box and nothing left at 0.3 box widths, skipped by TalkBack, moves without recomposing, glows in Calm and more in Bold with Bold's glow reaching past the box, snaps with animations off), `CompactLandscapeStylesTest`, `TunerContentTest`, `SettingsContentTest`.
- **Pictures for the owner:** `scripts/meter-look-screens.sh` (~2 min) runs `MeterLookScreenshots` with `-a meterScreenshots=true` (without it the class has no cases): every look in every style, light above dark, 20 cents flat and in tune with Bold, as PNGs plus an `index.html` contact sheet in `build/owner-screens/meter-looks/`.

### Meter art language
The looks are drawn "as if by the same artist" (owner, after two rounds of moving mock-ups, October 2026). The approved mock-ups are the reference: [docs/design/meter-looks-preview.html](docs/design/meter-looks-preview.html) and, for the open face of Phase 14, [docs/design/theme-styles-preview.html](docs/design/theme-styles-preview.html) (their top comments list the same rules). *u* = box width / 340, about 1 dp on a phone.
- **Colours:** roles only, from the current style: background (stage), surface (plate), onSurface (ink), onSurfaceVariant (muted), outlineVariant (track), primary (accent) and the "in tune" colour. No ornaments beyond the style's finish (below). Minor ticks are ink at 50 % and numbers ink at 80 % (`MINOR_TICK_INK`, `SCALE_NUMBER_INK`), so they keep 3:1 and 4.5:1 on every style's background.
- **Font:** only the style's number face (`numberFontFor(style)`), with lining figures (`LINING_FIGURES`); wide faces (Michroma, Orbitron) at 82 %.
- **Plate:** none (Phase 14). No plate, frame or drop shadow: the meter sits straight on the screen's background. The dial (Classic) grew to a 146u radius around a pivot 17u above the box's bottom (it was 124u and 24u inside the plate).
- **Field:** instead, a calm field: a soft oval wash of the background colour, 190u × 150u each way round a point 47u above the box's bottom middle, 75 % in its middle, 56 % at 62 % of the way out, 0 at its edge, no edge line. The same for every look.
- **Glass:** dial looks have none. A window that is an object lying on the screen (the spirit level's tube) is recessed: sunk toward the background, 1u rim in ink at 14 %, inner shadow under the top edge (7u blur), one sheen from the top (white 28 % light, 7 % dark, gone by 45 % of its height), inner corners 10u, and a soft contact shadow under it (10u blur, 4u down, black 50 % dark, 16 % light).
- **Scale** (the open face's larger one, Phase 14): a tick every 5 cents, none at 0. Major (every 10) 13u × 2.1u in ink; minor 7u × 1.3u at 50 %; the style's caps. Numbers 10–50 without sign, 12.5u, ink at 80 %, centred 27u from the tick's base, at least 8u apart (`numberFit` sets close numbers up to 30 % smaller; only Classic has a scale since Phase 25). The dial's ticks start 4u inside its arc.
- **♭ and ♯:** inside the box, in muted, at the ends of each look's scale (`SignsArt`, 20u in the music-sign face): under the dial's end ticks (fitted between them and the box's bottom), under the vial's and the eclipse's path's ends, under the outer arrows, in the light arc's and the light bars' lower corners. The row of signs under the box went, so the meter takes 2:1 and nothing more.
- **Centre:** one 3.5u rounded bar in the accent.
- **Marker** (needle, bubble, moon, lights or bars): a small soft shadow (3u blur, 1.5u right, 2.5u down); the beam glows instead (a 6u halo of itself at 18 %).
- **Finish** (`MeterFinish.kt`, the mock-up's `fin`; one of each per style, same proportions, same art): needle (Ancient spear, Classic watch hand with a ring near its tip, Retro VU line with an accent tip, Contemporary plain bar, Futuristic beam with a chevron, Space Age ball tip), hub over the pivot (stone, cap in the centre colour, ink disc with a dot, ink dot, ring, ringed planet), arc (dots in the accent, railway of two ink hairlines, broad band in the track colour, line, dashed accent line, dots), tick caps (round, butt, butt, round, square, round) and, for Ancient only, ticks drawn by hand (±12 % length, ±20 % width, ±0.05 rad, from a fixed hash so they never change). Classic wears the needle and the arc; the scale and the spirit level's lines the caps. The arcs are decoration (the ticks carry the scale), so the dashed and dotted accent arcs (55–60 %) need no contrast minimum.
- **Light:** one glow only, radial, in the "in tune" colour (32 % dark, 16 % light at its middle, fading to 0), never clipped by the box.
- **At rest:** every look's centre (Classic's centre bar and hub, Light arc's middle ray, Arrows' bar) is the muted colour without a note and fades to the accent with `presence` (`MeterRoles.centre(tuned, presence)`, `RestingCentreTest`): with wallpaper colours the accent can be green, and a resting meter must never look in tune (Phase 26).
- **In tune:** one eased amount (smoothstep, 0.4 s in, 0.6 s out) blends centre mark and marker to "in tune"; the glow eases the same way. Both follow the steady hint's decision; with "Remove animations" both switch at once. Nothing flashes, bursts, flies, pulses or repeats.
- **Motion:** springs with a damping ratio of 0.5 or more.

### Wave view
Most people don't know what a cent is, so the wave display (`WaveView`, 240 × 40 dp, low and frameless so it doesn't compete with the meter) shows how far off the note is as a moving shape under the note. It borrows the beats you hear between two close notes: `WaveMotion` (`dial/WaveMotion.kt`, plain Kotlin) pinches the ribbon into pulses.
- **Drift follows the strobe rule exactly:** `WaveMotion` runs its own `StrobeMotion` (§3), so it stands dead still within half a cent and drifts right when sharp, left when flat, faster the further off (up to 4 pulses/s from 10.5 cents). It uses the exact cents, not `inTune`, so the last few cents still show.
- **Shape shows distance from afar, up to 50 cents:** the pinch deepens (`depthFor`) and more pulses fit across (`beatsFor`, 1.5 to 4.5) the further off; within half a cent the band is perfectly even. Shape eases towards the reading at 5/s, so a new string never makes it snap.
- **Breathing:** off pitch the band breathes slowly (one breath every 2.5 s, 10 % of its height). On the note it fades out (`WaveMotion.stir` → 0 in about a second), so nothing moves at all, like a strobe disc. The owner picked this over breathing on gently (October 2026); the temporary "When in tune" choice and its saved key `wave_breathes_in_tune` are gone, and an old saved value is ignored.
- **Colour:** off pitch a tint of `primary` at 80 % (60 % was too dim on dark backgrounds); in tune the "in tune" colour with a soft halo; without a reading a faint line.
- **No words for the distance:** during a note the pill stays empty and uncoloured (it keeps its place); in tune a small check mark (Phase 26) shows in its middle in the "in tune" colour, or at its start while a tip or the tune hint fills it, and fades out where it was, so colour-blind players see in tune too; and the frequency line is left out; in tune shows in the note's colour, glow and pop. With the tune hint on, the pill shows "Tune up ↑" / "Tune down ↓". TalkBack still hears the cents.
- **Drawing:** the frame loop runs only while there is a reading, with `withInfiniteAnimationFrameNanos` (UI tests skip infinite animations), and redraws only the view's own layer, without recomposing. `WaveView` is `clearAndSetSemantics {}` (test tag `TunerTestTags.WAVE` only); `NoteDisplay`'s live region says the reading, and the sentence never changes between frames.
- **Layout:** 240 × 40 dp at any font size (30 dp in the compact note on a phone on its side). In two-pane on a short screen the note and wave get smaller so the readout fits.

### Strobe look
The first wave look: two rows of stripes that drift right when sharp, left when flat, and stand still within half a cent, for the last cent of fine tuning. `drawWave` passes `WaveMotion.phase` to `drawStrobe` (`dial/Strobe.kt`) in the current style's own marks (see *Visual styles*), the lower row at twice the speed (`phase · 2`), like the rings of a strobe disc. The marks fade over the outer fifth at each end (`strobeFade`, by position only, so the wrap stays seamless). Without a reading the rows shrink to half height in the faint resting colour. On the note it freezes, as every look does. It was a separate third display until October 2026; now every look shares one view and one set of layout tests.

### Wave looks
Setting "Wave look", shown while the display is the wave: six looks (`WaveLook`: strobe, ribbon, dots, fireflies, loop, ripples, in that grid order), picked from `WaveLookPicker` cards with live previews (`LookCardGrid`, as the meter picker).
- **One cue, each in its own way:** off pitch something moves one step of the look per strobe period (`WaveMotion.phase`), right or outwards when sharp, left or inwards when flat; within half a cent everything stands still. `unrest(depth)` (0 on the note, ~0.4 a cent off, 1 at 50 cents) shows distance from afar and eases to nothing, so every look settles into one calm shape on the note.
- *Strobe:* see above. *Ribbon:* pulses drift and smooth out (`dial/SoundRibbon.kt`, in each style's marks). *Dots:* a dot-matrix strip scrolling one dot per period (`dotColumnAt`, `edgeFade`). *Fireflies:* eight specks per pulse riding the pulses, scattered by `unrest`, gliding into an even line on the note (`fireflyAt`). *Loop:* a hoop spinning like a coin at the beat rate, its brighter near half sweeping the way the note is off, settling face-on into a still ring (`loopAt`, `loopWidth`, `loopNearSide`). *Ripples:* five rings spreading out when sharp and drawing in when flat, swelling unevenly off pitch, smooth ovals on the note (`rippleAt`, `rippleWobble`).
- Strobe and ribbon use each style's own marks; the other four have one shape in the style's colours.
- Every position is a continuous periodic function of `phase`, so nothing jumps when the direction flips or the phase wraps. JVM tests check each function for direction, stillness on the note and no jumps.
- Drawing allocates nothing: one `Ribbon` refilled, the caller's `Path` reused, strokes from `roundStroke` / `buttStroke`, cached per quarter-pixel width. `drawWave` (`dial/WaveLooks.kt`) draws them; the settings previews use the same `drawWave` through one shared `WaveMotion`.
- **Tests:** `WaveViewTest` (every look in every style drawn inside its box, at most a 4 dp glow outside; motion without recomposing), `TunerContentTest` (TalkBack skips the wave and hears the reading once), `SettingsContentTest` (radio buttons, names on one line at 1.3× and 2× font). The wave's size is the same for every look, so the layout tests cover all six.

### Visual styles
Six styles, in the owner's order (Phase 14, October 2026): Ancient, Classic, Retro, Contemporary (the default, and the only one that can follow the wallpaper), Futuristic and Space Age. Versions before October 2026 had seven; a saved Prehistoric or Middle Ages opens as Ancient (see *Saved settings*). Colours, faces, shapes and backgrounds follow the approved mock-up [docs/design/theme-styles-preview.html](docs/design/theme-styles-preview.html) (its data block is the source). Each style owns one accent hue round the colour wheel (Ancient terracotta, Retro avocado, Futuristic cyan, Contemporary blue, Space Age violet, Classic burgundy); greens are kept for "in tune". Each style sets:
- **Palette** (`StylePalettes.kt`): a light and a dark `Palette` of the mock-up's roles (background, surface, ink, muted, track, accent + onAccent, inTune + onInTune, and `second`/`third` for background art only, never text), copied exactly, turned into a Material 3 `ColorScheme`: primary = accent; primary and secondary containers (selected segments, chips, the slider's track) = surface mixed 22 % (light) / 32 % (dark) with the accent; secondary/tertiary = second/third (the background reads them there, so Contemporary's wallpaper colours reach it); outline = muted, outlineVariant = track. `StylePaletteTest` holds every palette, light and dark, to WCAG 2.2 AA: 4.5:1 for ink, muted, accent and inTune on the background, surface and surface container, for onAccent/onInTune on their fills and for text on every container; the meter's numbers (ink at 80 %) 4.5:1 and its minor ticks (ink at 50 %), centre mark and outlines 3:1. It also keeps the accents at least 30 degrees apart in hue and out of the greens.
- **Lettering** (`StyleTypography.kt`): a display face for the note, headlines and titles, a number face for readouts and the meter (`numberFontFor`), plain reading text. Ancient: Caesar Dressing, numbers in Alegreya Sans Medium (Caesar Dressing's 0 looks like a diamond). Classic: Playfair Display 400, numbers in Bodoni Moda 500 (optical size 14), serif reading text. Retro: Righteous. Contemporary: the phone's font, light. Futuristic: Orbitron 500 (+0.06 em on titles), numbers Orbitron 500. Space Age: Michroma (+0.02 em). Every text style, and the meter's numbers, ask for lining figures (`fontFeatureSettings = "lnum"`, `LINING_FIGURES`), so a 0 never looks like an o (Playfair Display's own figures are old-style; faces without the feature ignore it). Bundled under the SIL OFL (`core/designsystem/src/main/res/font`, licences in `assets/licenses`, credited on the About page via `bundledFontCredits`): Caesar Dressing, Alegreya Sans (one weight), Playfair Display, Bodoni Moda (variable, upright only), Righteous, Orbitron, Michroma. About 0.95 MB of font files, nothing downloaded.
- **Music signs** (`MusicSigns.kt`): none of those faces has ♯ or ♭, and the fallback drew them at a different size in each, so every ♯ ♭ ♮ ♩ ♪ comes from `music_signs.ttf` (Noto Sans Symbols cut to those glyphs, 2.6 KB, `scripts/subset-font.py`). `musicText()` sets a sign after a letter like a chord symbol (0.7 em and raised; ♭ 0.8 em). The text itself is unchanged, so UI tests see "C♯"; TalkBack hears words via `NoteNameSpeech`.
- **Shapes** (`shapesFor`, mock-up corners: `small` = the cents pill, `medium` = look cards and tips): uneven pebbles for Ancient, fine 4 dp corners for Classic, fat 18 to 22 dp curves for Retro, Contemporary's round ones, corners cut on every side for Futuristic, capsules for Space Age. String buttons (`StringChipShape.kt`: `stringChipShape(style, index)` and `stringChipSize(style)`, shared by the tuner and the mood cards) are pebbles (six, no two alike), ivory keys (38 x 50 dp, the name low, a shaded front edge: `stringChipShading`), soft hi-fi buttons (lit from above, shaded below), circles, bevelled neon tiles (see-through with an accent outline at 55 %, the picked one glowing: `neonGlow`; Futuristic's mode switch is outlined the same way) and capsules, at the mock-up's proportions; in the tuner each sits in a touch target of at least 48 dp each way (`minimumInteractiveComponentSize`), and the compact row's small ones shrink to fit 32 dp. Rows of 7 or 8 strings that don't fit shrink every button alike, keeping its proportions (see *Tuner screen*, *String row*).
- **Background** (`StyleBackdrop`): drawn once by `MainActivity` behind every see-through screen (`Scaffold(containerColor = Transparent, contentColor = onBackground)`), in its own offscreen `graphicsLayer` (`CompositingStrategy.Offscreen`), so the tuner's readings at up to 120 Hz only reuse a cached texture; seeded random numbers make it the same every time. The mock-up's motifs, ported one to one at 1 unit = 1 dp: Ancient a stone wall (grit, soft patches) with a terracotta hand stencil and rows of scratched tally marks; Classic velvet folds, a spotlight and the gold curves of a concert-hall shell; Retro avocado, mustard and orange rainbow bands curving in from the left; Contemporary two soft washes; Futuristic a neon perspective grid low on the screen with a magenta horizon glow (and scan lines by night); Space Age a violet starfield with orbits and an orange ringed planet by night, silver atomic orbits and starbursts by day. Every screen but the tuner (metronome, settings, About, the tuning editor) gets the quiet version (`quiet = true`: no hand stencil, softer folds and bands, no Futuristic horizon line, which ran through the metronome's see-through Start / Stop button, no Space Age twinkles, starbursts or planet). Bright motifs stay in the outer fifths (`sideX`), away from the note and pill; on its side, where the note column takes the right and the meter starts a tenth in, they keep to the strip left of the meter (Ancient's hand stencil moves to the corner above the meter's left end), and Space Age's planet is sized by the shorter side. Nothing is fixed to the screen's edges; the settings list ends 24 dp above the bottom inset.
- **Mood card** (`StyleMood.kt`): the style's picture on its card in Settings (4:5, from the approved mock-up `docs/design/theme-styles-preview.html`): its background (`StyleBackdropPreview`: the motifs at the mock-up's card scale, 2.2 times the card's share of a 393 dp phone, plus a soft wash of the accent from below), a big "A" in its display face, a strip of its ribbon marks in its accent colour (never "in tune", so each card keeps its own colour) drifting gently 3 cents sharp, and two string buttons (E, A picked) in its shape and the mock-up's card sizes (keys and capsules taller). Sized by the card's width, so it looks the same at any font size; hidden from TalkBack (the card says the name). The per-style hand-drawn dials of the old style cards went with them; `dial/DialGeometry.kt` keeps only the shared ±50-cent angle.
- **Sound ribbon** (`dial/SoundRibbon.kt`) and **strobe** (`dial/Strobe.kt`): the ribbon and strobe looks in each style's own marks, as the mock-up's `mark` and `period`: Ancient fingertip dabs with a smudge (13 dp apart), Classic an engraved band (fill 32 %, 1.7 dp outline, a hairline through it; strobe bars between two hairlines), Retro a glowing phosphor band (strobe: backlit bars), Contemporary rounded voice-memo bars, Futuristic thin neon bars that always glow softly, Space Age pairs of stars (strobe: twinkles over glowing dots); `stripePeriod` 8–13 dp. Every stripe of a row looks the same, so the pattern wraps without a jump.

`TwangleTheme(style, darkTheme, dynamicColor)` provides the `ColorScheme`, `Typography`, `Shapes` and `LocalStyleTokens` (`StyleTokens`: the style, its "in tune" pair, the unfaded scheme), remembered per style and brightness. A style or brightness change fades every colour over 450 ms (one `Animatable`) and cross-fades the background. Each mood card wraps its own `TwangleTheme`, so it previews that style whatever the current one is.

### Metronome screen
Phase 19 (`:feature:metronome`), after the approved mock-up [docs/design/metronome-nav-preview.html](docs/design/metronome-nav-preview.html) (its top comment is the spec). **Owner decided (2026-10-14):** keep the round tempo dial; everything else as shown; bar variant B (Frameless) for the navigation bar (§6, *Navigation bar*), which it shares the window with (it opens from the Metronome tab; switching tabs stops it).
- **Layout, upright** (one column, at most 480 dp, scrolls with very large fonts): the meter picker (2/4 3/4 4/4 5/4 6/8 7/8, where the tuner's mode switch is; one radio group "Beats in a bar"; 50 dp buttons so six fit a 360 dp phone, wrapping at very large fonts), the beat lights (64 dp), the tempo dial (288 dp, smaller on a narrow phone), − Tap tempo +, Start / Stop, "Vibrate on the beat"; the free height shared evenly between the groups. **On its side** (≥ 600 dp wide and wider than tall): the dial (up to 300 dp) at the start, the rest in a scrolling column beside it. The quiet background, as Settings.
- **Tempo dial** (`TempoDialArt` in `:core:designsystem` `metronome/`, gestures and TalkBack in `TempoDial`): frameless on the meter's calm field, 30–250 BPM clockwise over 300° (`dialDegrees`), the gap at the bottom; a tick every 10 BPM with the meter's scale rules (major ticks and numbers at 30, 50, 100, 150, 200, 250; numbers kept 3u clear of their tick's end whichever way it points), the style's arc finish unlit over the range and lit in the accent up to the tempo, the style's needle inside the arc pointing at it. The tempo sits in the middle in the style's number face (58 units, fixed like the tuner's note; the mock-up draws it in the number face, which also spares Ancient's display face its diamond 0), "BPM" and the Italian marking under it (growing with the font up to 1.3×). A touch on the ring sets the tempo it points to, a drag follows the finger (a touch in the gap keeps to the nearer end, `bpmAtTouch`), saved when the finger lifts. Only the ring reacts (`isOnDialRing`: from 74 units out, 20 inside the arc and just clear of the tempo's figures and marking at their widest, to the dial's edge at 144), so a tap on the tempo or "BPM" in the middle does nothing; until Phase 26 it jumped the tempo to 30 or 250, as the middle's angle is anything. A drag that started on the ring follows the finger anywhere but the middle (`isClearOfDialMiddle`), past the dial's edge too. `TempoDialTest` (JVM) checks the angles, the gap, the ring and its scaling. TalkBack: one slider "Tempo, drag to change", "96 beats per minute, Andante" (Dutch "96 slagen per minuut", the usual Dutch for BPM), 30–250 in 1 BPM steps (`progressBarRangeInfo` + `setProgress`).
- **Beat lights** (`BeatLightsArt`): one mark per beat of the bar in the style's own wave mark (Ancient dab, Classic engraved band, Retro phosphor band, Contemporary rounded bar, Futuristic neon bar, Space Age star pair), beat 1 largest, group starts (`BeatAccent.GROUP`) middle sized, the plain beats smallest; beat numbers under them. The beat heard lights up in the accent (never in-tune green) with a soft glow and eases (200 ms) to a resting 40 % until the next. Hidden from TalkBack.
- **The beat** (`BeatClock`): `MetronomePlayer.beats` gives each click with the moment it is heard; a frame loop (`withInfiniteAnimationFrameNanos`, only while playing, skipped by UI tests) moves only the lights and one soft accent glow behind the tempo (220 ms decay, full on a downbeat, 75 % on a group start, 55 % otherwise), read in the draw phase, so playing never recomposes. Changes are heard from the next beat (≈ 0.12 s).
- **Controls**: see-through buttons in the style's shape (`shapes.small`, round − and + in Contemporary and Space Age) with a muted outline; picked ones in the container colour with an accent outline; Start in the accent; Futuristic's as neon outlines (Start / Stop's 14 % accent tint lies on the background colour, so the grid's lines don't show through it). The meter buttons are radio buttons heard by name ("Six-eight time", Dutch "Zesachtstemaat"), as TalkBack would read "3/4" as a date or a fraction. − / + step 1 BPM ("Slower", "Faster"); Tap tempo (`TapTempo`, §3) counts the touch, lights up for 120 ms, and TalkBack's double tap counts too. "Vibrate on the beat" (off by default) buzzes the motor directly (as `InTuneHaptic`): `EFFECT_HEAVY_CLICK` on the downbeat, `EFFECT_CLICK` otherwise (35 / 18 ms one-shots before Android 10).
- **State** (`MetronomeViewModel`): tempo, meter and vibration, each saved at once (a dial drag when the finger lifts); opens stopped at the saved values (passed in from the settings already read, so the first frame is right). It stops the clicks when cleared; the screen stops them when it leaves (§5), but not for a configuration change (the activity's ViewModel and the app's player live on, so the clicks play on and the new screen shows them).
- **Tests**: `MetronomeViewModelTest`, `TapTempoTest`, settings tests (JVM); `TempoDialTest` (JVM); `MetronomeScreenTest` (opens stopped, Start / Stop, ± and meter reach the player and are saved, the dial by touch on its ring and by TalkBack, a touch on its middle does nothing, labels, vibration switch, tap tempo, leaving stops it, Dutch at 2× on its side) and `MetronomeStylesTest` (every style light and dark: fits without scrolling on a 360 dp phone, the Xiaomi at 1.25× and on its side, nothing overlaps; at 2× every control wholly shown).

### Home-screen widget
Phase 20 (`:app` `widget/`). A tile for the home screen, three cells by one (resizable across, down to two): the navigation bar's tuning fork in the accent, the instrument and tuning as the tuner names them ("Guitar · Standard", a custom tuning by its own name, "Chromatic" in chromatic mode) in ink, and "Open the tuner" ("Open de stemmer") in the muted colour under it, on a rounded tile in the style's background colour (corners: the launcher's own on Android 12+, 16 dp before). No border, no art: calm beside other widgets. A tap anywhere opens Twangle on the tuner.
- **Tech: plain `RemoteViews`** (`layout/widget_tuning.xml`, an `AppWidgetProvider`), not Jetpack Glance. The widget is one static layout with three values to fill in; Glance would add a library, a second Compose runtime for widgets and a WorkManager-backed session for no gain here. Text sizes come from the layout (the title shrinks from 16 to 11 sp to fit, `autoSizeTextType`), the face is the system's medium sans: `RemoteViews` can't take the styles' bundled faces without a layout per style, and the colours already carry the style.
- **Colours** (`TuningWidget.paint`): the style's scheme as the app ends up with it (`colorSchemeFor` in `:core:designsystem`, wallpaper colours for Contemporary with Material You on, `usesWallpaperColors`): background, `onBackground` (ink), `onSurfaceVariant` (muted) and `primary` (accent), set as colour filters on the tile and the fork and as text colours. With the theme on "System" on Android 12+ both sets go in (`setColorInt` light/night), so the launcher follows the phone's dark mode without a redraw; otherwise the set for the current brightness. The picker's preview (Android 12+, `previewLayout`) is the layout itself in Contemporary light or dark (`values/widget.xml`).
- **Kept up to date by the app, never on a timer** (`updatePeriodMillis` 0): `TwangleApplication` follows the settings (`TuningWidget.follow`) for as long as its process lives and redraws the widgets when what they show changes (`WidgetState`: mode, instrument, tuning, custom name, style, theme, wallpaper colours; A4 or the meter's look change nothing), and when the configuration changes (language, dark mode before Android 12). `TuningWidgetReceiver` draws a widget when it is placed and redraws on the phone's `LOCALE_CHANGED`, reading the settings off the main thread (`goAsync`). With no widget placed, a redraw is one `getAppWidgetIds` call.
- **One tap opens the tuner** (`TuningWidget.openTuner`): an immutable `PendingIntent` to `MainActivity` with `ACTION_OPEN_TUNER` and `NEW_TASK | CLEAR_TOP | SINGLE_TOP`. A cold start opens on the tuner anyway; an open app gets `onNewIntent`, which counts a request, and `TwangleApp` switches to the tuner (an open tuning editor closes as with Back, dropping its draft).
- **Never the microphone:** the widget and its receiver touch only the settings. The mic opens only when the tuner it opens is shown, exactly as from the launcher (§5), and the tuner asks for the permission there.
- **TalkBack:** the tile is one button; the title reads as the tuner's button does ("Guitar, Standard"), then "Open the tuner".
- **Tests:** `WidgetStateTest` (JVM: names, custom tuning, chromatic, which changes redraw); `TuningWidgetTest` (device: the views applied as a launcher does show the names in the style's colours and are tappable; drawing them records nothing; the tap's intent brings the open app from Settings back to the tuner).

### Watch app (Wear OS)
Phase 20 (`:wear`). A standalone Wear OS app (`com.google.android.wearable.standalone`): it listens with the watch's own microphone and needs nothing from the phone. Compose for Wear OS (`androidx.wear.compose` Material 3, `AppScaffold` with the time at the top), minSdk 30 (Wear OS 3).
- **Same application ID as the phone** (`io.github.klaboukes.twangle`), as Wear OS and Play expect for a phone app and its watch app; namespace `…twangle.wear`. **`versionCode` = the phone's + 1,000,000** (1,010,000 for 1.0.0), because Play needs a different code for each build; both come from `twangle.version` (§4, *Release build*). The release build is signed with the phone's upload key. The launcher icon is the phone's adaptive icon (copied into `wear/src/main/res`).
- **The pitch engine is the phone's**: `WatchPitchPipeline` runs `:core:dsp`'s `FrameAssembler` → `SignalGate` → `SustainCheck` (with its own noise floor for the room rule) → YIN (`AnalysisSettings.newPitchDetector`) → `PitchSmoother` → `InTuneDetector` (the phone's default window: within 5 cents for 300 ms, released past 7), with frame sizes from the recorder's rate, so a 16 kHz watch mic gets the same window and hop as 48 kHz. On a watch-class core it costs about 13–20 % of the CPU (§4, *Watch CPU and the native detector*). It leaves out the phone's extras (SNR, reception, tips, strum check, low-note window, precision setting): chromatic, A4 = 440 Hz, sharps. It allocates nothing per frame and sends a new `WatchTunerState` (`Listening`, `Detected(note, cents, inTune)`, `Failed`) only when the note, the whole cents or "in tune" change. A note lost for a moment stays on screen 0.6 s beyond the smoother's own hold (as long as the phone's glow bridges a dropout) and keeps "in tune" if the same note comes back, so the watch never flickers between a reading and "Play a note".
- **The microphone is `:core:audio`'s `AndroidAudioRecorder`**, unchanged: unprocessed source, then voice recognition, the watch's native rate, the built-in mic while a Bluetooth headset is connected.
- **Microphone lifetime** as on the phone: `WatchTunerViewModel.state` is `stateIn(WhileSubscribed(5_000))` and the screen collects it with `collectAsStateWithLifecycle()`, only once `RECORD_AUDIO` is granted. The permission is asked for when the app first opens; afterwards a button asks again, or opens the app's page in the watch's settings once Android stops showing its dialog. `rememberWatchMicPermission` follows the phone's `MicPermissionRules` (§5): a first dialog dismissed without an answer keeps "Allow microphone", and only a real "don't ask again" leads to settings. A refusal is remembered in the watch's own small `SharedPreferences` file (`twangle_wear`, `mic_refused`), as the phone keeps it in its settings (Phase 26; before, a dismissed first dialog went to settings). `WatchMicPermissionTest` on the JVM. A busy or broken mic shows a message with "Try again".
- **Screen off and ambient let go of the mic at once.** On Wear OS the activity stays *resumed* when the screen dims to ambient (always-on) or goes off (seen on the emulator: display `DOZE`, Twangle still the top resumed activity), so the lifecycle alone would keep the mic open. `ScreenOnEffect` listens for `ACTION_SCREEN_OFF` / `ACTION_SCREEN_ON` (sent when the display leaves or enters interactive mode, ambient included) and checks `PowerManager.isInteractive` on start; the view model then switches its upstream to a plain `Listening`, without the 5 s grace, and opens the mic again when the screen comes back. The app doesn't declare ambient support, so the watch shows the system's ambient view. Measured on the emulator: the mic is released within 0.9 s of `KEYCODE_SLEEP` (most of it adb) and reopened on wake; Home still keeps the 5 s grace.
- **Screen:** a ring along the edge (inset 6 % of the smaller side, so it sits the same on round and square screens), with the cents scale at its top: ±50 cents over ±60° either side of 12 o'clock, a tick every 10 cents and a longer one in ink at the target. A dot in the accent marks the reading and glides there (a low-stiffness spring), drifting back to the centre as it fades when the note stops. The note is large in the middle (30 % of the dial, light weight, the octave small beside it on the same baseline, a ♯ raised and smaller in the phone's cut of Noto Sans Symbols, bundled with its licence), the cents under it ("+12 cents", "−3 cents"), and "Play a note" while nothing is heard; reading and "Play a note" cross-fade (400 ms). Sizes follow the screen, not the font setting, so the reading always fits inside the ring (checked from 170 to 225 dp). The tuner leaves out the time, where the ring runs; the permission and error messages keep it.
- **In tune:** the ring, the dot and the note ease to the in-tune colour over 700 ms (`FastOutSlowInEasing`) with a soft band of light around the ring (a radial gradient, 35 % on the ring, fading to nothing 5 % of the dial either side), hold while the note is in tune and fade the same way. No pulse, no sparks. TalkBack hears the note, the cents and "in tune".
- **Colours** are the phone's default style, Contemporary dark (`WatchColors`: ink, muted, track, accent, in tune), on black. They are copied rather than shared because `:core:designsystem` brings the phone's settings, fonts and Material 3; `WatchDialTest` fails if they drift from `StylePalettes.kt`. The watch has no style choice.
- **Tests:** `WatchPitchPipelineTest` (JVM, synthetic notes through the fake recorder: A4 in tune, cents within 1 of the played pitch, a 16 kHz mic, silence, few states for a held note, in tune only after 300 ms, never at 20 cents, a new note earns it again, a 400 ms dropout keeps reading and glow, back to listening after the note stops), `WatchTunerViewModelTest` (mic closed until collected, released 5 s after, released at once when the screen goes off and reopened when it comes on, error and retry, note names) and `WatchDialTest` (angles, colours match the phone's). On the Wear OS emulator (AVD `Wear_OS_Large_Round`, Wear OS 6, 454 px = 227 dp round): `WatchTunerTest` (6 Compose tests: "Play a note", the reading, TalkBack's "in tune", cross-fade both ways, "Try again", the reading inside the ring from 170 to 225 dp). By hand it installs, records through voice recognition at 48 kHz (the emulator has no unprocessed source), shows the ring with "Play a note", lets go of the mic on sleep and takes it back on wake. The PC's microphone did not reach the emulator (host mic switched on, two short 440 Hz beeps from the laptop: nothing heard), so a live note was only seen through `WatchTunerScreenshots`. A real watch is the owner's check (ROADMAP, *Owner checks*).

### Landscape and wide screens
`tunerLayoutFor(width, height, compactLandscape)` (`TunerLayout.kt`, JVM-tested) picks the arrangement from the space, not the device: `SINGLE_COLUMN` (max 480 dp wide) unless the window is at least 600 dp wide *and* wider than tall. Then `COMPACT` by default, or `TWO_PANE` with the setting "Full layout on its side" (`keepTwoPaneLandscape`). `TunerScreenTest` checks both layouts and a live change on a phone on its side.

**Compact layout** (`CompactLayout`): only what matters while tuning, big enough to read from a distance. The note column is measured first and the meter takes all the width left (`FitGauge`, at most 840 dp, keeping 2:1; about 450 dp on the S26, twice its two-pane size). Mode switch, strum check switch and string buttons are hidden, and so is the navigation rail (with its Tuning item), so the meter gets the whole width (`TunerScreen` tells `MainActivity` through `onCompactChange`). Guitar mode shows a small string row under the note (32 dp chips, not buttons, hidden from TalkBack because the reading names the string; eight strings make the note column 284 dp wide and the meter that much narrower); chromatic with the wave shows the `ChromaticReadout`.
- **Tap for the controls:** a tap anywhere, or TalkBack's "Show controls" button, cross-fades to the two-pane layout, with the rail sliding in at the start, for 5 s (`COMPACT_CONTROLS_SHOWN_MS`), lengthened by Android's "time to take action" setting. Every touch restarts the time, and an open instrument and tuning panel holds it. Local UI state; a rotation starts compact again.
- **The hint:** when the compact layout appears, a quiet "Tap to show the controls" (body text in `onSurfaceVariant`, one line) sits at the bottom centre over the layout, so nothing moves, for 4 s (`COMPACT_TAP_HINT_SHOWN_MS`, lengthened by "time to take action"), then fades out (400 ms); a tap ends it at once. It shows a fixed time, never in and out with the sound, and TalkBack skips it (the screen is already its "Show controls" button).
- `CompactLandscapeStylesTest` checks every style and meter look on a phone and a tablet on their side (fit, no overlap, reachable at 2× font, drawn in light and dark, "Show controls" works). Layout runs in the light theme only: a style's fonts and shapes don't change with dark.

**Two-pane layout** (`TwoPaneLayout`, also shown while the compact layout's controls are up):
- **Readout pane** (start): `GaugeAboveNote` measures the note first and shrinks the meter (2:1, 160–560 dp wide) so both fit a phone on its side (~330 dp tall).
- **Controls pane** (end): mode switch, strum check switch and strings, max 480 dp, with 56 dp clearance top and bottom: a margin when the column scrolls (very large fonts). It was first made room for the string-lock tip under the strings; it stayed when the tip went (Phase 24), because without it the controls would sit higher wherever the column only just scrolls.
- Each pane scrolls on its own with very large fonts; both screens use `WindowInsets.safeDrawing` (the camera cutout is at the side in landscape).
- The activity is recreated on rotation (no `configChanges`); mode and tuning are saved, the locked string lives in the ViewModel, and the 5 s grace keeps the `AudioRecord` session.
- **Settings** scrolls the full width but keeps its rows in a centred column at most 600 dp wide.
- **Right to left** (Arabic): both layouts mirror with the language, so the readout pane, the compact layout's note column and the rail sit on the right and the meter on the left; the meter, the string row and the other measuring graphics inside them stay left to right (see Languages).

### Accessibility
- **TalkBack:** `NoteDisplay` is one node whose description is the reading in words ("E 2, 12 cents flat, tune up", "F sharp 2, in tune", "Play a string"), a *polite live region*; its visible texts are `hideFromAccessibility()`. `SpokenReadingThrottle` (pure) decides what TalkBack gets from ~47 updates a second: the first text at once, a new note or in-tune change after 400 ms, losing the note after 1.5 s, cents-only changes at most every 2 s. The meter and wave are hidden (`clearAndSetSemantics {}`).
- **Separators:** where code joins spoken parts (the panel's open strings, the strum check's "12 cents flat, tune up"), the separator is `tuner_spoken_separator`: ", " in most languages, the Arabic comma "، " in Arabic, "、" in Japanese, "，" in Chinese, the same marks the languages' spoken format strings use.
- **Spoken note names:** every TalkBack text naming a note goes through `NoteNameSpeech` (`:core:designsystem`, `rememberNoteNameSpeech()`, tested against every name the app can show): readout, string chips, locked-string hint, the panel's tunings and notation choices. ♯/♭ become words ("C sharp"). `spoken_letter_names` (`res/values*/speech.xml`, not translated) picks how letter names are said: `words` ("C sharp"), `dutch` (cis, des, es, bes; b, not h) or `german` (Cis, Des, Es, As, B for B♭, His; naturals as written, so the German notation's H is said "H"; speech never changes which note a name means, so English letters picked in German still say "B" for B). Solfège keeps the sign as a word ("Sol kruis", "Mi mol"), and `spoken_solfege` spells the syllables the way the language writes them so TalkBack pronounces them right (French Ré, Portuguese Dó Ré Fá Lá, Arabic دو ري مي; the screen still shows Do Re Mi). Polish says letter names the German way (cis, es, b, h). A new language sets these two only if it differs from the default. The octave is the number on screen ("cis 4"). UI tests check Dutch with `DeviceConfigurationOverride.Locales`, which doesn't reach popups or the panel's window, so the Dutch panel is checked on the phone.
- **Labels:** strings read "A 2" (on every instrument, "F sharp 1" on an 8-string) plus "selected" / "Locked" and the lock action, and the long-press action "Play A 2" (while a tone sounds: "Playing" and "Stop the tone", and the hint "Playing A 2"); the navigation bar's Tuning item says "Tuning, Guitar, Standard", "double-tap to change instrument or tuning"; in the panel the title is a heading, instruments are radio buttons and tunings say their name and strings ("Half step down, E flat, A flat …"); the A4 slider reads "442 Hz". Settings rows are whole-row radio buttons and switches.
- **Large fonts:** the tuner body scrolls when taller than the screen (each pane on its own in two-pane). The 112-unit note name is in dp, so it doesn't grow further; string labels follow the font scale up to 1.3× (fixed 48 dp circles), and shrink further where a name would not fit its button. Squeezed 8-string rows give each button a touch area narrower than 48 dp (41 dp on a 360 dp phone), the only touch targets below 48 dp. A UI test checks every control is reachable at 2× font.

### Languages
- **English (default), Dutch, German, French, Spanish, Italian, Portuguese (Brazil), Chinese (Simplified), Japanese, Korean, Hindi, Indonesian, Russian, Turkish, Polish and Arabic.** Register: German, Spanish, Italian and Dutch use the informal you (du, tú, tu, je), French uses vous, Brazilian Portuguese você. French puts a no-break space (U+00A0) before : and ? and inside « ». Brazilian Portuguese calls the guitar "Violão" ("guitarra" is the electric one). Chinese uses 你, Japanese polite です/ます for sentences and short plain labels, Korean 해요체, Hindi आप with the loanwords Indian guitarists use (ट्यूनर, ट्यूनिंग, स्ट्रम), Indonesian Anda and the guitarist's *stem* (tuning), *genjreng* (strum), *kres*/*mol* (♯/♭). Chinese says a sharp before the letter (升C) and reads 2/4 as 四二拍. Chinese, Japanese, Korean and Indonesian have only the plural quantity "other"; Hindi has "one" and "other". Russian and Polish use the informal ты/ty and their guitarist words (тюнер, строй, подтяни/ослабь; stroik, strój, podciągnij/popuść); Turkish uses the short sen imperative (akort, tel, yükselt/düşür). Russian and Polish plurals have one/few/many/other (1 цент, 2 цента, 5 центов, "other" for fractions; 1 cent, 2 centy, 5 centów, 12 centów), Turkish one/other with the noun in the singular (12 sent). Russian writes Гц for Hz. Text set in capitals in code uses the app's locale (`uppercase(LocalConfiguration.current.locales[0])`), so Turkish i becomes İ; Kotlin's plain `uppercase()` is locale-free. Cyrillic is only in Playfair Display and Alegreya Sans, so in Russian the titles of Ancient, Retro, Futuristic and Space Age come from the phone's font (whole words, since every letter falls back); Caesar Dressing (Ancient) lacks ğ İ ş and the Polish ą ć ę ń ś ź ż, and Orbitron (Futuristic) also lacks ł, so Turkish and Polish titles in those two styles mix faces within a word. No style font covers Han, Kana, Hangul or Devanagari, so those glyphs come from the phone's own fonts (Android falls back per glyph); styles' letter-spacing still applies to them. Indonesian's folder is `values-in` (Android's old code; a phone set to `id` resolves to it). Arabic is Modern Standard Arabic with the masculine imperative of app texts (اعزف وترًا, اختر وترًا) and the words Arab guitarists use: الموالف (tuner), الدوزان (tuning), وتر/أوتار (string/strings), شُدّ/أرخِ (tune up/down), دييز/بيمول (♯/♭ spoken), اضرب (strum); Drop D, Open G and Low G stay in Latin letters, like Russian. Its plurals use all six quantities (zero, one, two, few, many, other: ٠ سنت, بسنت واحد, بسنتين, ٣ سنتات, ١١ سنتًا, ١٠٠ سنت). No style font has Arabic, so it comes from the phone's font. Each module keeps its texts in `res/values/strings.xml` with a copy per language in `res/values-<language>/strings.xml`; brand and symbols (`app_name`, `DADGAD`, ♯/♭, ♪) are `translatable="false"`. Font and library names are proper names and stay in English.
- **One language list:** `twangle.languages` in the root `gradle.properties` (`en,nl,de,fr,es,it,pt-rBR,zh-rCN,ja,ko,hi,in,ru,tr,pl,ar`), as Android resource qualifiers (`de`, `pt-rBR`, `zh-rCN`, `b+sr+Latn`). The first is the default, whose texts are in `res/values/`.
- **In-app language (Settings → Language):** the same choice as phone Settings → Apps → Twangle → Language, made inside the app, on every Android version. `SettingsScreen` reads and sets it with AppCompat's `AppCompatDelegate.getApplicationLocales` / `setApplicationLocales`: on Android 13+ that is the system's per-app language (so both places always agree), on Android 8–12 AppCompat keeps it in a file of its own (`autoStoreLocales` on `AppLocalesMetadataHolderService` in `:app`'s manifest) and sets it on the activity, which is why `MainActivity` is an `AppCompatActivity` (its window theme `Theme.Twangle` derives from `Theme.AppCompat.Light.NoActionBar`, and `Theme.AppCompat.NoActionBar` in dark mode; Compose draws everything, so nothing else of AppCompat shows). The languages come from `BuildConfig.LANGUAGES`, which `:app`'s build file fills from `twangle.languages` like `localeFilters`, so the setting offers exactly the system list (`LocalizationTest` checks the build file). `AppLanguages` (`:feature:settings`, JVM-tested in `AppLanguagesTest`) turns qualifiers into language tags (`pt-rBR` → `pt-BR`), names each language in its own words with a capital ("Polski", "Português (Brasil)"; Chinese by its script, 简体中文, as Android's own list does) and matches a regional variant picked in phone Settings to its language. Names are not translated, and each carries its language (a `SpanStyle` `localeList`, which reaches TalkBack as a `LocaleSpan`), so TalkBack reads "Polski" in Polish and Han characters get their Chinese or Japanese forms. A switch recreates the activity; texts, digits and the note-name default (`appLanguage()`, from the configuration) follow at once, and Settings stays open. The home-screen widget is redrawn in the new language (`onLanguageChange` → `TwangleApplication.redrawWidgets`; Android 13+ also through `onConfigurationChanged`); on Android 8–12 it takes the language from AppCompat (`TuningWidget.inAppLanguage`), so in a process started for the widget alone, before the app has been opened since the phone started, it shows the phone's language until then. The Play Store bundle doesn't split by language (`bundle.language.enableSplit = false`), so every language is installed and one the phone doesn't use works at once. The watch app has no setting and follows the watch's language.
- **Per-app language (Android 13+):** `:app` sets `androidResources.generateLocaleConfig = true` with `res/resources.properties` (`unqualifiedResLocale=en`). Both `:app` and `:wear` set `localeFilters` from `twangle.languages`, so the generated locale config (the in-app language list) holds exactly the listed languages, and library texts never appear in an unlisted one. The locale config takes a language from any resource, libraries included (Compose and AndroidX ship most languages), so a listed language shows up in the list even before Twangle's own texts exist; the guard below is what keeps the list honest.
- **Formatting:** plurals for counts (`tuner_cents_flat/sharp`) and placeholders for numbers (`%1$.1f Hz`), so Dutch shows "440,0 Hz". **Digits** follow the app's language as Android's resources format them (`String.format` in the app locale): Arabic gets Arabic-Indic digits (٤٤٠ هرتز). Numbers the app draws itself (the meter scales, the tempo dial and its BPM, the beat numbers, the time signatures ٣/٤, the watch's "+١٢") go through `localDigits` (`:core:designsystem`; `MeterRoles.digits`), so every number on a screen uses the same digits; literal numbers in an Arabic text are written ٠–٩ too. Note names keep their octave in 0–9 (A4, E♭2): they are Latin symbols, and a Western digit after a letter stays in the letter's left-to-right run (Unicode bidi rule W7), so "E♭2" can't come apart inside Arabic text, where an Arabic-Indic one would move the ♭ in front. Note names are not translated; they follow the notation setting, whose default follows the language (*Notation by language*). Chinese, Japanese and Korean text may break between any two characters, so a one-word label in a width-sharing row (the mode switch) is measured at its full one-line width, not its narrowest.
- **Right to left (Arabic):** both manifests set `android:supportsRtl="true"`, so Compose mirrors the layout: texts, rows, settings, panels, the navigation bar and rail, the mode switch, the meter picker, switches, the tour's buttons; the back arrow and the settings chevrons are `autoMirrored` vector drawables. What stays left to right, after Material's rule not to mirror graphs, gauges and clocks, and because low pitch sits left like a keyboard and a stave: the meter (flat left, sharp right; drawn on a `Canvas`, whose coordinates never mirror), the wave, the strum check, the string row and the style cards' little strings (`CompositionLocalProvider(LocalLayoutDirection provides Ltr)`), the tempo dial (clockwise, like a clock) with − slower left and + faster right below it, the beat lights (counted left to right, as in sheet music), the A4 slider with its − and + (a pitch scale), and the tuning editor's − note + group. A note name with its octave (the big note, the watch's) is also wrapped left to right, so the octave stays right of the letter. Compose sets a paragraph's direction from the layout, not from its text, so a list of note names in a right-to-left screen is given `TextDirection.Ltr` (the panel's open strings, else "E♭ … E♭" puts its last ♭ in front). The play ▶ icon isn't mirrored (Material: media controls keep their direction).
- **Guard:** `LocalizationTest` (JVM, `:app`) reads `twangle.languages` and fails when:
  - a module's English string has no copy in a listed language, or the copy's placeholders differ (for plurals: the "other" item must match, every other item may only use placeholders of "other", and only Android's quantities are allowed);
  - a `values-<x>/strings.xml` exists for a language that isn't listed;
  - the first language isn't `unqualifiedResLocale`, or an app module doesn't take `localeFilters` from the list;
  - Kotlin passes a hard-coded literal to `Text(...)`, `contentDescription`, `stateDescription`, `onClickLabel` and similar.

  Every module's `res` and Kotlin sources, the build files and `gradle.properties` are declared inputs of `:app`'s unit tests, so changing any of them reruns the test. Lint's `MissingTranslation` and `StringFormat*` back it up.
- **Adding a language:** append its qualifier to `twangle.languages`, then add `res/values-<language>/strings.xml` to every module that has a `res/values/strings.xml` (today `:app`, `:wear`, the three features and `:core:designsystem`), translating every translatable string and plural. `LocalizationTest` names what is missing. Nothing else changes: the language list on the phone and the watch's texts follow. The `/add-language` skill walks through it, including the note-name default, TalkBack names, fonts and right-to-left checks.

### Fast UI tests
Compose UI tests use `createSharedActivityComposeRule()` (`:core:testing`): one activity for the whole run, a fresh composition (own recomposer, test clock and `ViewModelStore`) per test. `SharedActivityTestRunner` stops AndroidJUnitRunner closing every activity after each test, which took ~0.7 s per test on the Xiaomi 12X; together they cut the tuner suite from ~8½ to ~3 minutes. Pixel checks take one capture and cut it up (a capture costs a frame), and build assertion messages only on failure. A test that changes the activity itself (rotation, recreation, window flags) still uses `createComposeRule()` or `ActivityScenario`. How to write them: [writing-tests.md](.claude/skills/ui-test/writing-tests.md).

### Every screen in every style
`TunerStylesTest`, `SettingsStylesTest` (Phase 14) and `MetronomeStylesTest` (Phase 19) check each screen in each of the six styles, light and dark, because a style brings its own fonts and button shapes: the tuner upright (a narrow S26-sized phone at 1×, the owner's Xiaomi 12X at 1.25×, each less 80 dp for the navigation bar) and in its full layout on its side (less the 80 dp rail) fits without scrolling, nothing overlaps; at 2× text every part, Settings row, card name and About text can be scrolled to and is then wholly shown (`assertWhollyShown` in `:core:testing`: nothing clipped, no line cut off or ellipsized), and the string buttons fit the longest names (solfège flats); TalkBack hears the reading once, nothing in the meter or wave, the mode switch, strings, style/meter/wave cards and light-or-dark choices by name with which one is picked. `CompactLandscapeStylesTest` covers the compact layout, `MeterLooksTest` and `WaveViewTest` every look. The Phase 14 check ran them all in every style (`--all --thorough`) and on the Xiaomi 12X by hand (each style light and dark, upright and on its side, at 1.25× and 2× text).

### Quick and thorough UI runs
While the look is still changing (October 2026 until Phase 23), a normal run leaves out the double checks: style test classes (`TunerStylesTest`, `SettingsStylesTest`, `MeterLooksTest`, `CompactLandscapeStylesTest`, `StringRowStylesTest`, `TourStylesTest`, two checks in `WaveViewTest`) run in the default style only (`allIfThorough(VisualStyle.entries, VisualStyle.DEFAULT)`), and `@Thorough` tests (variants of a quicker test in another font size, language, orientation or view) are skipped. `--thorough` runs everything. This cut the tuner suite from ~3 minutes to ~1. Each family keeps its hardest case in the quick run (e.g. Dutch at 2× font on a phone on its side), so most layout breaks still show at once. The six styles were finished in Phase 14 (October 2026), but the double checks stay out of normal runs until Phase 23: phases 15 to 22 still add screens (instruments, the tuning editor, the metronome), and every increment would pay the thorough run (about 15 minutes on the Xiaomi 12X, which also heats the phone). Each increment that changes a style's look, fonts or shapes runs `--thorough` once before it lands.

## 9. Privacy
Audio is processed in memory and thrown away immediately. Nothing is recorded to disk or sent over the network, and there is no `INTERNET` permission. The merged manifest holds only `RECORD_AUDIO`, `VIBRATE` (in-tune tick, metronome beat) and AndroidX's internal `DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION`. The home-screen widget (§6) adds none: it shows the saved instrument and tuning on the home screen and holds no mic. The watch app (`:wear`, §6) asks only for `RECORD_AUDIO`, has no `INTERNET` either and stores only whether the microphone was ever refused.

The privacy policy is [PRIVACY.md](PRIVACY.md), with a Dutch copy in [PRIVACY.nl.md](PRIVACY.nl.md); keep the two in sync. Settings stay in DataStore on the device, and because `android:allowBackup="true"` (no extraction rules) Android's own backup and device transfer may include them. If a change touches permissions, stored data, backup or anything that leaves the device, update the policy (and its effective date) in the same change. The About page shows the gist; the Play listing will link to a public copy (Phase 23), and the data-safety form will say no data is collected or shared.
