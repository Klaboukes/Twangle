# Twangle — Architecture

Twangle is a chromatic and guitar-string tuner for Android. It listens to the microphone, finds the fundamental frequency of the note being played, and shows how far that note is from the target pitch, in cents.

## 1. Tech stack

| Concern | Choice | Why |
|---|---|---|
| Language | **Kotlin 2.x** | First-class Android language, null safety, coroutines. |
| UI | **Jetpack Compose + Material 3** | Declarative UI fits a screen that redraws ~30–60×/s from a single state object. Custom gauge/needle drawing is easy with `Canvas`. |
| Audio capture | **`android.media.AudioRecord`** (PCM float, mono) | Gives raw samples with no extra dependencies. A tuner can tolerate ~50–100 ms of latency, so Oboe/AAudio through the NDK isn't needed. |
| Pitch detection | **YIN algorithm in pure Kotlin** (`:core:dsp`) | Accurate to under a cent on monophonic instrument signals, and resistant to octave errors. Pure Kotlin keeps it unit-testable on the JVM with no device. |
| Async | **Kotlin Coroutines + Flow / StateFlow** | Audio frames → pitch → UI state is naturally a stream. |
| State holder | **AndroidX ViewModel** | Survives configuration changes and owns the audio pipeline's lifetime. |
| DI | **Manual (`AppContainer`)** | The object graph is tiny. Hilt would cost build time and add complexity without much benefit. Revisit if the graph grows. |
| Persistence | **Jetpack DataStore (Preferences)** (`:core:settings`) | Stores settings: A4 reference, selected tuning, notation, theme, keep screen on, tune up/down hint. |
| Build | **Gradle 9 + AGP 9 (built-in Kotlin), Kotlin DSL + version catalog** (`gradle/libs.versions.toml`) | Standard for modern Android. Versions live in one place. |
| Testing | JUnit 4 (JVM), kotlinx-coroutines-test, Compose UI test | DSP is checked with synthesized signals. UI is tested with Compose test rules. |
| CI | **GitHub Actions** (`.github/workflows/android.yml`) | test + lint + assembleDebug on every PR. The debug APK is uploaded as an artifact. |
| Min / target SDK | **minSdk 26** (Android 8.0) / targetSdk 37 | `ENCODING_PCM_FLOAT` and the `UNPROCESSED` audio source work reliably from API 24+. 26 covers about 97% of active devices. minSdk 26 also means adaptive icons need no PNG fallbacks. |

### Name, app ID and icon
- **Name:** Twangle (until October 2026: InTune, which clashed with Microsoft Intune). Names that advertise "free" were dropped: Google Play's metadata policy bans price words in titles.
- **App ID:** `io.github.klaboukes.twangle`, the usual reverse-domain ID for an open-source app hosted on GitHub. It was changed before the first store release, while that was still free. Kotlin packages and module namespaces live under it (`io.github.klaboukes.twangle.<module path>`).
- **Launcher icon:** a dark-brown string on gold that comes in at an angle, makes one round loop and leaves straight: tangled, then in tune. Where the straight part crosses, the string passes under it. It's an adaptive icon (`res/drawable/ic_launcher_foreground.xml` + `ic_launcher_background` colour), and the same foreground is the monochrome layer for themed icons (Android 13+ uses only its shape). The artwork stays within 32.2 dp of the centre, inside the 33 dp safe-zone circle every launcher mask keeps, so round, squircle and Samsung's shapes never clip it. `android:roundIcon` points at the same adaptive icon, which needs no separate round variant from API 26.
- **Opening screen:** `androidx.core:core-splashscreen` (`installSplashScreen()` in `MainActivity`, launch theme `Theme.Twangle.Starting`), so Android 8–11 look like 12+. It shows the icon's string on a gold tile: on full-screen gold in light mode and on dark warm brown (`#1C1510`) in dark mode (`values-night`). It follows the phone's dark mode, because the app's own theme setting isn't known before the app starts. It stays up until the settings are read and the first real frame is composed (`setKeepOnScreenCondition`), so there's no blank frame before the tuner. The window theme is dark in dark mode too, so nothing white shows behind it.

### Rejected alternatives
- **Flutter / React Native**: microphone DSP would go through platform channels, which adds latency and complexity for a single-platform app.
- **C++/Oboe via NDK**: lower latency, but a tuner doesn't need it. `PitchDetector` is an interface, so a native version can replace the Kotlin one if profiling shows a need.
- **FFT peak picking**: easily fooled by strong harmonics (guitar low E often has a weaker fundamental than its 2nd harmonic), and poor resolution at low frequencies. Time-domain YIN handles both better.

## 2. Module structure

```
:app               Android application: Activity, Application, AppContainer (DI), navigation
:feature:tuner     Tuner screen: Compose UI, TunerViewModel, UI state, gauge components
:feature:settings  Settings screen: A4 calibration and the other preferences, SettingsViewModel
:core:audio        Microphone capture: AudioRecord wrapper exposing Flow<FloatArray>, permission helpers
:core:settings     Saved user settings: SettingsRepository backed by DataStore
:core:designsystem Visual styles: TwangleTheme, palettes, fonts, backgrounds, the hand-drawn dials, StylePicker
:core:dsp          Pure Kotlin/JVM (NO Android deps): pitch detection, note math, tunings, smoothing
:baselineprofile   Android test module (com.android.test): Baseline Profile generator, startup benchmark
```

Dependencies ("→" = depends on):

```
:app               → every module below (it wires them together)
:feature:tuner     → :core:audio, :core:settings, :core:designsystem, :core:dsp
:feature:settings  → :core:settings, :core:designsystem (and through them :core:dsp)
:core:designsystem → :core:settings (for VisualStyle and ThemeMode)
:core:settings     → :core:dsp
:core:audio        → no other module
:core:dsp          → no other module
:baselineprofile   → drives :app on a device (targetProjectPath); nothing depends on it
```

Rules:
- `:core:dsp` is a plain `kotlin("jvm")` module. It must never import `android.*`. This keeps the most important code fast to test and reusable.
- `:core:audio` knows about Android audio but knows nothing about notes or UI.
- `:core:settings` knows how settings are saved, and nothing about audio or UI. It uses `Tuning` and `Notation` from `:core:dsp`.
- `:core:designsystem` holds everything both screens draw with, and nothing about audio or notes.
- `:feature:*` modules never depend on each other.
- Only `:app` wires concrete implementations together (`AppContainer`) and switches between screens (`MainActivity`).
- `:baselineprofile` only runs on demand with a phone connected (see §4, Baseline Profile). CI never runs it.

## 3. Signal pipeline

```
 Microphone
    │  AudioRecord.read()  (dedicated thread, 48 kHz mono float, blocking; built-in mic while a
    │                      Bluetooth headset is connected)
    ▼
 AudioRecorder ──Flow<FloatArray>(chunk = one hop ≈ 21 ms, 1024 samples at 48 kHz)──►
    ▼
 FrameAssembler        ring buffer → overlapping analysis window (≈ 85 ms, 4096 samples at 48 kHz)
    ▼
 SignalGate            RMS level check (< ~-50 dBFS → "no signal"), DC offset removal
    ▼
 PitchDetector (YIN)   [upsample to ≥ 32 kHz if the rate is lower] → 4 kHz low-pass → difference fn
    │                  → CMNDF → absolute threshold → whole-period checks → least-squares
    │                  refinement → PitchResult(frequencyHz, confidence), or PitchResult.NONE
    ▼
 PitchSmoother         Hz → fractional MIDI (NoteMapper.midiOf, honours A4) → octave-jump rejection
    │                  → median of 5 → EMA (snaps on a new note, smaller steps when unsure)
    │                  → note with ±15-cent hysteresis
    ▼
 NoteMapper / Tuning   note name + octave; in Auto mode → nearest string in tuning, cents from it
    ▼
 TunerViewModel        combine with settings → StateFlow<TunerUiState>
    ▼
 Compose UI            needle gauge, note name, cents, string row, in-tune indicator + haptic
```

### Key numbers
- **Sample rate**: 48 000 Hz. This is the device's native rate on most phones, which avoids resampling. `SampleRateSelector` reads `AudioManager.PROPERTY_OUTPUT_SAMPLE_RATE` and uses it if it is between 44 100 and 48 000 Hz (higher native rates would only cost CPU), then tries 48 000, 44 100, 32 000, 16 000 and 8 000. The first rate `AudioRecord.getMinBufferSize` accepts wins. The low ones are a last resort; any rate from 8 to 96 kHz works end to end (see "Other sample rates" below).
- **Analysis window**: 4096 samples, or about 85 ms. Low E (82.41 Hz) has a 12.1 ms period, so the window holds about 7 periods. That is enough for YIN, which needs at least 2. Bass and 7-string support (down to ~30 Hz) will need 8192 samples.
- **Hop**: 1024 samples, or about 21 ms. That gives ~47 pitch estimates per second, which the smoother turns into a calm needle.
- **Detection range**: 62 Hz to 1500 Hz for the default guitar profile. This sets YIN's τ range (τ_max = sampleRate / f_min). The floor sits just above 60 Hz mains hum, so a humming amplifier or fridge alone reads nothing, and still below drop C (C2, 65.4 Hz).
- **YIN threshold**: 0.15 (tunable; the paper suggests 0.10–0.15). The first CMNDF dip below it is accepted as the period.
- **Accuracy target**: ±1 cent on synthetic test signals and ±3 cents on recorded guitar fixtures.
- **"In tune"**: |cents| ≤ 5 held for at least 300 ms (counted in frames: 15 hops at 48 kHz). It then stays in tune until the reading drifts past 7 cents, so a note hovering at 5 cents doesn't flicker. That is the default **Relaxed** precision; the **Precise** setting narrows it to ≤ 2 cents, released past 3 (same 300 ms hold). Show a green state and give one haptic tick (see §5, Settings).

### Other sample rates
`AnalysisSettings.forSampleRate(rate)` (8–96 kHz) scales the window and hop with the rate, so they always last ≈ 85 ms and ≈ 21 ms and the smoother's frame counts mean the same time. 48 kHz gives exactly the numbers above, 44.1 kHz a 3763-sample window and 941-sample hop. `PitchPipeline` builds its `FrameAssembler` and detector from it, and `AudioConfig.forSampleRate` makes the recorder's chunks one hop long. A rate outside 8–96 kHz ends the flow with `InitializationFailed` instead of crashing.

Below 32 kHz a period spans too few samples for the ±1 cent target (≈ 5 cents at 8 kHz, ≈ 2.5 at 16 kHz). There `UpsamplingPitchDetector` first interpolates the frame by an integer factor to ≥ 32 kHz (×4 at 8 kHz, ×2 at 16 or 22.05 kHz) with a polyphase windowed-sinc FIR (Kaiser, β = 8, 32 taps per phase, cut-off 0.45 × the input rate), then runs YIN at that rate. YIN's low-pass drops to 0.4 × the input rate (3.2 kHz at 8 kHz) so no interpolation images get through. Measured: every rate from 8 to 96 kHz within 1 cent on sines, saws, plucks and weak fundamentals; 8 kHz costs 0.5 ms per frame on the JVM.

### Frame assembly
`FrameAssembler` keeps a 4096-sample ring buffer. Callers `push()` audio chunks of any size. Each call consumes samples until a frame is ready, then stops so no frame is skipped. `readFrame(out)` copies the window oldest-first into a caller-owned array. The first frame arrives after one full window, then one every hop (1024). The ring and the output window are allocated once.

### Signal gate
`SignalGate.process(frame)` removes the DC offset in place (it subtracts the mean), then measures the RMS level in dBFS as `20 · log10(rms)`, so a full-scale square wave reads 0 dBFS and a full-scale sine about −3 dBFS. Silence is floored at −120 dBFS. The gate opens at **−50 dBFS** and closes only below **−56 dBFS** (6 dB hysteresis), so a decaying note doesn't flicker on and off. Frames are only sent to the pitch detector while the gate is open.

### Pitch detection (YIN)
`YinPitchDetector` follows de Cheveigné & Kawahara (2002), steps 2–5, with two additions. The difference function `d(τ)` is computed with the FFT (`FftDifference`, see §4). Both were added because measurements on synthetic signals missed the ±1 cent target without them.
1. **Low-pass pre-filter.** A 4th-order Butterworth at 4 kHz (two RBJ-cookbook biquads) runs into a scratch buffer, and its ~92-sample start-up transient is skipped. Without it, very bright tones (full-band sawtooth/square near 1.4 kHz) give a V-shaped dip that 3-point parabolic interpolation misjudges by ~2.5 cents. The filter also removes hiss above 4 kHz.
2. **Adaptive least-squares refinement.** Instead of a fixed 3-point parabola, a cubic is fitted to the raw difference function over the lags `τ ± k` that lie within 5% of the way from the dip to the mean (`k` ≤ τ/16). Sharp dips use k = 1, which is the classic parabola. Broad dips (pure low notes) average over dozens of lags. With white noise at 20 dB SNR this cut the worst low-E error from ~23 cents to under 1. The cubic term removes a ~0.3-cent bias that a wide parabola picks up from the fixed integration window.

**Range edge and whole-period checks.** The first dip is followed down to its minimum; if that is still falling at τ_max, the real minimum lies below 62 Hz and the frame has no pitch (this is what keeps 60 Hz hum out). Two checks then catch the period being off by a whole factor, both comparing raw `d` values:
- *Too long (noise).* In heavy noise `d′` is inflated at short lags (the cumulative mean is still small there), so the true period can miss the threshold and the first accepted dip is at 2 or 3 periods. If `d` at a local minimum near τ/k is at most 15 % above `d(τ)` (and `d′` there < 0.5), τ/k is taken. For a tone plus noise every multiple of the period has the same expected `d`, while τ/k of a true period carries the out-of-phase harmonics.
- *Too short (harmonics).* A high note with a strong 2nd harmonic and weak odd harmonics (e.g. 0.2 : 1 : 0.2) nearly repeats every half period, `d′(τ/2) ≈ 0.15`. If `d′(τ) ≥ 0.05` and `d` at 2τ or 3τ is below a quarter of `d(τ)`, that longer lag is the period.

Search range τ = 32…775 (1500…62 Hz) plus 50 extra lags for the fit. The integration window is `W = 4096 − 92 − 825 = 3179` samples. Confidence = 1 − d′(τ). `PitchResult` is a value class that packs two floats into a `Long`, and `PitchResult.NONE` means "no pitch". It is never nullable, so returning it doesn't box. Measured on synthetic signals: worst error ≈ 0.1 cent for sines, ≈ 0.5 cent for saw/square/pluck/weak-fundamental, < 1 cent at 20 dB SNR, < 5 cents at 10 dB SNR. There are no octave errors, including high strings with dominant 2nd/3rd harmonics. Allocation-free `detect()` is checked by a test that counts the bytes allocated.

### Smoothing
`PitchSmoother` works on fractional MIDI numbers, so cents are just ×100 and A4 calibration is already applied. Each frame passes through four stages:
1. **Octave-jump rejection.** A reading a whole number of octaves (±30 cents) away from the running median is dropped. If it holds for 3 frames in a row (~64 ms), it's a real octave change: the filters restart there.
2. **Median of the last 5** (~107 ms) removes other single-frame outliers.
3. **EMA, α = 0.3,** settles a step within about 10 frames. If the median is more than 50 cents from the EMA (a new string was plucked), the EMA snaps to it instead of sliding the needle across. Readings the detector is unsure of take smaller steps: the step is weighted by the confidence, 1 from 0.97 up, falling linearly to 0.2 at 0.88 and below. A clean tone scores ≈ 0.99; white noise 10 dB below it ≈ 0.97; at the same level ≈ 0.86, as does the quiet end of a note. This roughly halves the needle wobble in a noisy room and at the end of a decay without slowing down clean notes.
4. **Note hysteresis.** The shown note only changes once the reading is more than 65 cents (50 + 15) from it, so the displayed cents can reach ±65.

Frames without a pitch call `noReading()`. Up to 4 missed frames (~85 ms) keep the last reading; after that it is cleared. `MedianFilter` and `ExponentialSmoother` are reusable building blocks. Everything is allocation-free.

### Edge cases (measured, `EdgeCaseTest`)
What the user sees after the whole chain (frame assembly → gate → YIN → smoother) on synthetic signals:
- **Very noisy room, white noise:** always the right note; worst shown error 0.8 cents at 10 dB SNR, 1.7 at 6 dB, 2.5 at 3 dB, ≈ 10 at 0 dB (low notes; high notes stay under 2).
- **Mains hum (50 or 60 Hz) 10 dB below the string:** right note within 3 cents. Hum alone, however loud, shows nothing. *Known limit:* hum within ~6 dB of the string can make YIN lock onto a period the two share (e.g. G3 read as C2), or show nothing for the low strings. A hum notch filter would be the fix if real rooms ever need it.
- **High strings with strong 2nd/3rd harmonics** (B3 to C6): within 1 cent, clean or at 20 dB SNR, no octave flips while a pluck decays.
- **Sustain decay:** a 0.8 s-decay pluck in a quiet room (−70 dBFS) stays within 1 cent until the gate closes after ≈ 4 s, the gate closes once and the reading clears within 5 frames. Over −60 dBFS room noise the last frames wobble up to 6 cents, never another note. When room noise is above the gate's closing level (the S26 measured −52…−56 dBFS), the gate stays open and YIN stops reporting once the note sinks into the noise; shown readings stay on the note.
- **Bluetooth-like audio:** band-limited to 300–3400 Hz (narrowband, so low E has lost its fundamental and 2nd harmonic) or 100–7000 Hz at 48 kHz: within 0.2 cents. Native 8 and 16 kHz: within 1 cent, still ~47 readings a second.

### Note math
```
midi  = 69 + 12 · log2(f / A4)        (A4 default 440 Hz, configurable 415–466)
note  = ceil(midi − 0.5)               (round half down, so exactly half-way reads +50)
cents = 100 · (midi − note)            range (−50, +50]
```
Octaves use scientific pitch notation (MIDI 60 = C4). `Note` is a value class over the MIDI number, so passing notes through the pipeline doesn't allocate.
`Notation` (`SHARPS`, `FLATS`, `SOLFEGE`) names a pitch class for display: C♯ / D♭ / Do♯, using the real ♯ and ♭ signs. Solfège is fixed-do (Do is always C, B is Si). Each entry holds its 12 names in both spellings (sharps and flats, also Re♭ Mi♭ … for solfège), so `nameOf()` returns the same string instances every frame. `PitchClass.symbol` (with `#`) is only used internally, e.g. to parse the presets.

**Tuning spelling.** A preset is written the way players write it, and that wins over the setting's sharps or flats: Half step down is E♭ A♭ D♭ G♭ B♭ E♭ (Mi♭ La♭ … in Do Re Mi), Open D keeps its F♯ and Open E its G♯ even with flats chosen. `Tuning.spelling` (`Accidental.SHARP` / `FLAT`, null for tunings without black keys) comes from how the preset is written in `Tunings` (`"Eb2"` gives flats, `"F#3"` sharps; mixing both is refused). `Notation.nameIn(tuning, …)` names a string with the tuning's spelling and the notation's letters or solfège. The string row, the tuning menu, the "Play the E♭2 string" hint and the big note in guitar mode use it; chromatic mode is not tied to a tuning, so there the setting alone decides (D♯ or E♭).
In **Auto (guitar) mode** the target is the closest string of the selected tuning, measured in cents, not Hz. In **Chromatic mode** the target is the nearest equal-tempered note.

### Tunings
`Tuning(id, strings)` lists open-string `Note`s from lowest to highest (index 0 = string 6 on a guitar). `id` is the stable key saved in settings. User-facing names live in the app's string resources, so `:core:dsp` stays free of UI text. `Tunings` holds the presets (Standard, Drop D, Half-step down, Full-step down, DADGAD, Open G, Open D, Open E), with `Tunings.DEFAULT` = Standard and `byId()` for restoring a saved choice.
- `nearestStringIndex(midi)` takes the fractional MIDI from `NoteMapper.midiOf`, so it follows A4 calibration. It picks the string with the smallest |Δ| in semitones (equivalently cents), and ties go to the lower string. No allocation: it loops over a precomputed `IntArray`.
- `centsFromString(midi, index)` = 100 · (midi − string midi). It is **not** wrapped to ±50, so a string tuned far off still shows the full distance to go.

### Strobe model
`StrobeMotion` (`strobe/`) moves the strobe view's striped pattern, one animation frame at a time, the way `WaveMotion` moves the wave view's ribbon (which drifts by this same rule, through a `StrobeMotion` of its own). A mechanical strobe tuner's stripes drift at the beat rate between the string and its disc, in Hz, so high strings move faster than low ones at the same cents; here the drift comes from the cents deviation instead, so every string looks the same. `driftSpeed(cents)`, in stripe periods per second: **0 within ±0.5 cent** (finer than the detector's ±1 cent target, so a string that is in tune stands perfectly still rather than creeping with the reading's jitter), then **0.4 stripes/s for every cent beyond that** (1 cent ≈ one stripe in 5 s), up to **4 stripes/s** from 10.5 cents. Positive (rightwards) when sharp, negative (leftwards) when flat. It does not use the "in tune" flag: that window is 2 or 5 cents wide, and the strobe exists to show the last cent. `advance(seconds, cents)` eases the shown deviation towards the reading (rate 20/s, about 0.1 s, so a note starting doesn't jolt the pattern), then moves `phase` (0..1, wrapping) on by `speed · seconds`; a step is capped at 0.1 s. Without a reading the view stops calling it (the pattern freezes) or passes 0 (it coasts to a stop). The drawing reads `phase` (and `speed` or `shownCents` for extra cues) in the draw phase only; rows at whole multiples of the speed, as on a real strobe, can use `phase · n`, wrapped. Nothing is allocated per frame. Tests step it directly and feed synthetic sines 0, ±1, ±3, ±5 and ±30 cents off every open string through the app's chain (`TunerChain`): in tune it stays exactly still, off pitch it drifts the right way within 0.1 stripes/s of `driftSpeed`.

### Audio source selection
1. Use `MediaRecorder.AudioSource.UNPROCESSED` if `AudioManager.getProperty(PROPERTY_SUPPORT_AUDIO_SOURCE_UNPROCESSED)` is `"true"`.
2. Otherwise use `VOICE_RECOGNITION`. It is required to have AGC and noise suppression turned off.
3. Never use `MIC` or `VOICE_COMMUNICATION`. Their AGC and noise suppression distort pitch and level.

**Bluetooth headsets.** Android records from a headset's mic only over SCO/HFP or LE Audio, a call-quality link: 8 or 16 kHz, band-limited to ~3.4 or ~7 kHz, often with the headset's own noise suppression. Twangle never asks for that route (no `startBluetoothSco()` or `setCommunicationDevice()`), so normally the phone's mic records while the headset plays. In case another app or the system has opened SCO, `InputDeviceSelector` pins the built-in mic with `AudioRecord.setPreferredDevice` whenever a Bluetooth input (`TYPE_BLUETOOTH_SCO`, `TYPE_BLE_HEADSET`) is present. Wired headsets and USB audio interfaces keep Android's normal routing, so a plugged-in mic or interface still works. If no built-in mic is listed, routing is left to Android; band-limited or low-rate audio is still handled (see Other sample rates and Edge cases). *Not yet verified with a real headset.*

`AudioSourceSelector.candidates()` returns the inputs to try in that order (`AudioInput` lists only these two). `AndroidAudioRecorder` opens the first one whose `AudioRecord` initializes, so a device that claims `UNPROCESSED` support but fails to open it still falls back to `VOICE_RECOGNITION`.

### Audio capture
`AudioRecorder.chunks()` is a cold `Flow<FloatArray>`. The mic opens when collection starts and is released when it stops. `AndroidAudioRecorder` builds an `AudioRecord` (mono, `ENCODING_PCM_FLOAT`, buffer ≥ 4 chunks) and reads one-hop chunks (1024 samples at 48 kHz) with `READ_BLOCKING` on its own single-thread dispatcher. To avoid ~47 new arrays a second it fills a **pool of 4 arrays** in turn, behind a channel of capacity 2. The collector holds one chunk, the channel up to two and the reader fills the fourth, so a chunk is never overwritten while it's in use. The catch: **a chunk is only valid until the collector takes the next one.** Downstream code copies samples out (into `FrameAssembler`) inside `collect` and must not `buffer()` the chunks themselves.

`PitchPipeline` (in `:feature:tuner`, because it joins `:core:audio` and `:core:dsp`) wires the stages above: it collects the chunks, pushes them into a `FrameAssembler`, then runs `SignalGate` and the pitch detector (both sized by `AnalysisSettings.forSampleRate` for the recorder's rate) on `Dispatchers.Default`, emitting one raw `PitchReading(frequencyHz, confidence, levelDbfs, gateOpen)` per hop. The DSP objects and frame buffer are created once per collection. Only the small immutable reading for the UI is new each frame.

`TunerViewModel` builds on it. For each listening session it creates a `TunerInterpreter` that feeds every reading and its confidence to `PitchSmoother` (`noReading()` when there's no pitch) and turns the smoothed MIDI value into a `TunerUiState`. That runs on `Dispatchers.Default`, in the same coroutine as the detector. The mode switch and the saved settings are combined into one immutable `TunerOptions` (mode, tuning, A4, locked string, notation), rebuilt only when one of them changes and read on every frame. Listening waits until the settings have loaded, so it never starts with the wrong tuning. Switching modes or changing a setting takes effect on the next frame (~21 ms) without reopening the mic or losing the smoothing history. A new A4 is the exception: it restarts the smoother, because the smoothed notes were measured against the old A4.
- **Chromatic:** the smoother's note (with its ±15-cent hysteresis) and cents.
- **Auto:** the closest string (`nearestStringIndex`) and `centsFromString`, not wrapped. The target string is sticky: it only changes once another string is closer by more than 15 cents, so a note half-way between two strings doesn't flicker.
- **Auto, string locked:** tapping a string in the string row locks the target to it (`TunerViewModel.toggleString`, `TunerOptions.lockedString`); tapping it again goes back to automatic. The cents are the full distance to that string, so a string tuned far off, or one closer to its neighbour, can still be brought up to pitch. The lock is kept in memory only, survives switching to chromatic and back, and is released when the tuning changes (an index means a different string in another tuning). A lock on a string that doesn't exist is ignored. So people find the lock, guitar mode shows a one-time tip, a speech balloon pointing at the string row: "Tap a string to tune only that one" (see §5, tuner screen).
- The frequency shown is the smoothed one (`NoteMapper.frequencyOf(smoother.midi)`), not the raw reading.
- `InTuneDetector` sets `Detected.inTune` from the smoothed cents and the frame duration (`PitchPipeline.frameSeconds` = hop / sample rate). It restarts when the note stops or the target note changes, so a new string always has to earn "in tune".

Failures end the flow with a typed `AudioRecorderException`, which the ViewModel maps to a recoverable error state:
- `PermissionMissing`: `RECORD_AUDIO` isn't granted (checked before opening, and on `SecurityException`).
- `InitializationFailed`: no input could be opened at the chosen rate.
- `MicrophoneBusy`: another app holds the mic. Before Android 10, `startRecording()` fails or the record never reaches `RECORDSTATE_RECORDING`. From Android 10 the mic is shared and a higher-priority app (such as a phone call) silences us with zeros instead, so `isClientSilenced` is checked after the first chunk. Silencing that starts mid-session just looks like silence (the gate closes) and recording resumes when the other app lets go.
- `ReadFailed(code)`: `read()` returned an error, e.g. `ERROR_DEAD_OBJECT` when the audio server restarts. Collecting again reopens the mic.

`Throwable.toTunerError()` maps these to `TunerError` (`MIC_PERMISSION_MISSING`, `MIC_BUSY`, `MIC_UNAVAILABLE`, `MIC_STOPPED`). The UI shows a message and a "Try again" button that restarts collection.

**Measured on the Galaxy S26 (Android 16):** the device doesn't offer `UNPROCESSED`, so the recorder uses `VOICE_RECOGNITION` at 48 kHz. `dumpsys audio` shows no effects attached and `silenced:false`. A 440 Hz tone from a PC speaker read 439.98 Hz (−0.1 cents) at about −31 dBFS, and quiet room noise sits around −52 to −56 dBFS, right at the gate threshold.

## 4. Threading & performance
- `AudioRecord.read()` blocks, so it runs on a dedicated single-thread dispatcher (`Dispatchers.IO.limitedParallelism(1)`). That keeps it from starving other coroutines.
- DSP runs on `Dispatchers.Default`.
- **No allocations in the per-frame loop.** The ring buffer, YIN scratch arrays and the window buffer are allocated once and reused. Per-frame garbage at ~47 Hz causes GC jank.
- **YIN difference function via FFT.** It started as the direct O(W·τ_max) sum, about 2.6 M multiply-adds per frame (3179 × 825 lags): **1.1 ms per frame** on the JVM, but on the S26 simpleperf showed it taking 69 % of the app's CPU cycles and about 7 ms of CPU per frame, a third of a core whenever a note sounds. `FftDifference` now computes `d(τ) = e(0) + e(τ) − 2·r(τ)` (paper, eq. 7): the energies `e` as a running sum, the cross-correlation `r` from one complex FFT carrying both real inputs plus one inverse FFT (N = 4096 at 48 kHz, radix-2 `Fft` with precomputed tables, all in doubles, no allocation). `FftDifferenceTest` checks it against the direct sum (within 1e-10 of `d`); all accuracy and edge-case tests are unchanged. `./gradlew :core:dsp:benchmark` (the `*Benchmark` tests, kept out of `test` and CI because timings depend on the machine): YIN detect **1.05 → 0.48 ms** per frame on the JVM, gate + detect + smoother 1.06 → 0.49 ms, 8 kHz upsampled ≈ 0.5 ms (dominated by the upsampler). Budget: 2 ms. The `PitchDetector` interface is unchanged.
- **Silent frames stay off the main thread.** While nothing is heard every frame gives an equal `Listening` state. `TunerViewModel` drops repeats with `distinctUntilChanged()` on the DSP dispatcher, before `stateIn`, so they no longer wake the main thread ~47 times a second.
- UI updates go through one `StateFlow<TunerUiState>`, and the screen only does work for what visibly changes:
  - **ViewModel:** `distinctUntilChanged { old, new -> old.looksLike(new) }` on the DSP dispatcher drops every reading that would look the same as the last one sent: same text (cents in whole cents, frequency to 0.1 Hz, as `NoteDisplay` writes them) and the needle less than `NEEDLE_STEP_CENTS` = 0.03 cents away (≈ 0.2 dp at the needle tip of the widest gauge, below a pixel), or pinned to the same edge. `looksLike` compares field by field so it allocates nothing; `TunerUiStateShownTest` fails if `Detected` gains a field it doesn't compare. The comparison is against the last state *sent*, so slow drift still gets through once it adds up.
  - **Composition:** `TunerScreen` composes from `state.asShown()` (the same rounding) through `derivedStateOf`, so the screen recomposes only when the text changes. The exact cents reach the gauge as a lambda (`TunerContent(needleCents = …)`) that is never read while composing.
  - **Needle:** `NeedleGauge` follows the lambda with `snapshotFlow` into an `Animatable` (the same spring, damping 0.8, that `animateFloatAsState` used; each new target is started with `launch` so the spring keeps its speed). The needle is drawn pointing up in its own `graphicsLayer`, and the animated value only sets that layer's `rotationZ`, so a moving needle neither recomposes nor re-records any drawing; the dial is a separate, static `Canvas`.

### Measured on the Galaxy S26 (Phase 5)
Minified `benchmarkRelease` build, Android 16, tuner listening in portrait, 48 kHz `VOICE_RECOGNITION`. CPU from `/proc/<pid>/task/*/stat` (percent of one core), frames from `dumpsys gfxinfo`, hotspots from `simpleperf record --app`. The "note" rows used 10 s bursts of a 440 Hz tone from a laptop speaker.

| | Before (direct YIN, JIT only) | After (FFT YIN + Baseline Profile) |
|---|---|---|
| Silence: whole app | 7.8 % (main thread 2.3 %) | 5.6 % (main thread ≈ 0) |
| Note sounding: whole app | ≈ 45 % | ≈ 20 % |
| Note sounding: DSP thread | ≈ 34 % (≈ 7 ms/frame) | ≈ 9 % |
| Note sounding: main thread | ≈ 9–10 % | ≈ 11 % (see the recomposition fix below) |

- **Frames:** nothing is drawn in silence (0 frames in 30 s). With a steady note only the frames whose readout changes are drawn, 4–8 a second; median frame 5–7 ms, 90th percentile 5–10 ms.
- **Battery:** `batterystats` puts the app's CPU cost at ≈ 0.02 mAh per 90 s of listening (≈ 0.8 mAh an hour of a 4300 mAh battery). The screen, which the tuner keeps on, costs far more than the app's own work.
- **Main thread:** with a note sounding the tuner used to recompose on every reading (~47 a second), because the smoothed cents and Hz change slightly each time, although only a few frames a second looked different. Now readings that look the same never reach the main thread, the screen recomposes only when its text changes, and the needle moves by turning its layer (see above). Measured with the same per-thread CPU method, 3 × 7 s each, on a temporary build that fed a synthetic 440 Hz tone (±3 cent slow drift, noise at −20 dB) instead of the mic, so both builds got identical input:

  | Main thread, note sounding | Before | After |
  |---|---|---|
  | Guitar mode (needle pinned at the edge, text changing) | 11.6 % | 5.1 % |
  | Chromatic mode (needle moving all the time) | 15.8 % at ~75 frames/s | 12.2 % at ~110 frames/s |
  | Main-thread CPU per drawn frame (chromatic) | ≈ 2.1 ms | ≈ 1.1 ms |

  Laptop-speaker bursts (the earlier method) were tried too, but how well the phone picked them up changed during the session (frame counts varied fivefold between runs), so the synthetic input is the comparison of record. In chromatic mode the needle now gets a frame whenever it moves (up to the display's 120 Hz) instead of waiting behind recompositions, so it is at least as smooth; that costs RenderThread time, but the main thread still does less.

### Baseline Profile
A Baseline Profile lists the classes and methods used at startup and on the tuner screen, so Android compiles them ahead of time on install instead of interpreting them first.
- `:baselineprofile` (plugin `androidx.baselineprofile`, versions in `libs.versions.toml`) has `BaselineProfileGenerator` (cold start, then listening, switching modes, opening settings and coming back) and `StartupBenchmark`. UI Automator finds the controls by test tag (`TunerTestTags`), which `MainActivity` exposes as resource ids with `testTagsAsResourceId`; tags don't change with the app's language.
- Generate with the phone connected: `./gradlew :app:generateBaselineProfile` (~5 min). It writes `app/src/release/generated/baselineProfiles/` (`baseline-prof.txt` and the startup profile `startup-prof.txt`), which is committed and packed into release builds. `profileinstaller` in `:app` installs it for APKs that don't come from the Play Store.
- Startup: `./gradlew :baselineprofile:connectedBenchmarkReleaseAndroidTest`. On the S26, cold start to first frame was 88.6 ms median without any compilation and 90.4 ms with the profile, i.e. no measurable difference on this fast phone. The profile stays because it is free, makes the DSP and Compose code compiled from the first frame instead of after JIT warm-up, and matters more on slower phones.
- Neither task runs in CI (both need a device).

### Release build: shrinking and signing
- **Shrinking:** the release build runs R8 (`isMinifyEnabled`) and resource shrinking (`isShrinkResources`). On the S26 check the APK went from 9.3 MB (`nonMinifiedRelease`, same code unshrunk) to 1.8 MB. Compose, AndroidX, DataStore and core-splashscreen bring their own keep rules; the app itself uses no reflection or serialization. `app/proguard-rules.pro` only keeps the constants of the enums that settings save by name (`TunerMode`, `ThemeMode`, `VisualStyle`, `WaveLook`, `Notation`) as a safety net. Never rename those constants: a saved setting must keep matching after an update.
- **Signing:** release builds are signed with the owner's **upload key**, which never goes in the repo. It lives in `~/.twangle-keys/` on the owner's PC (`twangle-upload.jks`, alias `upload`, RSA 4096, CN=Klaboukes) with `keystore.properties` (`storeFile`, `storePassword`, `keyAlias`, `keyPassword`) and a README for the owner. `app/build.gradle.kts` reads that file, or the absolute path in the Gradle property `twangle.keystoreProperties` (e.g. in `~/.gradle/gradle.properties`). Without the file (CI, other machines) the release build is left unsigned and nothing fails. `.gitignore` excludes `*.jks`, `*.keystore` and `keystore.properties`.
- Build a signed release with `./gradlew assembleRelease` (APK in `app/build/outputs/apk/release/app-release.apk`; `bundleRelease` for the store's AAB). Check it with `apksigner verify --print-certs` from the SDK build-tools. The Play Store will use Play App Signing: Google holds the app-signing key, and a lost upload key can be reset through Play support.
- **Version:** `versionName` is `0.9.0-beta` (the v0.9 beta from Phase 5 onwards), `versionCode` is major × 10000 + minor × 100 + patch (900 now, 10000 for 1.0.0). Every build that leaves the PC needs a higher `versionCode` than the one before; bump both together. The About page and the About link in settings show `versionName`.
- A release APK and the debug APK have different signatures, so switching between them on a phone means uninstalling first (which clears the saved settings).

## 5. Lifecycle & permissions
- `RECORD_AUDIO` is requested at runtime from the tuner screen. `rememberMicPermissionState()` tracks a `MicPermissionStatus` (rules in the pure, unit-tested `MicPermissionRules`) and `PermissionPrompt` shows one action per state:
  - `NOT_REQUESTED`: asked automatically once when the screen first appears. The prompt explains why and offers "Allow microphone".
  - `DENIED` (refused, `shouldShowRequestPermissionRationale` is true): rationale text, ask again.
  - `PERMANENTLY_DENIED` (refused and no rationale, so Android won't show the dialog again): "Open settings" deep-links to the app's page (`ACTION_APPLICATION_DETAILS_SETTINGS`). Dismissing the very first dialog by tapping outside looks identical to Android, so it lands here too. Settings still fixes it.
  - `GRANTED`: the tuner. The status is checked again on every `ON_RESUME`, so a grant made in Settings is picked up on return. Revoking in Settings kills the process, so the app starts fresh.
  - The status survives rotation (`rememberSaveable`). It isn't persisted: on a fresh start, an earlier permanent denial shows as `NOT_REQUESTED` until the automatic request comes back denied without a dialog.
- The microphone is open **only while the tuner screen is visible**. The ViewModel shares the pipeline with `SharingStarted.WhileSubscribed(5_000)`. The UI collects with `collectAsStateWithLifecycle()`, which stops in the background, so `AudioRecord` is released and the privacy indicator turns off.
- `MicLifecycleTest` (`:app` instrumented test, needs a device) checks this against Android's own list of active recordings (`AudioManager.activeRecordingConfigurations`): open while the tuner is shown, still open 3 s after `onStop`, released within about 5 s, reopened on return, released when the activity closes. Home, the lock screen and screen-off all go through `onStop`, so they follow the same path.
- There is no foreground service. Background microphone capture is neither needed nor allowed for this use case.
- If another app holds the mic, or `AudioRecord` fails to initialize, the UI shows a recoverable error state.

### Settings
The gear button in the tuner's top corner opens the settings screen (`:feature:settings`). `MainActivity` switches between the three screens (tuner, settings, About) with one saved `Screen` value, so the app needs no navigation library. A `SaveableStateHolder` keeps each screen's saved state (such as how far settings is scrolled) while another one is shown, and the back button returns from About to settings and from settings to the tuner. While settings are open the tuner isn't visible, so the mic is released after the usual 5 s. `SettingsViewModel` shows the saved settings and saves every change straight away; there is no "save" button.
The settings come in three groups, each under a heading in the style's title face and main accent colour (`titleLarge`, `primary`), marked as a heading for TalkBack so its users can jump from group to group: **Tuning** (A4 calibration, note names, in-tune precision), **Look** (style cards, light or dark, wallpaper colours, display and wave look) and **While tuning** (keep screen on, vibrate when in tune, tune up/down hint), followed by **About** (see below). Groups are 32 dp apart; rows and headings keep 16 dp from the column's edges, and only the style cards run to the edges, so their row visibly continues off-screen.
- **Note names:** radio buttons for sharps, flats or Do Re Mi (`RadioGroupSetting`, a reusable titled radio group). The interpreter writes `noteName` in the chosen notation, and the string row, tuning menu and "Play the La2 string" hint follow it. A preset tuning's own spelling wins over sharps or flats in guitar mode (see §3, Tuning spelling). Long names such as "Sol♯" use a smaller font to fit the string circles.
- **Style:** a sideways row of style cards at the top of the Look group (`StylePicker`, see §6, Visual styles); tapping one restyles the app at once.
- **Light or dark:** radio buttons for system default, light or dark, plus a "Wallpaper colours" switch (dynamic color), shown only on Android 12+ and only in the contemporary style (the others have their own colours). `MainActivity` reads the settings before drawing anything, so the app never flashes the wrong theme, and applies them through `TwangleTheme` (`ThemeMode.useDarkTheme(systemDark)`). It also calls `enableEdgeToEdge` again whenever dark/light changes, so the status-bar icons follow the app's theme rather than the phone's.
- **Keep screen on** (default on): while the tuner is shown and the mic permission is granted, `TunerScreen` sets `View.keepScreenOn` (`FLAG_KEEP_SCREEN_ON` on the window). Leaving the tuner (settings, home, lock) clears it, so the screen times out normally. It is a window flag, not a wake lock, so no extra permission is needed. `TunerViewModel.keepScreenOn` exposes the setting.
- **Vibrate when in tune** (default on): `InTuneHaptic` clicks the vibration motor once (`VibrationEffect.EFFECT_CLICK`, a 20 ms one-shot before Android 10) when `Detected.inTune` turns true. It uses `Vibrator` directly, not Compose/View touch haptics, because those obey the phone-wide touch-feedback setting, which many people (including the S26 we test on) switch off; this switch is the tuner's own. That needs the `VIBRATE` permission (normal, granted at install, declared by `:feature:tuner`). `InTuneTickRule` (JVM-tested) skips a second tick when the *same* note becomes in tune again less than 1.5 s after it last was: a short drop-out of the reading resets "in tune", and that shouldn't buzz twice. Whether the note was in tune is saved with the screen state, so rotating or coming back from settings doesn't tick. `TunerViewModel.vibrateInTune` exposes the setting.
- **In-tune precision:** radio buttons "Relaxed: within 5 cents" (default) or "Precise: within 2 cents" (`InTunePrecision`, saved as `in_tune_precision`). `TunerViewModel` passes it in `TunerOptions`, and `TunerInterpreter` swaps in `InTuneDetector.forPrecision(precision)` (5 / 7 or 2 / 3 cents) on the next frame when it changes, starting "in tune" over. Everything that follows `Detected.inTune` follows the precision too: the "in tune" colours and check mark, the haptic tick and the tune up/down hint, which therefore shows at 4 cents in Precise but not in Relaxed.
- **Show tune up/down hint** (default on): while a note is off pitch, `NoteDisplay` says which way to turn the peg, "Tune up ↑" (flat) or "Tune down ↓" (sharp), in the style's primary colour. `tuneDirectionFor(cents, inTune)` (`TuneDirection.kt`, JVM-tested) decides: nothing once `inTune`, and nothing while the reading shows "0 cents", so the hint never disagrees with the number. In the wave view the hint fills the otherwise empty pill; with cents it gets its own line between the pill and the frequency, which keeps its height while empty, also while listening, so nothing jumps when the note comes in tune or when a note starts or stops (with the switch off the line isn't there). On a phone on its side that extra line only fits with the smaller note, as with the wave view. TalkBack adds it in words without the arrow: "E 2, 12 cents flat, tune up". The one switch controls both; with it off TalkBack still reads the note and cents. `TunerViewModel.showTuneHint` exposes the setting.
- **A4 calibration:** a slider over 415–466 Hz with one stop per Hz, − and + buttons for single steps, and "Reset to 440 Hz". A drag is saved once the finger lifts. The tuner shows the reference in use as "A4 = 442 Hz" under the mode switch.
- **About** (its own page, `AboutScreen` with `AboutSection`, opened from a `LinkSetting` row at the end of settings that shows the version; on the settings list itself the long texts made it too crowded). Settings and About share `SettingsPage`: the see-through top bar with a back arrow and the centred scrolling column. The page holds the app's name and version (`MainActivity` passes `BuildConfig.VERSION_NAME` to both screens, so the library module needs no build config of its own), the free-forever promise (README), a short privacy statement (the gist of PRIVACY.md: keep the two in step), then a credit for every bundled font and the open-source libraries. Each credit is a button row ("Read the licence") that opens an `AlertDialog` with the full licence text, read from assets on `Dispatchers.IO` and reflowed to the screen (`reflowLicence`: paragraph lines joined, ruler lines dropped, capital headings on their own line). The app has no internet permission, so every licence text ships in the APK: the OFL texts in `:core:designsystem` `assets/licenses` (listed in `bundledFontCredits`, which a JVM test keeps in step with `res/font`), the Apache License 2.0 in `:feature:settings` `assets/licenses` (Jetpack Compose & AndroidX by Google, Kotlin & kotlinx.coroutines by JetBrains). A new library under another licence needs its own credit and licence file. Font and library names are proper names and stay in English; everything else is in `strings.xml` in both languages.

`SettingsRepository` (`:core:settings`) exposes `settings: Flow<AppSettings>` plus one suspend setter per value. `AppSettings` holds `a4Hz` (default 440), `mode` (`TunerMode.AUTO` / `CHROMATIC`, default `AUTO`; an unknown saved value gives `AUTO`), `tuning` (default Standard), `notation` (`Notation.SHARPS` / `FLATS` / `SOLFEGE`), `inTunePrecision` (`InTunePrecision.RELAXED` / `PRECISE`, default `RELAXED`), `theme` (`ThemeMode.SYSTEM` / `LIGHT` / `DARK`), `style` (`VisualStyle`, default `CONTEMPORARY`), `dynamicColor` (true), `keepScreenOn` (true), `vibrateInTune` (true), `showTuneHint` (true), `display` (`TunerDisplay.NEEDLE` / `WAVE` / `STROBE`, default `WAVE`; key `tuner_display`. Before the display picker this was the switch `show_waves`: while no display is saved, a saved `show_waves` gives `WAVE` (on) or `NEEDLE` (off), and saving a display removes that old key), `waveLook` (`WaveLook`, default `RIBBON`), `waveBreathesInTune` (true; key `wave_breathes_in_tune`, the temporary "When in tune: Breathe gently / Hold perfectly still" choice under the wave looks; it and the losing option go once the owner has compared both on the phone), `keepTwoPaneLandscape` (false; key `keep_two_pane_landscape`, the "Full layout on its side" switch at the end of the Look group) and `stringLockTipSeen` (false; key `string_lock_tip_seen`, set once the string-lock tip is dismissed, with no switch on the settings screen).
- `DataStoreSettingsRepository` stores them with DataStore Preferences in `files/datastore/settings.preferences_pb`. `AppContainer` creates the only instance, because DataStore allows one per file. The tuning is saved by its `id` and enums by their `name`, so those must never be renamed.
- Reading is forgiving. A missing, unknown or out-of-range value falls back to its default: a tuning id that no longer exists becomes Standard, and A4 is clamped to 415–466 Hz and rounded to whole Hz (`AppSettings.normalizeA4`, which the setter applies too). An unreadable file gives all defaults, and a corrupt one is replaced with defaults so saving works again.
- `FakeSettingsRepository` (in the `:core:settings` `testFixtures`) keeps settings in memory for ViewModel tests.

## 6. UI state model

```kotlin
enum class TunerMode { AUTO, CHROMATIC }   // in :core:settings, saved by name

sealed interface TunerUiState {
    data object PermissionRequired : TunerUiState
    data class  Error(val reason: TunerError) : TunerUiState
    data class  Listening(val mode: TunerMode, val tuning: Tuning, val a4Hz: Float, val lockedString: Int?, val notation: Notation) : TunerUiState   // no usable signal
    data class  Detected(
        val mode: TunerMode,
        val tuning: Tuning,
        val a4Hz: Float,               // concert pitch in use (A4 calibration)
        val notation: Notation,        // how note names are written
        val noteName: String,          // target note in that notation, e.g. "E", "D♭", "Re"
        val octave: Int,               // e.g. 2
        val frequencyHz: Float,        // smoothed
        val cents: Float,              // smoothed; Auto: unwrapped distance to the string, Chromatic: about ±65
        val targetString: Int?,        // index into tuning, Auto mode only
        val lockedString: Int?,        // string the user locked (then also targetString), else null
        val inTune: Boolean,           // ≤ 5 cents for ≥ 300 ms, released past 7 (Precise: ≤ 2, past 3)
    ) : TunerUiState
}
```

`TunerViewModel` exposes it as `state: StateFlow<TunerUiState>`, plus `mode: StateFlow<TunerMode>` so the mode switch reacts instantly. The mode is a saved setting, so the app reopens in the mode last used: `setMode` switches at once (a picked mode wins over the saved one in both `mode` and `TunerOptions`) and saves it in the background. `MainActivity` has already read the settings, so it passes the saved mode to `TunerScreen(savedMode = …)`, which hands it to the ViewModel as `mode`'s first value; without that the first frame would show Guitar and flip to Chromatic ~90 ms later (seen on the S26). The string-lock tip works the same way: `showStringLockTip` starts from `TunerScreen(savedStringLockTipSeen = …)`, so a tip dismissed earlier never flashes up at the start, and `dismissStringLockTip()` (also called by `toggleString`) hides it at once and saves `stringLockTipSeen`. Its inputs are `onPermissionChanged(granted)`, `setMode(mode)`, `setTuning(tuning)`, `toggleString(index)`, `dismissStringLockTip()` and `retry()`. The permission status itself lives in the UI (`rememberMicPermissionState`), which decides between the permission prompt and the tuner and passes "granted" on to the ViewModel. Until then the state is `PermissionRequired` and the pipeline isn't started, so the mic stays closed even while the screen is visible. Mode, tuning, A4 and notation come from `SettingsRepository`.

`TunerScreen` wires the ViewModel and shows the settings gear and, in the opposite corner, a palette button (both also on the permission prompt, inset 8 dp so they clear the frames some styles draw). The palette opens a bottom sheet with the style cards (`StylePicker`); a tap saves the style through `TunerViewModel.setStyle` and the app restyles behind the open sheet; `TunerContent(state, onRetry)` is the stateless screen body used by previews and UI tests. It shows `NeedleGauge` (half circle, −50…+50 cents, a tick every 10; readings beyond ±50, such as a string tuned far off in Auto mode, pin the needle to the edge) above `NoteDisplay` (big note name with its octave in the style's display face, shrinking to fit when a face or a solfège name is wide; "12 cents flat" rounded to whole cents in a pill; and the smoothed frequency). The pill's numbers use `numberFontFor(style)`: the title face, except in Prehistoric, whose 0 looks like a diamond. While `Listening`, the needle rests faded in the centre and the text asks to play a string (Auto) or a note (Chromatic). Above the gauge, `ModeSwitch` (Material 3 segmented buttons "Guitar" / "Chromatic") reads `TunerViewModel.mode`. Its selected segment takes the style's main accent (`primaryContainer`), not Material's default secondary colour, which put Futuristic's purple beside its cyan. In guitar mode `TuningPicker` shows the selected tuning's name ("Standard ▾") under the readout. Tapping it opens a menu of every preset with its open strings, the current one ticked, and the choice is saved through `TunerViewModel.setTuning` (user-facing names are string resources keyed by `Tuning.id`). Below it `StringSelector` shows the tuning's open strings (E₂ A₂ D₃ G₃ B₃ E₄), with `targetString` highlighted and marked `selected` for accessibility. Each string is a button (`onClickLabel` "Lock to this string" / "Pick strings automatically"). The locked string gets an extra outer ring and the state description "Locked", stays highlighted while listening, and the hint becomes "Play the A2 string". Until the user has tapped a string (or the tip itself) once, `StringLockTip` ("Tap a string to tune only that one ×") floats as a speech balloon with a small pointer at the string row, in the style's own corner shape (`shapes.medium`) and accent container colours (`primaryContainer` with a `primary` outline), light and dark. `GuitarControls` places it without giving it room, so nothing moves when it comes or goes, and the tuning picker stays visible and usable underneath it. Where it goes depends on the layout. On an upright phone there is no room under the strings (the S26 has about 14 dp), so the balloon sits in the 24 dp gap above the picker: its body ends where the picker's button starts, and its pointer reaches down beside the picker (14 % from the start) towards the strings. Above the picker it would cover the frequency or the tune hint once a note sounds, so there it fades out while a note is detected and comes back when the tuner is listening again. In the two-pane layout it sits under the string row, in the controls pane's bottom padding, pointer up, and stays while a note sounds. Its text grows with the system font only up to 1.3×, so the balloon still fits that gap. It never covers the note, the cents and frequency, the hint or the string chips (UI tests check the bounds in both views, at 2× font and on a phone on its side). The tip is one button: TalkBack reads its text and offers "Dismiss tip". It belongs to guitar mode only, so like the rest of the guitar controls it is hidden in chromatic mode without changing the slot's height. UI tests must not call `performScrollTo` on the balloon: it lies outside its parent's bounds, and Compose's scroll-into-view then never returns. They scroll to the picker or the strings instead, and every tuner UI test runs under a 10 s timeout rule (the slowest takes about 2 s) so that a hang can't leave a frozen window on the phone. In chromatic mode the picker and string row are hidden, but their slot keeps its height, so switching modes doesn't move the layout under the user's finger. With the wave view, which leaves the numbers out under the note, chromatic mode shows `ChromaticReadout` in that slot instead: the cents ("12 cents flat", fading to the "in tune" colour) and the frequency ("434.9 Hz"), at the bottom where the string row sits. With the needle they are already under the note, so the slot stays empty. The slot (`ModeSlot`) measures both modes' content all the time and takes the taller one's height (at least 104 dp), placing only the current mode's content and clearing the other's semantics, so nothing moves on a mode switch, also at 2× font. The readout's texts are hidden from TalkBack, because the note's live region already says the cents. While `inTune`, the needle, centre tick, note, cents text and highlighted string fade to the style's "in tune" colour (`StyleTokens.inTune`, read through `InTuneColor.kt`; Material 3 has no success role). A check-mark icon also appears beside the cents text, so "in tune" doesn't depend on seeing green. The cents pill fills with the "in tune" colour, a soft glow lights up behind the note and the note pops (grows 8 % and springs back). These animations run once per change and are read only in the draw phase, so nothing animates or recomposes while the state holds. String chips take the style's outline (an octagon for the Middle Ages, a chamfered tile for Futuristic, a circle otherwise) and, like the mode switch, a see-through backing, so they stay readable on busy backgrounds.

**Display** (setting "Display", radio buttons in the Look group): what shows how far off a note is under it, `TunerDisplay` *needle* (the cents in a pill and the frequency, as described above), *wave* (the default) or *strobe*. The needle dial is there in all three. The wave and the strobe both take the cents' place, so `NoteDisplay` and `TunerContent` treat them alike for layout (no pill colour or check mark, no frequency line, the `ChromaticReadout` in chromatic mode, the compact note on a phone on its side); only the picture under the note differs.

**Wave view** (display "Wave", the default). Most people don't know what a cent is, so `NoteDisplay(display = WAVE)` shows how far off the note is as a soft ribbon of sound under the note (`WaveView`) instead of in cents. It is not the recorded sound, and is kept low (40 dp) and frameless so it doesn't compete with the dial, but it gives the same "getting closer" cue as the strobe. It borrows the beats you hear when two notes are close but not the same: `WaveMotion` (plain Kotlin, JVM-tested) pinches the ribbon into pulses that drift right when sharp and left when flat. **The drift follows the strobe's speed rule exactly** (`StrobeMotion.driftSpeed`, see §3, Strobe model, in pulses per second; `WaveMotion` runs its own `StrobeMotion`, which is why `:core:designsystem` depends on `:core:dsp`): dead still within half a cent, 0.2 pulses/s at 1 cent, 1 at 3, 1.8 at 5, up to 4 from 10.5 cents. It comes from the exact cents, not the `inTune` flag (2 or 5 cents wide), so the last few cents still show. **The shape shows the distance from afar, up to 50 cents:** the pinch deepens (`depthFor`, `1 − (1 − √x)²` of the range beyond the still half cent: about 0.15 at 1 cent, 0.3 at 3, 0.8 at 50) and more pulses fit across (`beatsFor`, 1.5 to 4.5 with the square root of the distance) the further off. Close to the note the pulses smooth out, and within half a cent the band is perfectly even. The shape eases towards the reading at 5/s, depth and pulse count each on their own scale, so a new string never makes the pulses snap; the drift settles in about 0.1 s, as the strobe's. JVM tests check the drift at 0, ±1, ±3, ±5 and ±30 cents against `driftSpeed`, that it matches a `StrobeMotion` frame for frame, and that the shape grows all the way to 50 cents. The band slowly breathes (one breath every 2.5 s, 10 % of its height; the fireflies twinkle on the same clock). **For now this is a choice** (`waveBreathesInTune`, Settings "When in tune"): *Breathe gently* keeps breathing on the note; *Hold perfectly still* lets the breathing fade out (`WaveMotion.stir` eases to exactly 0 in about a second, at 6/s) while the drift stands still, so on the note nothing moves at all, like the strobe, and the band settles at its full, calm height. Off pitch both breathe. The owner compares both on the phone and the other one goes. `inTune` fades it to the "in tune" colour with a soft halo; off pitch it is a quiet tint of the style's primary colour, and without a reading it rests as a faint line. The dial already says how far off and which way, so there are no words for that: during a note the pill stays empty and uncoloured, without the check mark (it keeps its place, so nothing jumps); being in tune shows in the note's colour, glow and pop and the ribbon smoothing out. The frequency line is left out. TalkBack, which can't see the dial or the ribbon, still hears the cents ("E 2, 12 cents flat"). With the tune up/down hint on (see §5, Settings), the pill shows "Tune up ↑" or "Tune down ↓" while the note is off pitch and stays empty once in tune. The frame loop runs only while there is a reading, uses `withInfiniteAnimationFrameNanos` (UI tests skip infinite animations, which would never let them settle), and each frame redraws only the ribbon's own layer, without recomposing. In the two-pane layout on a short screen (a phone on its side) the note and the ribbon get smaller so the readout still fits (the note also does so for the tune hint's line).

**Strobe view** (display "Strobe"). `StrobeView` takes the wave view's place and size under the note: rows of stripes that drift right when sharp and left when flat and stand perfectly still within half a cent, for the last cent of fine tuning. It advances `StrobeMotion` (`:core:dsp`, see §3, Strobe model) in its own frame loop while there is a reading, with the exact cents and not the in-tune flag, and passes `phase` to `drawStrobe` (`:core:designsystem` `dial/Strobe.kt`, which doesn't depend on `:core:dsp`) with the current style: two rows of even stripes in that style's own marks (see *Visual styles*, Strobe), the lower row at twice the speed (`phase · 2`), as the rings of a real strobe disc. Its colour follows the wave's (a tint of the primary colour off pitch, the "in tune" colour with a soft halo in tune, faint without a reading, when the stripes freeze where they are). **The motion lives in the draw phase only:** the frame loop writes a frame-time state that only the `drawBehind` block reads, together with `StrobeMotion.phase`, so each frame redraws the view's own `graphicsLayer` and nothing recomposes. `StrobeViewTest` proves it: with the test clock on manual (which lets the "infinite" frame loop run) it steps 15 frames and checks that the stripes moved while the Recomposers' `changeCount` stayed the same (reading the frame time in composition makes it fail), and that within half a cent the pixels don't change at all. In other UI tests, with the clock on automatic, it is an infinite animation they skip. **TalkBack** skips the stripes (`clearAndSetSemantics {}`; only the test tag `TunerTestTags.STROBE` stays, for UI tests): `NoteDisplay`'s live region says the reading in words, the same sentence as with the needle and the wave ("E 2, 12 cents flat, tune up", in Dutch too), throttled as before. As the stripes move without recomposing, that sentence never changes between readings, so TalkBack isn't told about each frame (`TunerContentTest` steps a second of frames on the whole tuner screen and checks the stripes moved while nothing recomposed and the sentence stayed the same). **Layout:** the stripes keep their 240 × 40 dp (30 dp high in the compact note on a phone on its side) at any font size; `TunerContentTest` checks them whole and in view on a phone on its side, on a tablet upright and on its side, and reachable by scrolling with 2× font (also on its side and in chromatic mode). `stripeOffset` and the per-style `stripePeriod` are JVM-tested.

**Wave looks** (setting "Wave look", shown while the display is the wave). The ribbon is one of six looks (`WaveLook`), picked from a grid of cards with a moving preview of each (`WaveLookPicker`). All six share `WaveMotion` (`dial/WaveMotion.kt`) and give the strobe's "getting closer" cue, **each in its own way**: off pitch something moves one step of the look per strobe period (`WaveMotion.phase`), so at the strobe's speed, right or outwards when sharp and left or inwards when flat; within half a cent everything stands still. How unsettled a look is, `unrest(depth)` (`√(depth / MAX_DEPTH)`: 0 on the note, about 0.4 a cent off, 1 at 50 cents), shows the distance from afar and eases to nothing on the note, so every look settles into one calm shape there. Only the ribbon is drawn in each style's own marks; the other five have one shape for every style, in the style's colours. *Ribbon*: pulses drift and smooth out (see above). *Stripes*: drift one stripe per period and lean right when sharp, left when flat (the strobe look replaces them in the next step). *Dots*: a dot-matrix strip that scrolls one dot per period (`dotColumnAt`; one extra column slides in at the end while another slides out, both faded by `edgeFade`), each column lit as far as the ribbon reaches as it passes. *Fireflies*: eight specks per pulse that ride the pulses (one pulse per period), scattered up and down and fluttering on the breath clock in proportion to `unrest`; on the note they glide into an even, level line, larger towards the middle (`fireflyAt`). *Loop*: a hoop spinning about its upright axis like a coin, one turn per period, so at the beat rate (`loopAt`, `loopWidth`); `unrest` sets how far it turns, so a cent off it only rocks and further off it spins right round. Its near half is drawn brighter and thicker than its far half (`loopNearSide`), so you see the near side sweep right when sharp and left when flat (the halves have flat ends, so no darker spot shows where they meet); on the note it settles face-on into a still, open ring with a fainter rim inside. *Ripples*: five rings spreading out from the middle like ripples on water when sharp and drawing in when flat, one ring apart per period (`rippleAt`), each fading in at the middle, thinning as it spreads and fading out at the edge; off pitch they swell unevenly like stirred-up water, more the further off and more as they spread (`rippleWobble`, two and three slow swells, up to 7 %), and on the note they are smooth ovals. Every position is a continuous, periodic function of `phase`, so nothing jumps when the direction flips or the phase wraps (a whole period later each dot, firefly or ripple stands where its neighbour stood). **Still in tune** follows the temporary breathe/hold choice: with *Hold perfectly still* `WaveMotion` snaps its shape exactly onto the goal once it is too close to see, and `stir` (passed to `drawWave`) stops the fireflies' twinkle too, so nothing changes at all; with *Breathe gently* only the size swells and the fireflies twinkle, with no sideways drift. Drawing allocates nothing per frame: one `Ribbon` is refilled and the caller's `Path` reused (both views draw on the main thread), and strokes come from `roundStroke` and `buttStroke`, which make each quarter-pixel width once. `drawWave` (`dial/WaveLooks.kt`) draws them; `unrest`, `dotColumnAt`, `edgeFade`, `fireflyAt`, `loopAt`, `loopWidth`, `loopNearSide`, `rippleAt` and `rippleWobble` are JVM-tested for direction (sharp vs flat), stillness on the note and no jumps at the wrap. The previews play a short loop (18 cents flat, tuned up to the note, slowing over the last few cents as when turning a peg, in tune, 14 cents sharp, tuned down, in tune; the "in tune" colour within 2 cents) through one shared `WaveMotion` and the same `drawWave`, so all six cards move exactly as the tuner's wave does and breathe or hold still on the note; like the wave view, it is an infinite animation that redraws only the cards' canvases, without recomposing.

### Visual styles
The user picks one of seven styles: Prehistoric, Middle Ages, Classic, Retro, Contemporary (the default, and the only one that can follow the wallpaper), Futuristic and Space Age. A style is more than colours; each one sets:
- **Palette** (`StylePalettes.kt`): a light and a dark `Palette` per style, turned into a Material 3 `ColorScheme` (containers are mixes of their colour and the surface). Light or dark still comes from the theme setting. `StylePaletteTest` holds every palette to WCAG 2.2 contrast: 7:1 for body text on backgrounds and surfaces, 4.5:1 for secondary text, accents and text on filled controls, 3:1 for the "in tune" colour, outlines, needle and ticks.
- **Lettering** (`StyleTypography.kt`): a display face for the note, headlines and titles; reading text stays in a plain face. The faces are bundled in `core/designsystem/src/main/res/font`, all under the SIL Open Font License (licence texts in `assets/licenses`): Caesar Dressing (Prehistoric), MedievalSharp (Middle Ages), Playfair Display (Classic), Righteous (Retro), Orbitron (Futuristic) and Michroma (Space Age). Contemporary uses the phone's font. About 0.7 MB in all, nothing is downloaded at run time.
- **Music signs** (`MusicSigns.kt`): none of those faces has ♯ or ♭, and the phone's fallback drew them at a different size in each (as big as the letter in Classic, tiny and sunken in the menu and settings). So every ♯ ♭ ♮ (and the notes ♩ ♪) comes from one bundled face, `music_signs.ttf`: Noto Sans Symbols (OFL) cut down to those five glyphs (2.6 KB, made with `scripts/subset-font.py`). `musicText()` turns a string into an `AnnotatedString` that sets each sign in that face; a sign right after a letter is set like a chord symbol, 0.7 em and raised (a ♭, which has no tail below the line, 0.8 em and raised a bit less, so both tops line up near the letter's top). A sign on its own (♭/♯ under the dial) keeps the text size. It is used for the big note, the string chips, the tuning menu, the hint ("Play the C♯3 string"), the notation setting and the dial labels. The text itself is unchanged, so UI tests see "C♯"; TalkBack hears the names in words through `NoteNameSpeech` (see Accessibility).
- **Waiting for a note:** the big note's place shows a faint ♪ in that face. It used to be an em dash, which some display faces draw as a wide block that looked like a grey loading bar.
- **Shapes**: cut corners for the Middle Ages and the HUD, soft pebbles, fine Classic corners, fat 70s curves and 60s capsules.
- **Background** (`StyleBackdrop`): drawn by `MainActivity` once behind both screens, which are see-through (`Scaffold(containerColor = Transparent)`, with `contentColor = onBackground`, because a transparent container gives no content colour). Cave wall with hand stencils, parchment in a gold-ruled border, an ivory concert hall, 70s walnut with a sunburst and stripes, a calm wash, a neon perspective grid with HUD brackets, and a starfield with a ringed planet (or atomic orbits and starbursts by day). It sits in its own `graphicsLayer`, so tuner readings never redraw it, and seeded random points make it the same every time. Frames keep inside the safe-drawing insets and within the 16 dp margin the screens keep free of text: Classic's brass lines sit 5 and 8 dp in (further in, they crossed the mode switch, because the tuner's column nearly fills a phone's height), the Middle Ages' gold rules 6 and 10 dp, and the HUD's corner brackets end 15 dp from the edge (bigger, they covered settings rows scrolling past the corners). The settings list ends 24 dp above the bottom inset, so its last row clears the frames and Retro's stripes.
- **Dial** (`dial/Dial.kt`): `drawDialScale` and `drawDialNeedle` draw each style's dial in the shared geometry (pivot `DialPivotInset` above the bottom centre of a 2:1 box, ±50 cents over a half circle): an ochre arc with a flint-tipped spear, a gold-ruled manuscript scale with a sword, an ivory clock face with a watch hand, a backlit 70s VU meter with red zones and an "in tune" lamp, the clean contemporary track, a segmented neon HUD, and an orbit with a satellite around a ringed planet. `DialColors` gives each needle and centre mark an out-of-tune and an in-tune colour (the VU meter's face is lit in both brightnesses, so its needle stays dark). `NeedleGauge` still only turns the needle's layer per reading.
- **Sound ribbon** (`dial/SoundRibbon.kt`): `drawStyleRibbon` draws the wave view's ribbon in each style's own marks, without a frame: dabs of paint, slanted quill hatching, an engraved outline with a hairline, a glowing phosphor band, rounded voice-memo bars, thin neon bars and pairs of stars tracing its edges. `ribbonAt` (JVM-tested) gives its shape: a lens that narrows to nothing at both ends, pinched into drifting pulses.
- **Strobe** (`dial/Strobe.kt`): `drawStrobe(style, phase, color, glow)` draws the strobe view's stripes in each style's own marks, like the ribbon: finger-pressed ochre dabs, slanted quill strokes between ruled lines, crisp bars between engraved hairlines (a polished strobe disc), rounded bars on a backlit drum that always glows a little, rounded pills, thin neon segments over a hairline, and a row of little stars over a row of glowing dots. Each style has its own stripe spacing (`stripePeriod`, 8–18 dp). Every stripe of a row looks the same, so the pattern wraps from phase 1 to 0 without a jump; the rules and hairlines stay put while the stripes move. It allocates nothing, as it runs every frame.

`TwangleTheme(style, darkTheme, dynamicColor)` provides the `ColorScheme`, `Typography`, `Shapes` and `LocalStyleTokens` (`StyleTokens`: the style, its "in tune" pair, dial colours and the unfaded scheme). The tokens are remembered per style and brightness, so recomposing for another setting changes nothing. A change of style or brightness fades every scheme colour over 450 ms (one `Animatable`, colours mixed with `lerp`) and cross-fades the background. Style cards in `StylePicker` are small live previews: each wraps its own `TwangleTheme`, so it shows that style's background, dial and lettering whatever the app's current style.

### Landscape and wide screens
`TunerContent` picks its arrangement from the space it gets, not from the device type: `tunerLayoutFor(width, height, compactLandscape)` (JVM-tested) returns `SINGLE_COLUMN` unless the window is at least 600 dp wide (the Material 3 "medium" width class) *and* wider than tall. So a phone held upright, a tablet in portrait, split screen and near-square foldables keep the single column (max 480 dp wide). A phone on its side or a tablet in landscape gets `COMPACT` when `TunerContent(compactLandscape = true)` (the default), else `TWO_PANE`. `compactLandscape` is the one switch between the two: `TunerScreen` passes `!keepTwoPaneLandscape`, from the Settings switch "Full layout on its side" (Look group, default off, so compact). `TunerViewModel.keepTwoPaneLandscape` follows the setting live and starts from the value `MainActivity` already read (`savedKeepTwoPaneLandscape`), so a phone on its side doesn't switch layout a moment after opening. `TunerScreenTest` runs the whole screen (fake recorder, fake settings) on a phone on its side and checks both layouts and a live change.

**Compact layout** (`COMPACT`, `CompactLayout` in `TunerScreen.kt`): only what matters while tuning, big enough to read from a distance. The note column (the note at full size, the cents pill or the wave/strobe, the frequency, the tune hint) is measured first, and the needle gauge takes all the width left (`FitGauge`: as wide as it fits, at most 840 dp, smaller when it would be taller than the screen, keeping its 2:1 shape). On the S26 that is about 450 dp, more than twice its size in the two-pane layout. The mode switch, the A4 label, the tuning picker, the string buttons and the string-lock tip are hidden; the palette and settings buttons in the corners stay. Under the note, guitar mode shows a small string row (`StringSelector(small = true)`: 32 dp chips, not buttons, labels that don't grow with the font) with the target string highlighted, or the locked string while listening; it is hidden from TalkBack, because the note's reading names the string. Chromatic mode with the wave or strobe shows the `ChromaticReadout` there instead (with the needle the cents are already under the note). An error shows its message and retry. The note column scrolls with a very large font. **Tested in every style:** each style has its own fonts and dial, so `CompactLandscapeStylesTest` (parameterised over `VisualStyle`) checks on a phone and a tablet on their side that the needle, wave and strobe, in guitar and chromatic mode, fit beside a meter at least half the width, with nothing overlapping and nothing in the top corners where `TunerScreen` puts the palette and settings buttons; that everything can be scrolled to at 2× font; that the meter is drawn in light and dark; and that a tap or TalkBack's "Show controls" brings back the controls. Layout runs only in the light theme, because a style's fonts and dial shape don't change with dark (`typographyFor(style)`), only its colours.
- **Tap for the controls:** a tap anywhere (`detectTapGestures`), or TalkBack's double tap on the screen, which is a "Show controls" button (Dutch "Bediening tonen"), cross-fades to the two-pane layout for `COMPACT_CONTROLS_SHOWN_MS` (5 s), lengthened by Android's "time to take action" accessibility setting (`calculateRecommendedTimeoutMillis`). Every touch while they show starts the time again (`onEveryTouch` watches touches in the initial pass without taking them), and an open tuning menu holds it (`TuningPicker(onExpandedChange)`), so the menu never vanishes under the finger. Then it fades back to the compact layout. The shown state is local UI state in `TunerContent`; a rotation starts compact again.

**Two-pane layout** (`TWO_PANE`, `TwoPaneLayout`, also what the compact layout shows while its controls are up):
- **Readout pane** (start side): the gauge above the note. `GaugeAboveNote` is a small custom `Layout`: it measures the note at its natural size and shrinks the gauge (keeping its 2:1 shape, never below 160 dp wide, at most 560 dp) so both fit in the pane's height. A phone on its side is only ~330 dp tall, too short for a full-width gauge.
- **Controls pane** (end side, under the settings gear): mode switch, A4 label, tuning picker and strings, max 480 dp wide, with 48 dp clearance top and bottom so nothing scrolls under the gear.
- Each pane scrolls on its own when it doesn't fit (very large fonts). Both screens use `WindowInsets.safeDrawing`, so content stays clear of the camera cutout, which sits at the side in landscape.
- The activity is recreated on rotation (no `configChanges`). The mode and tuning are saved settings and the locked string lives in `TunerViewModel`, which survives that, and the `WhileSubscribed(5_000)` grace period keeps the same `AudioRecord` session running through the rotation.
- **Settings** scrolls across the whole width but keeps its rows in a centred column at most 600 dp wide.

### Accessibility
- **TalkBack:** `NoteDisplay` is one node whose description is the reading in words, e.g. "E 2, 12 cents flat", "F sharp 2, in tune" or the hint ("Play a string"), and it is a *polite live region*, so TalkBack reads changes without moving focus. Its visible texts are `hideFromAccessibility()`, so they aren't read twice (UI tests still find them). The screen changes ~47×/s, so `SpokenReadingThrottle` (JVM-tested) decides what TalkBack gets: the first text at once, a new note or in-tune change once it has lasted 400 ms, losing the note after 1.5 s (so drop-outs stay quiet), and only-the-cents-moved at most every 2 s. Every TalkBack text that names a note goes through one helper, `NoteNameSpeech` in `:core:designsystem` (`rememberNoteNameSpeech()`, JVM-tested against every name the app can show): the readout, the string chips, the locked-string hint ("Play the E flat 2 string"), the tuning menu (each preset says its name and open strings, "Half step down, E flat, A flat …") and the notation choices in Settings. It turns ♯/♭ into words ("C sharp"), since TalkBack reads the symbols badly. In Dutch (the `spoken_dutch_letter_names` bool resource) letter names are said the way Dutch musicians say them: cis, dis, eis, fis, gis, ais, bis; ces, des, es, fes, ges, as, bes; naturals plain c … b (b, not h). Solfège has no such forms and keeps "Sol kruis", "Mi mol". The octave is the number on screen in every language ("cis 4"). What's on screen doesn't change. UI tests check the Dutch descriptions with `DeviceConfigurationOverride.Locales`; that doesn't reach popups, so the Dutch tuning menu is checked on the phone. The needle gauge is hidden from TalkBack (`clearAndSetSemantics {}`), because the readout says the same thing.
- **Labels:** each string reads "A 2" plus "selected"/"Locked" and the lock/unlock action; the tuning picker says "double-tap to change tuning"; the A4 slider reads "442 Hz" instead of a percentage. Settings rows are whole-row radio buttons and switches (§5).
- **Large fonts:** the tuner body scrolls when it is taller than the screen (in two-pane mode each pane scrolls separately). The 112-unit note name is sized in dp, so it doesn't grow further with the system font. The string labels follow the font scale up to 1.3× (they sit in fixed 48 dp circles), and the guitar slot grows past its 104 dp minimum when the tuning picker does. A UI test checks that every control is reachable at 2× font.

### Languages
- **English (default) and Dutch.** Each module keeps its texts in `res/values/strings.xml` with a Dutch copy in `res/values-nl/strings.xml`; the app follows the phone's language. Brand and symbols (`app_name`, `DADGAD`, ♯/♭, the waiting ♪) are `translatable="false"`.
- **Per-app language (Android 13+):** `:app` sets `androidResources.generateLocaleConfig = true` with `res/resources.properties` (`unqualifiedResLocale=en`), so the system *App languages* page offers Twangle in English or Dutch. `localeFilters` keeps only `en` and `nl`, so library texts (Material menus) never appear in a third language.
- **Formatting:** counts use plurals (`tuner_cents_flat/sharp`) and numbers go through placeholders (`%1$.1f Hz`), which Android formats in the resource locale, so Dutch shows "440,0 Hz" and "12 cent te laag". Note names are not translated: they follow the notation setting (C♯ / D♭ / Do♯) in every language. TalkBack's spoken accidentals are resources ("C sharp"); Dutch says letter names in one word (cis, des, es, see TalkBack above) and keeps "kruis" / "mol" only for solfège.
- **Guard:** `LocalizationTest` (JVM, in `:app`) fails when a module's English string has no Dutch copy or a different set of placeholders, and when Kotlin code passes a hard-coded literal to `Text(...)`, `contentDescription`, `stateDescription`, `onClickLabel` and similar. Lint's `MissingTranslation` and `StringFormat*` checks back it up.

## 8. Testing strategy
| Layer | How |
|---|---|
| `:core:dsp` | JVM unit tests with signals from `TestSignals` (in the `testFixtures` source set, so other modules' tests can use them via `testImplementation(testFixtures(project(":core:dsp")))`): pure sines, sawtooth/square waves (rich harmonics), a weak fundamental with strong 2nd harmonic, added white noise or mains hum, band-limited (Bluetooth-like) audio at any rate, and decaying plucks. Assert ±1 cent. `EdgeCaseTest` runs whole recordings through the app's chain (`TunerChain`: frame assembly, gate, detector, smoother) and checks what would be shown (see §3, Edge cases). Recorded WAV fixtures go in `src/test/resources/`. |
| `:core:audio` | JVM tests for the pure parts (source, sample-rate and Bluetooth input selection, chunk sizes). Instrumented tests (`./gradlew :core:audio:connectedDebugAndroidTest`, device needed) record from the real mic: full chunks, pooled arrays, mic released after collection. `FakeAudioRecorder` (in `:core:audio`'s `testFixtures`, used via `testImplementation(testFixtures(project(":core:audio")))`) plays a `FloatArray`, typically from `TestSignals`, as chunks paced like a real mic (instant under `runTest` virtual time). It can loop, end with an `AudioRecorderException`, and reports `isRecording` / `startCount`, so everything downstream, including mic lifetime, can be tested without a device. Like the real recorder it reuses its chunk array. |
| `:core:settings` | JVM tests of `DataStoreSettingsRepository` on a real DataStore file in a temporary folder: defaults, saving, surviving a restart, clamping, and falling back on unknown or unreadable values. |
| `:core:designsystem` | JVM tests: WCAG contrast of every palette in both brightnesses, dark versions dark and light ones light, every style distinct with its own lettering; `ThemeMode.useDarkTheme`; every bundled font credited with its OFL text (`FontCreditsTest`). |
| `:feature:tuner` | ViewModel tests with `kotlinx-coroutines-test` and the fake recorder. Compose UI tests for each `TunerUiState`. |
| `:feature:settings` | `SettingsViewModel` tests with `FakeSettingsRepository`; `CreditsTest` for the licence reflow and the bundled Apache licence. ## 9. Privacy
Audio is processed in memory and thrown away immediately. Nothing is recorded to disk or sent over the network, and the app requests no `INTERNET` permission. The merged manifest holds only `RECORD_AUDIO`, `VIBRATE` (in-tune tick) and AndroidX's internal `DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION`.

The privacy policy is [PRIVACY.md](PRIVACY.md), with a Dutch copy in [PRIVACY.nl.md](PRIVACY.nl.md); keep the two in sync. It also covers the saved settings: they stay in DataStore on the device, and because `android:allowBackup="true"` (no extraction rules) Android's own backup and device-to-device transfer may include them. If a change touches permissions, stored data, backup or anything that leaves the device, update the policy (and its effective date) in the same change. The About page (Phase 8) shows it in the app; the Play Store listing will link to a public copy (Phase 21), and the data-safety form will say no data is collected or shared.
